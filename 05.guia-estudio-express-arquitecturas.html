Bloque 1

Express: del http nativo al framework

Toda esta guía asume que la API está escrita con Express. Antes de discutir cómo estructurarla, conviene ver qué es Express y por qué prácticamente ningún proyecto Node arranca sin él — y la mejor forma es escribir el mismo endpoint con y sin él.

Node ya trae un servidor: el módulo http

Node no necesita instalar nada para levantar una API: el módulo http del core alcanza. El mismo GET + POST de productos, en http puro, se ve así:

server.js — solo con el módulo http nativo
import http from 'node:http';

const productos = [{ id: 1, nombre: 'Teclado', precio: 25000 }];

const server = http.createServer((req, res) => {
  // ruteo manual: comparar método + url a mano
  if (req.method === 'GET' && req.url === '/api/productos') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify(productos));
    return;
  }

  if (req.method === 'POST' && req.url === '/api/productos') {
    let body = '';
    req.on('data', chunk => { body += chunk; });   // juntar el body de a pedazos
    req.on('end', () => {
      let data;
      try { data = JSON.parse(body); }            // parsear el JSON a mano
      catch {
        res.writeHead(400, { 'Content-Type': 'application/json' });
        return res.end(JSON.stringify({ error: 'JSON inválido' }));
      }
      const { nombre, precio } = data;
      if (!nombre || precio <= 0) {
        res.writeHead(400, { 'Content-Type': 'application/json' });
        return res.end(JSON.stringify({ error: 'Datos inválidos' }));
      }
      const nuevo = { id: productos.length + 1, nombre, precio };
      productos.push(nuevo);
      res.writeHead(201, { 'Content-Type': 'application/json' });
      res.end(JSON.stringify(nuevo));
    });
    return;
  }

  // cualquier otra ruta: 404 a mano
  res.writeHead(404, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ error: 'No encontrado' }));
});

server.listen(3000);

Funciona idéntico a la versión con Express. Pero mirá todo lo que hay que hacer a mano: rutear comparando method y url con if, juntar el body chunk por chunk escuchando eventos, parsear el JSON con su propio try/catch, escribir Content-Type y status en cada respuesta, y devolver el 404 vos mismo. Y eso con un solo recurso: con diez, esa cadena de if se vuelve inmanejable.

Express: la misma API, sin la plomería

app.js — con Express (la que diseccionamos en el bloque 2)
import express from 'express';
const app = express();
app.use(express.json());

const productos = [{ id: 1, nombre: 'Teclado', precio: 25000 }];

app.get('/api/productos', (req, res) => {
  res.json(productos);
});

app.post('/api/productos', (req, res) => {
  const { nombre, precio } = req.body;
  if (!nombre || precio <= 0) {
    return res.status(400).json({ error: 'Datos inválidos' });
  }
  const nuevo = { id: productos.length + 1, nombre, precio };
  productos.push(nuevo);
  res.status(201).json(nuevo);
});

app.listen(3000);

Menos de la mitad de líneas, y casi todas dicen qué hace la API en vez de cómo hablar HTTP. La clave conceptual: Express no agrega poder que Node no tenga — por debajo sigue usando el mismo módulo http. Lo que aporta es una capa fina que se lleva puesta la plomería repetitiva (ruteo, parseo del body, headers, 404) para que el código que escribís sea la lógica de la API.

Cómo se instala

Express es un paquete de npm. En una carpeta vacía:

terminal
# inicializa package.json
npm init -y

# dependencia de producción
npm install express

# cómodo en desarrollo: reinicia el server al guardar
npm install --save-dev nodemon

Dos ajustes en package.json conviene dejar hechos: "type": "module" para usar import (la sintaxis ESM de la unidad de JavaScript) en lugar de require, y un script para arrancar con nodemon.

package.json (fragmento)
{
  "type": "module",
  "scripts": {
    "dev": "nodemon app.js",
    "start": "node app.js"
  }
}

Con eso, npm run dev levanta la API en http://localhost:3000 y la reinicia sola con cada cambio. (Express 5 es la versión estable actual; npm install express ya la trae.)

Bloque 2

El problema: todo en un archivo

Una API REST mínima en Express entra cómoda en un solo archivo. Y funciona perfecto:

app.js — la API completa
import express from 'express';
const app = express();
app.use(express.json());

const productos = [{ id: 1, nombre: 'Teclado', precio: 25000 }];

app.get('/api/productos', (req, res) => {
  res.json(productos);
});

app.post('/api/productos', (req, res) => {
  const { nombre, precio } = req.body;
  if (!nombre || precio <= 0) {                        // validación
    return res.status(400).json({ error: 'Datos inválidos' });
  }
  const nuevo = { id: productos.length + 1, nombre, precio }; // lógica de negocio
  productos.push(nuevo);                               // acceso a datos
  res.status(201).json(nuevo);                        // respuesta HTTP
});

app.listen(3000);

Mirá el handler del POST: en diez líneas conviven cuatro responsabilidades distintas — hablar HTTP, validar, aplicar reglas de negocio y guardar datos. Con dos endpoints no molesta. El problema aparece cuando el proyecto crece:

  • Más recursos → un archivo de 2000 líneas donde nadie encuentra nada.
  • Cambiar el array por una base de datos → hay que tocar todos los handlers, uno por uno.
  • Testear la lógica de negocio → imposible sin levantar el servidor y hacer requests HTTP.
  • Trabajar en equipo → todos editan el mismo archivo; conflictos de merge constantes.
Importante
La arquitectura no se nota cuando el código funciona: se nota cuando hay que cambiarlo. El mismo programa corre igual con cualquier estructura; lo que cambia la estructura es cuánto cuesta modificarlo, testearlo y entenderlo dentro de tres meses.
Bloque 3

Arquitectura en capas: el patrón base

La respuesta clásica es separar por responsabilidad técnica: cada pieza del handler anterior pasa a vivir en su propia capa, y cada capa solo habla con la de al lado.

Routes
Mapean método + URL a un controller: GET /productos → listar. No tienen lógica: son la tabla de contenidos de la API.
Controllers
Hablan HTTP y nada más: leen req, llaman al service y arman la respuesta (status + JSON). No saben cómo se guardan los datos.
Services
La lógica de negocio: reglas, validaciones de dominio, coordinación. No conocen Express ni la base de datos — reciben y devuelven datos puros.
Repositories
El único lugar que sabe dónde y cómo viven los datos: un array, un archivo, MongoDB, MySQL. Exponen operaciones: buscar, guardar, eliminar.
+ Middleware (transversal)
Las preocupaciones que cruzan todos los recursos — autenticación, validación de entrada, manejo de errores, logging — no viven en una capa: se enchufan entre el request y el controller, o al final de la cadena.

El recorrido de un request queda así:

  1. Llega POST /api/productos. Express lo recibe.
  2. Pasa por los middlewares globales: express.json(), logging, autenticación si corresponde.
  3. La route matchea método y URL, y delega en el controller.
  4. El controller extrae los datos del req y llama al service.
  5. El service aplica las reglas de negocio y usa el repository.
  6. El repository lee o escribe los datos. La respuesta vuelve por el mismo camino: service → controller → res.json().

El mismo endpoint, separado

El POST del bloque 2, repartido en cuatro archivos. Notá que cada archivo importa solo la capa que tiene debajo — los módulos ESM que vimos en la unidad de JavaScript son el mecanismo que hace posible esta separación:

productos.routes.js
import { Router } from 'express';
import { listar, crear } from './productos.controller.js';

export const productosRouter = Router();
productosRouter.get('/', listar);
productosRouter.post('/', crear);
productos.controller.js
import * as service from './productos.service.js';

export async function crear(req, res, next) {
  try {
    const producto = await service.crearProducto(req.body);
    res.status(201).json(producto);
  } catch (err) {
    next(err);  // lo captura el middleware de errores
  }
}
productos.service.js
import * as repo from './productos.repository.js';

export async function crearProducto(datos) {
  if (!datos.nombre || datos.precio <= 0) {
    throw new Error('Datos inválidos');
  }
  return repo.guardar(datos);
}
productos.repository.js
const productos = [];

export async function guardar(datos) {
  const nuevo = { id: productos.length + 1, ...datos };
  productos.push(nuevo);
  return nuevo;
}

¿Por qué el service y el repository son async si hoy usan un array en memoria? Porque mañana el repository habla con una base de datos — una operación asincrónica, como vimos en la clase de asincronía — y si la firma ya devuelve una promesa, nada más cambia. Ese es el pago de la separación:

  • Cambiar el array por MongoDB toca un solo archivo: el repository.
  • La lógica de negocio se testea llamando a crearProducto() directo, sin levantar el servidor.
  • Autenticación, validación y errores se resuelven una vez como middleware, no en cada handler.

¿Y esto no era "MVC"?

Casi. MVC (Modelo–Vista–Controlador) nace para aplicaciones con interfaz gráfica; en una API no hay "vista" — o si se quiere, la vista es el JSON que se devuelve. Cuando un tutorial de Express dice "estructura MVC", en la práctica describe esto mismo: routes + controllers + models. La arquitectura en capas es la adaptación de esa idea a APIs, con el agregado explícito de services y repositories.

Bloque 4

¿Por rol técnico o por feature?

Definidas las capas, queda una segunda decisión, independiente de la primera: cómo agrupar los archivos en carpetas. Hay dos criterios, y los dos usan exactamente las mismas capas:

Por capas (rol técnico)
src/
├─ routes/
│  ├─ productos.routes.js
│  └─ usuarios.routes.js
├─ controllers/
│  ├─ productos.controller.js
│  └─ usuarios.controller.js
├─ services/
│  └─ ...
├─ repositories/
│  └─ ...
└─ app.js
Por feature (recurso)
src/
├─ productos/
│  ├─ productos.routes.js
│  ├─ productos.controller.js
│  ├─ productos.service.js
│  └─ productos.repository.js
├─ usuarios/
│  └─ ...
├─ shared/   ← middleware, errores, db
└─ app.js

Por capas es la forma más intuitiva al empezar: cuatro carpetas, cada una con un tipo de archivo. Funciona bien con dos o tres recursos. El costo aparece al crecer: para tocar "productos" hay que saltar entre cuatro carpetas, y cada recurso nuevo agrega un archivo en cada una.

Por feature invierte el criterio: todo lo que hace a un recurso vive junto. Alta cohesión — lo que cambia junto, está junto —, cada integrante del equipo puede trabajar en su carpeta sin pisarse, y un feature completo se puede extraer o eliminar borrando una carpeta. Es la organización que recomiendan las guías de buenas prácticas de Node.js para proyectos reales, y la que mejor escala con el tamaño del equipo y de la API.

Importante
Regla práctica: con pocos recursos, cualquiera de las dos sirve — elegí una y sé consistente. Con muchos recursos o varios integrantes, por feature. Y en ambas, lo transversal (middleware, manejo de errores, conexión a la base) va a una carpeta shared/ o common/.
Bloque 5

Arquitecturas con nombre: Hexagonal, Clean, Onion

En algún momento van a cruzarse con estos nombres: Hexagonal (o Ports & Adapters, Cockburn, 2005), Onion (Palermo, 2008) y Clean Architecture (Martin, 2012). Difieren en detalles y vocabulario, pero son variantes de una misma idea, que se puede resumir en una regla:

Adaptadores
Lo concreto y reemplazable: Express, MongoDB, la consola, un test
Puertos
Interfaces que el dominio define: "necesito algo que guarde productos"
Dominio
Entidades y reglas de negocio — no conoce nada de lo de afuera
Las dependencias apuntan hacia adentro: afuera puede cambiar, el centro no se entera.

La regla: la lógica de negocio en el centro, sin depender de frameworks ni de la base de datos. El mundo exterior se conecta mediante puertos (interfaces que el dominio define) y adaptadores (implementaciones concretas: un controller de Express es un adaptador de entrada; un repository de MongoDB, uno de salida).

Y acá la buena noticia: con las capas del bloque 3 ya hicieron una versión light de esto. El service no conoce Express (el controller lo adapta) y no sabe cómo se guardan los datos (el repository lo esconde). Hexagonal y Clean formalizan esa intuición con interfaces explícitas e inversión de dependencias: el dominio declara qué necesita, y la infraestructura lo implementa.

El trade-off: a cambio de máxima testabilidad e independencia tecnológica, pagás más archivos, más interfaces y más abstracción. Para una API chica suele ser sobre-ingeniería; en sistemas grandes, de larga vida o con dominio complejo, es donde brilla. Lo importante hoy es que reconozcan la idea cuando la vean — no que la implementen completa.

Dato
NestJS es un framework sobre Node que trae gran parte de estas decisiones ya tomadas: módulos por feature, controllers y services separados, e inyección de dependencias de fábrica. Es la opción "arquitectura incluida" — muy común en la industria — y van a entenderla mejor por haber visto de dónde salen sus piezas.
Bloque 6

Monolito, monolito modular, microservicios

Ojo con el cambio de eje: hasta acá hablamos de cómo ordenar el código adentro de una aplicación. "Monolito vs microservicios" responde otra pregunta: ¿cuántas aplicaciones desplegables tenés?

OpciónQué esTrade-off
Monolito Una sola API, una base de datos, un deploy. Todo lo visto hoy aplica adentro. Simple de desarrollar, testear y desplegar. Escala hasta mucho más lejos de lo que se suele creer.
Monolito modular Un solo deploy, pero módulos internos con límites estrictos — organización por feature llevada a rajatabla. Casi toda la ganancia de los microservicios sin el costo operacional. La antesala natural.
Microservicios Cada dominio es un servicio independiente, con su propia base de datos y su propio deploy, comunicados por red. Resuelve escala de equipos y de tráfico. A cambio: fallas de red, consistencia distribuida, observabilidad, mucho DevOps.
Cuidado
Microservicios no es "la versión mejor": es un trade-off pensado para problemas de escala que un TP — y muchísimas empresas — no tienen. La recomendación clásica de la industria es monolith first: empezar monolítico y bien modular, y partir en servicios solo cuando los límites del dominio ya se conocen y el dolor es real.
Bloque 7

¿Cómo elegir? Criterios y cierre

El mapa completo, en una tabla:

EstructuraCuándo convieneCosto
Un archivo Demos, pruebas de concepto, scripts de una tarde. Se vuelve inmantenible apenas crece.
Capas (por rol) Proyectos chicos, pocos recursos, un solo desarrollador. Las carpetas crecen en paralelo; mucho salto entre carpetas.
Capas por feature La mayoría de las APIs reales; equipos de varias personas. Requiere disciplina para respetar los límites entre features.
Hexagonal / Clean Dominios complejos, sistemas de larga vida, mucho testing. Más abstracción, más interfaces, más archivos.
Microservicios Escala grande de equipos y de tráfico, dominios ya maduros. Complejidad operacional alta; no arranca nadie por acá.

Dos ideas cierran el criterio de elección. Primero: la arquitectura se elige por el problema y el equipo, no por prestigio — una estructura simple aplicada con consistencia le gana siempre a una sofisticada aplicada a medias. Segundo: las opciones no compiten en un ranking; son respuestas a preguntas distintas — cómo separar responsabilidades (capas), cómo agrupar archivos (rol vs feature), cuánto desacoplar del framework (hexagonal), cuántas unidades desplegar (monolito vs micro).

Idea central
No existe la arquitectura correcta. Existe separar responsabilidades y que las dependencias apunten en una sola dirección. Test rápido: si tu lógica de negocio no importa nada de Express ni sabe qué base de datos hay debajo, elegiste bien — se llame como se llame la arquitectura.
Lo que sigue
Todo esto se materializa en el TP de la materia: la API REST que van a construir necesita una de estas estructuras, y la evaluación mira precisamente la separación de responsabilidades — capas, middleware, validación, manejo de errores. Esta guía es el mapa para decidir y defender esa estructura.
Autoevaluación

Ponete a prueba

Respondé cada pregunta mentalmente y después tocá para revelar la respuesta y verificar.

1. Express usa el módulo http de Node por debajo. Entonces, ¿qué le agrega a Node que http por sí solo no podía hacer?
En cuanto a capacidad, nada: la potencia es la misma porque Express corre sobre el mismo http. Lo que aporta no es poder nuevo sino sacarte la plomería repetitiva — ruteo, parseo del body, headers, 404 — para que escribas la lógica de la API y no el andamiaje HTTP. Un framework da convenciones y código hecho, no capacidades que el lenguaje no tenga.
2. Con el módulo http nativo, nombrá tres cosas que tenés que hacer a mano y que Express te resuelve.
Cualquiera de estas: rutear comparando method + url con if (Express: app.get('/ruta', ...)); juntar el body chunk por chunk y hacer JSON.parse con try/catch (Express: express.json() y req.body); escribir Content-Type, status y JSON.stringify en cada respuesta (Express: res.status(201).json(...)); devolver el 404 uno mismo (Express lo hace por defecto).
3. ¿Qué comando instala Express y qué hay que dejar configurado en package.json para poder usar import en lugar de require?
npm install express (después de npm init -y). Para usar la sintaxis ESM (import) hay que agregar "type": "module" en el package.json. Suele sumarse también nodemon como dependencia de desarrollo (npm install --save-dev nodemon) para reiniciar el servidor al guardar.
4. ¿Por qué “el código funciona” no alcanza como criterio para decidir la estructura de un proyecto?
Porque el programa corre igual con cualquier estructura. La arquitectura define lo demás: cuánto cuesta cambiarlo, si la lógica se puede testear sin levantar el servidor, y si varias personas pueden trabajar en paralelo sin pisarse. La arquitectura se nota al modificar el código, no al ejecutarlo.
5. Nombrá las cuatro capas típicas de una API y la responsabilidad de cada una, en una línea por capa.
Routes: mapean método + URL a un controller, sin lógica. Controllers: hablan HTTP — leen req, llaman al service, arman la respuesta. Services: la lógica de negocio pura, sin conocer Express ni la base de datos. Repositories: el único acceso a la fuente de datos (array, archivo, MongoDB, MySQL).
6. ¿Qué capas son las únicas que deberían conocer Express? ¿Y la única que sabe cómo se guardan los datos?
Express vive en el borde HTTP: routes, controllers y middleware. El service no debería importar nada de Express. Y de los datos sabe únicamente el repository: si otra capa arma una consulta a la base, la separación se rompió.
7. Mañana reemplazás el array en memoria por MongoDB. En una arquitectura en capas bien hecha, ¿qué archivos tocás?
Solo el repository (más la configuración de conexión). Controller y service no cambian una línea — y por eso sus funciones ya eran async: la firma con promesa estaba lista de antemano para una fuente de datos real.
8. ¿Qué diferencia hay entre organizar “por capas” y “por feature”? ¿Desaparecen las capas al organizar por feature?
No desaparecen: son las mismas cuatro capas; lo que cambia es el criterio para agrupar los archivos en carpetas. Por rol técnico, todos los controllers viven juntos en controllers/; por feature, todo lo de un recurso (sus routes, controller, service y repository) vive junto en productos/. Por feature escala mejor con el tamaño del proyecto y del equipo.
9. ¿Qué es un middleware y por qué se dice que es “transversal” a las capas?
Es una función que se ejecuta en la cadena del request — antes del controller, o al final para los errores. Es transversal porque resuelve preocupaciones que cruzan todos los recursos — autenticación, validación de entrada, logging, manejo de errores — una sola vez, en lugar de repetirlas en cada handler.
10. ¿Qué regla comparten Hexagonal, Clean y Onion?
Que las dependencias apuntan hacia adentro: el dominio (la lógica de negocio) está en el centro y no conoce frameworks ni base de datos; el mundo exterior se conecta mediante puertos (interfaces que el dominio define) y adaptadores (implementaciones concretas, como un controller de Express o un repository de MongoDB).
11. ¿Qué pregunta responde “monolito vs microservicios” que no responde “capas vs hexagonal”?
Cuántas unidades desplegables tiene el sistema: una sola aplicación o muchos servicios independientes comunicados por red. Capas y hexagonal, en cambio, ordenan el código adentro de una aplicación. Y la respuesta por defecto es: monolito, bien modular — monolith first.
12. Un compañero pone la consulta a la base directamente en el controller “porque es más corto”. Dale dos razones concretas para moverla al repository.
Cualquiera de estas: (1) si otro endpoint necesita la misma consulta, se duplica; (2) cambiar de base de datos obliga a tocar todos los controllers en vez de un archivo; (3) la lógica queda imposible de testear sin levantar HTTP y base de datos reales. Con dos alcanza — las tres valen.
Cierre

Resumen

  • Todo en un archivo funciona, pero mezcla HTTP, validación, negocio y datos: el costo aparece al cambiar, testear y trabajar en equipo.
  • Capas — routes, controllers, services, repositories — separan por responsabilidad técnica; el middleware resuelve lo transversal (auth, validación, errores) una sola vez.
  • La regla que ordena todo: las dependencias apuntan en una dirección — el service no conoce Express; el repository es el único que sabe dónde viven los datos.
  • Por rol o por feature es cómo agrupar esos archivos: por feature escala mejor con el tamaño del proyecto y del equipo.
  • Hexagonal, Clean y Onion formalizan la misma dirección de dependencias con puertos y adaptadores: dominio en el centro, frameworks en el borde.
  • Monolito vs microservicios es otra pregunta — cuántas unidades desplegables —, y la respuesta por defecto es: monolito, bien modular.
  • Criterio final: consistencia sobre sofisticación — la mejor arquitectura es la más simple que tu proyecto y tu equipo puedan sostener.
