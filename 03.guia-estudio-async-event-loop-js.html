Bloque 1

El problema: sincronía vs asincronía

JavaScript es single-threaded: ejecuta una sola cosa a la vez, en un único hilo. Esto plantea un problema cuando una operación tarda — pedir datos a un servidor, leer un archivo, un temporizador. Si esa operación bloqueara el hilo, toda la aplicación se congelaría hasta que termine.

La asincronía resuelve esto: permite arrancar una operación lenta y seguir ejecutando el resto del código. Cuando la operación termina, recibimos el resultado.

El ejemplo más simple: setTimeout

console.log('1');

setTimeout(() => console.log('2 (después de 2s)'), 2000);

console.log('3');
Salida
1
3
2 (después de 2s)

El punto clave: '3' se imprime antes que '2', aunque en el código esté después. El setTimeout no detiene la ejecución — programa el callback para más tarde y JS sigue de largo.

Importante
El tiempo de setTimeout es un mínimo, no un valor exacto. JS primero termina de ejecutar todo el código sincrónico y recién después atiende los callbacks pendientes. setTimeout(fn, 0) no ejecuta fn "ya", sino "apenas se libere el hilo".
Más adelante en esta guía
¿Quién decide exactamente en qué orden se ejecuta cada cosa? Un mecanismo llamado event loop. Primero vamos a aprender a escribir código asincrónico (callbacks, promesas, async/await) y en la segunda parte de esta guía abrimos el capó para ver cómo funciona por dentro.
Bloque 2

Callbacks

Un callback es una función que se pasa como argumento a otra para ejecutarse más tarde. Ya lo vimos en la clase de funciones. En el contexto asincrónico, el callback es la función que se ejecuta cuando la operación lenta termina.

El patrón básico

function pedirDatos(callback) {
  setTimeout(() => {
    const datos = { id: 1, nombre: 'Ada' };
    callback(datos); // avisamos cuando "llegaron" los datos
  }, 1000);
}

pedirDatos((datos) => {
  console.log('Llegaron:', datos);
});

Convención error-first (Node.js)

En Node.js se popularizó una convención: el primer parámetro del callback es el error (o null si todo salió bien), y el segundo son los datos.

pedirDatos((error, datos) => {
  if (error) {
    console.error('Algo falló:', error);
    return;
  }
  console.log('Llegaron:', datos);
});

El problema: callback hell

Cuando una operación depende del resultado de otra, y esa de otra, los callbacks se anidan. Se forma la llamada pirámide de la perdición (pyramid of doom):

getUser(1, (user) => {
  getPosts(user, (posts) => {
    getComments(posts[0], (comments) => {
      console.log(comments);
      // ...y seguimos anidando hacia la derecha
    });
  });
});
Por qué es un problema
El código se desplaza hacia la derecha, se vuelve difícil de leer y de seguir. Pero el problema más serio es el manejo de errores: hay que controlarlo en cada nivel por separado, lo que es repetitivo y fácil de olvidar. Esto fue exactamente lo que motivó la creación de las Promesas.
Bloque 3

Promesas

Una Promise (promesa) es un objeto que representa el resultado futuro de una operación asincrónica. En vez de pasarle un callback a la operación, la operación nos devuelve una promesa, y nosotros le "enganchamos" qué hacer cuando se resuelva.

Los tres estados de una promesa

pending
Estado inicial. La operación todavía no terminó.
resolve() →
fulfilled
Se cumplió. Hay un valor. Lo recibe .then()
reject()  →
rejected
Falló. Hay un error. Lo recibe .catch()

Una vez que una promesa pasa de pending a fulfilled o rejected (se dice que está settled, asentada), su estado ya no cambia más.

Crear una promesa

const promesa = new Promise((resolve, reject) => {
  setTimeout(() => {
    const exito = true;
    if (exito) {
      resolve({ id: 1, nombre: 'Ada' }); // → fulfilled
    } else {
      reject(new Error('No se pudo'));  // → rejected
    }
  }, 1000);
});

La función que recibe el constructor (el executor) recibe a su vez dos funciones: resolve (para cumplir la promesa) y reject (para rechazarla).

Consumir una promesa

promesa
  .then((datos) => console.log('OK:', datos))      // si se cumple
  .catch((error) => console.error('Error:', error)) // si falla
  .finally(() => console.log('Terminé igual'));   // pase lo que pase

Encadenar promesas (chaining)

Acá está la clave que resuelve el callback hell. Cada .then() devuelve una nueva promesa, así que se pueden encadenar en plano, sin anidar:

getUser(1)
  .then((user) => getPosts(user))
  .then((posts) => getComments(posts[0]))
  .then((comments) => console.log(comments))
  .catch((error) => console.error(error)); // UN solo catch para toda la cadena
Comparar con los callbacks
Es la misma lógica que la pirámide de antes (usuario → posts → comentarios), pero plana y legible, y con un único punto de manejo de errores: si cualquier paso de la cadena falla, salta directo al .catch().

Métodos estáticos útiles — para profundizar

Cuando se trabaja con varias promesas a la vez:

MétodoQué hace
Promise.all([...])Espera a que todas se cumplan; devuelve un array con los resultados. Si una falla, rechaza de inmediato.
Promise.allSettled([...])Espera a todas, nunca rechaza. Devuelve el resultado de cada una con su status.
Promise.race([...])Se asienta con la primera que termine (se cumpla o falle).
Promise.any([...])Se cumple con la primera que se cumpla; rechaza solo si fallan todas.
Bloque 4

async / await

async/await es azúcar sintáctico sobre las promesas: por debajo siguen siendo promesas, pero el código se escribe como si fuera sincrónico, de arriba hacia abajo.

Dos reglas

  • async antes de una función hace que siempre devuelva una promesa.
  • await dentro de una función async pausa la ejecución hasta que la promesa se resuelva, y devuelve su valor.
async function mostrarUsuario() {
  const user = await getUser(1); // espera y guarda el VALOR, no la promesa
  console.log(user);
}
Dónde se puede usar await
Solo dentro de funciones async. (Desde ES2022 también en el nivel superior de un módulo — top-level await.) Usar await en una función normal es un error de sintaxis.

Manejo de errores: try / catch

En vez de .catch(), con async/await se usan try/catch — la misma estructura que ya conocen para errores sincrónicos:

async function mostrar() {
  try {
    const user = await getUser(1);
    const posts = await getPosts(user);
    const comments = await getComments(posts[0]);
    console.log(comments);
  } catch (error) {
    console.error('Algo falló:', error);
  }
}

La misma lógica, tres formas

Este es el mismo problema (usuario → posts → comentarios) resuelto de las tres maneras. La evolución del lenguaje en una imagen:

Callbacks · anidado 
getUser(1, (user) => {
  getPosts(user, (posts) => {
    getComments(posts[0], (comments) => {
      console.log(comments);
    });
  });
});
Promesas · encadenado 
getUser(1)
  .then((user) => getPosts(user))
  .then((posts) => getComments(posts[0]))
  .then((comments) => console.log(comments))
  .catch((error) => console.error(error));
async / await · plano 
async function mostrar() {
  try {
    const user = await getUser(1);
    const posts = await getPosts(user);
    const comments = await getComments(posts[0]);
    console.log(comments);
  } catch (error) {
    console.error(error);
  }
}
Idea central
Las tres hacen lo mismo. async/await es la forma preferida en código moderno por su legibilidad, pero por debajo son promesas. Entender promesas no es opcional: es la base sobre la que está construido async/await.

async siempre devuelve una promesa

async function dameUno() {
  return 1;
}

dameUno().then((n) => console.log(n)); // 1 — el valor se envuelve en una promesa
Bloque 5

En la práctica

fetch: pedir datos a una API

El uso más común de async/await en la práctica es fetch, para pedir datos a un servidor. fetch devuelve una promesa que se resuelve con un objeto Response.

async function getUsuario() {
  try {
    const response = await fetch('https://api.example.com/users/1');

    if (!response.ok) {
      throw new Error(`Error HTTP: ${response.status}`);
    }

    const datos = await response.json(); // .json() también devuelve promesa
    console.log(datos);
  } catch (error) {
    console.error('Falló el pedido:', error);
  }
}
⚠ Trampa clásica de fetch
fetch solo rechaza ante errores de red (no hay conexión, el servidor no responde). Un código de error HTTP como 404 o 500 NO hace que la promesa falle — la promesa se cumple igual. Por eso hay que chequear response.ok a mano y lanzar el error nosotros.

Errores comunes

1. Olvidarse el await

const user = getUser(1);        // ❌ user es una Promise, no el valor
const user = await getUser(1);  // ✅ user es el valor

2. Secuencial cuando podría ser paralelo

// ❌ Secuencial — lento: espera a getUser y RECIÉN ahí arranca getProduct
const user = await getUser(1);
const product = await getProduct(2);

// ✅ Paralelo — las dos arrancan juntas, esperamos a ambas
const [user, product] = await Promise.all([
  getUser(1),
  getProduct(2),
]);

Usar Promise.all cuando las operaciones son independientes entre sí.

3. forEach no respeta await

// ❌ forEach ignora el await — 'listo' se imprime ANTES de terminar
ids.forEach(async (id) => {
  await procesar(id);
});
console.log('listo');

// ✅ for...of espera correctamente cada iteración
for (const id of ids) {
  await procesar(id);
}
console.log('listo'); // ahora sí: después de procesar todos
Conecta con la clase de sintaxis
Como vimos en la tabla for vs forEach, forEach no funciona bien con async/await. Para iteración secuencial asincrónica, usar for...of. Para procesar todo en paralelo, map + Promise.all.
Bloque 6

El event loop: las piezas del mecanismo

Hasta acá aprendimos a escribir código asincrónico. Queda la pregunta de fondo: si JS ejecuta una sola cosa a la vez, ¿quién coordina qué se ejecuta y cuándo? Ese coordinador es el event loop.

La idea central ya la vimos en el Bloque 1: cuando aparece una tarea que lleva tiempo, JS no se queda esperando — se la delega al entorno (el navegador o Node), sigue ejecutando lo que viene, y cuando la tarea termina, su callback entra en una cola para ejecutarse apenas el hilo quede libre. Para entender el mecanismo completo hay que conocer cuatro piezas:

Call Stack
La pila donde JS ejecuta el código sincrónico, función por función. Si una función llama a otra, se apila; cuando termina, se desapila.
Web APIs / Entorno
El navegador o Node manejan setTimeout, fetch y los eventos. JS les delega la tarea y sigue ejecutando sin esperar.
Microtask Queue
Cola de promesas (.then, .catch, async/await) y queueMicrotask. Tiene prioridad alta.
Macrotask Queue
Cola de setTimeout, setInterval, eventos de I/O y del DOM. Tiene prioridad menor que la de microtasks.

El event loop en sí es un bucle que pregunta constantemente: "¿está vacío el call stack? Si lo está, ¿hay algo esperando en las colas para ejecutarse?". La clave está en que las dos colas no tienen la misma prioridad.

function saludar() {
  console.log("Hola");
}
saludar(); // se apila, se ejecuta, se desapila
Bloque 7

El orden de prioridad

En cada vuelta, el event loop sigue siempre el mismo orden:

  1. Ejecuta todo el código sincrónico (vacía el call stack).
  2. Vacía por completo la cola de microtasks.
  3. Ejecuta una sola macrotask de la cola.
  4. Vuelve a vaciar toda la cola de microtasks.
  5. Repite desde el paso 3.
La regla en una frase
Entre cada macrotask, el event loop vacía toda la cola de microtasks. Por eso las promesas siempre se ejecutan antes que el próximo setTimeout.

El ejemplo clásico

Este es el ejemplo que conviene tener grabado. Tratá de predecir la salida antes de leer la explicación:

console.log("1");

setTimeout(() => {
  console.log("2");
}, 0);

Promise.resolve().then(() => {
  console.log("3");
});

console.log("4");
Salida
1
4
3
2

¿Por qué ese orden?

  • 1 y 4 son sincrónicos → se ejecutan de inmediato.
  • 3 es una promesa (microtask) → se ejecuta antes que cualquier macrotask, aunque el setTimeout tenga 0 ms.
  • 2 es una macrotask (setTimeout) → espera a que se vacíe primero toda la cola de microtasks.
Bloque 8

Macrotasks en concreto

Estos son los casos más comunes que generan macrotasks.

setTimeout

Agrega una tarea a la cola de macrotasks cuando se cumple el tiempo (o apenas el call stack queda libre, si es 0).

setTimeout(() => {
  console.log("Corre en el próximo ciclo del event loop");
}, 1000);

setInterval

Igual que setTimeout, pero encola una macrotask nueva cada vez que se cumple el intervalo, hasta que lo cancelás con clearInterval.

let contador = 0;

const id = setInterval(() => {
  contador++;
  console.log("Tick", contador);
  if (contador === 5) clearInterval(id);
}, 1000);

Eventos de I/O (en Node.js)

Operaciones de archivos, red, etc. El callback se encola como macrotask recién cuando el sistema operativo termina la operación en segundo plano.

const fs = require('fs');

fs.readFile('archivo.txt', 'utf8', (err, data) => {
  console.log("Archivo leído:", data);
});

console.log("Esto se ejecuta primero");
Salida
Esto se ejecuta primero
Archivo leído: [contenido del archivo]

Eventos del DOM (en el navegador)

Clics, scroll, teclas. Cada vez que el usuario interactúa, el navegador encola el handler como macrotask: no corre "en el instante exacto" del clic, sino que espera su turno como cualquier otra tarea.

document.getElementById("miBoton")
  .addEventListener("click", () => {
    console.log("Botón clickeado");
  });
Entre macrotasks no hay jerarquía fija
El orden entre distintas macrotasks (un evento del DOM vs un setTimeout vs I/O) depende de cuál entró primero a la cola, no de su tipo. La jerarquía clara es solo microtasks sobre macrotasks: las promesas siempre van primero.

Entender este mecanismo explica comportamientos que de otra forma parecen mágicos: por qué un .then() corre antes que un setTimeout(…, 0) escrito más arriba, por qué setTimeout(fn, 0) nunca significa "ya", o por qué cierto código que depende del orden de ejecución funciona (o falla) como funciona.

Autoevaluación

Ponete a prueba

Respondé cada pregunta mentalmente y después tocá para revelar la respuesta y verificar. Las primeras siete son de la parte de asincronía; las últimas cinco, del event loop.

1. Si JS es de un solo hilo, ¿por qué necesita asincronía?
Justamente porque es single-threaded: si una operación lenta (red, archivo, timer) bloqueara el único hilo, se congelaría toda la app. La asincronía permite arrancar la operación y seguir ejecutando, recibiendo el resultado cuando esté listo.
2. ¿Qué imprime? console.log(1); setTimeout(() => console.log(2), 0); console.log(3);
Imprime 1, 3, 2. El setTimeout no detiene la ejecución: encola el callback (una macrotask) para cuando el hilo quede libre, así que 3 sale antes que 2 aunque tenga 0 ms.
3. ¿Cuáles son los tres estados de una promesa?
pending (todavía no terminó), fulfilled (se cumplió, hay un valor) y rejected (falló, hay un error). Una vez que pasa a fulfilled o rejected, no cambia más.
4. ¿Qué hace await y dónde se puede usar?
Pausa la función hasta que la promesa se resuelva y devuelve su valor. Solo se puede usar dentro de una función async (o en el nivel superior de un módulo).
5. ¿Por qué fetch no falla ante un error 404 o 500? ¿Qué hay que hacer?
fetch solo rechaza ante errores de red. Un 404/500 se considera una respuesta válida, así que la promesa se cumple igual. Hay que chequear response.ok y lanzar el error a mano.
6. Tengo dos operaciones independientes: ¿conviene await una y después la otra, o usar Promise.all?
Si son independientes, Promise.all: arrancan en paralelo y esperás a ambas, más rápido. Encadenar await las hace secuenciales (una espera a la otra sin necesidad).
7. ¿Por qué un forEach con async adentro no espera a que terminen las operaciones?
Porque forEach ignora la promesa que devuelve el callback y no la espera. Para iteración secuencial con await se usa for...of; para paralelo, map + Promise.all.
8. ¿Qué es el call stack?
Es la pila donde JS ejecuta el código sincrónico, función por función. Cuando una función llama a otra, se apila; cuando termina, se desapila.
9. Cuando llamás a setTimeout o fetch, ¿lo maneja el motor de JS o el entorno?
El entorno (navegador o Node), a través de las Web APIs. JS le delega la tarea y sigue ejecutando sin esperar; el callback vuelve a una cola cuando la operación termina.
10. Entre microtasks y macrotasks, ¿cuál tiene prioridad?
Las microtasks (promesas). El event loop vacía por completo la cola de microtasks antes de tomar una sola macrotask (como un setTimeout).
11. ¿Qué imprime y por qué? console.log('1'); setTimeout(() => console.log('2'), 0); Promise.resolve().then(() => console.log('3')); console.log('4');
Imprime 1, 4, 3, 2. Primero lo sincrónico (1 y 4). Después se vacía la cola de microtasks: la promesa (3). Por último, la macrotask del setTimeout (2), aunque tenga 0 ms.
12. ¿Las promesas son micro o macrotasks? ¿Y setTimeout?
Las promesas (.then/.catch, async/await) son microtasks. setTimeout, setInterval, I/O y eventos del DOM son macrotasks.
Cierre

Resumen

Puntos clave para recordar

  • JS es single-threaded; la asincronía evita bloquear el único hilo.
  • Callbacks: función que se ejecuta al terminar la operación. Problema: anidamiento (callback hell) y errores difíciles de manejar.
  • Promesas: objeto con tres estados — pending → fulfilled / rejected. Se consumen con .then(), .catch(), .finally(). Se encadenan en plano.
  • async/await: azúcar sintáctico sobre promesas. Código sincrónico-looking, errores con try/catch.
  • fetch no rechaza ante 404/500 — chequear response.ok. forEach no respeta await — usar for...of. Operaciones independientes → Promise.all.
  • El event loop coordina todo: el call stack ejecuta lo sincrónico, las Web APIs del entorno manejan lo que lleva tiempo, y los callbacks vuelven por dos colas.
  • Orden en cada vuelta: código sincrónico → vaciar todas las microtasks → una macrotask → vaciar microtasks de nuevo → repetir.
  • Las microtasks (promesas) tienen prioridad sobre las macrotasks (setTimeout, I/O, eventos del DOM). Entre macrotasks, manda el orden de llegada.
  • setTimeout(fn, 0) no ejecuta fn "ya": la encola para cuando el hilo quede libre y no haya microtasks pendientes.
Lo que sigue
A lo largo de esta guía usamos promesas como objetos y llamamos a sus métodos (.then, .catch, .finally). La guía de Objetos en JavaScript da el marco completo para entender qué es un objeto, qué es un método, y cómo funciona todo esto por dentro — incluyendo las propias promesas.
