Autenticación y autorización

Quién sos, y qué podés hacer — Material de estudio

Prerequisito: la API con MikroORM y MySQL (unidad 8), middlewares de Express (unidad 6) y TypeScript (unidad 7)
Introducción

Contenidos de la guía

La API que venimos construyendo desde la unidad 6 tiene un agujero del tamaño de un colectivo: cualquiera puede hacer cualquier cosa. No hay usuarios, no hay dueños y no hay puertas. En esta unidad se las ponemos.

El tema tiene una trampa: se puede aprender entero como una receta —instalar bcrypt, instalar jsonwebtoken, copiar el middleware— sin entender nada. Esta guía está armada al revés: cada pieza aparece como respuesta a un problema que se plantea antes. Si al terminar sabés por qué el payload de un JWT no puede tener datos privados, la leíste bien aunque no te acuerdes de la firma de jwt.sign().

Bloque 1

La API está abierta

Abrí el .http del ejemplo 8.2 y borrá un producto. Sin credenciales, sin nada. Ahora la pregunta: ¿quién borró ese producto?

No hay respuesta posible. La API no tiene idea de quién le está hablando, y no la va a tener nunca mientras no se lo pidas.

Eso son dos problemas distintos, y conviene separarlos desde el principio porque después todo el tema se ordena solo:

Autenticación
¿Quién sos?
Probar la identidad. Una sola pregunta, una sola respuesta posible. Falla con 401.
Autorización
¿Podés hacer esto?
Decidir permisos. Una pregunta distinta por cada regla del sistema. Falla con 403.

La analogía que funciona: entrar a un edificio. En la puerta te piden el documento y comparan la cara — eso es autenticarse, y pasa una sola vez. Adentro, tu tarjeta abre algunos pisos y otros no: eso es autorización, y se evalúa en cada puerta.

401 Unauthorized403 Forbidden
Qué significaNo sé quién sosSé quién sos, y no podés
Por qué pasaFalta el token, venció, la firma no cierraSos usuario común y esto es de admin
Qué hace el clienteIr a loguearseNada. Loguearse de nuevo no cambia nada
Cuidado
El nombre del 401 en el estándar HTTP es Unauthorized, y significa no autenticado. El de autorización es el 403. El nombre quedó mal desde 1997 y ya no se cambia. Anotalo una vez y listo: lo vas a leer mil veces en la documentación y te va a chocar cada vez.
Bloque 2

Variables de entorno: sacar los secretos del código

Este bloque va antes que todo lo demás por una razón práctica: en unas pocas páginas vas a generar un secret, y no tiene que terminar escrito en un archivo .ts. Además cierra una deuda que la unidad 8 dejó abierta a propósito.

8.2 — mikro-orm.config.ts, tal cual quedó
  dbName: 'dsw_persistencia',
  host: 'localhost',
  user: 'root',
  password: 'root',   // ← esto está mal, y lo sabíamos

Tres razones para sacarlo del código, en orden de gravedad:

  1. Secretos. Un secret en un repo público es publicar la llave de tu casa. Y borrarlo en el commit siguiente no alcanza: queda en el historial de git para siempre.
  2. Ambientes. El mismo código tiene que correr contra tu MySQL local y contra la base de producción. Lo único que cambia es la configuración.
  3. Equipo. Cada uno tiene su MySQL con su contraseña. Sin .env, esa línea se cambia en cada pull y se commitea sin querer una vez por semana.

Cómo se ve

.env — NO se versiona
DB_PASSWORD=miClaveReal123
JWT_SECRET=8f3a1c9e4b7d...
.env.example — SÍ se versiona
DB_PASSWORD=root
JWT_SECRET=cambiame-por-uno-al-azar

El .env.example es lo que le dice al que clona el repo qué variables necesita. Sin él, el proyecto no arranca en otra máquina y nadie sabe por qué.

.gitignore — la línea que evita el accidente
# dotenv environment variable files
.env
.env.*
!.env.example

Validar la configuración al arrancar

Este es el paso que casi nadie da. process.env es un objeto de string | undefined. Sin validar, un PORT mal escrito aparece como NaN tres capas más abajo, y un JWT_SECRET faltante recién cuando alguien intenta loguearse.

9.3 — config/env.ts
import { config } from 'dotenv';
import { z } from 'zod';

config({ quiet: true });   // lee el .env y lo mete en process.env

const envSchema = z.object({
  PORT: z.coerce.number().default(3000),
  DB_PASSWORD: z.string().default(''),

  // El único sin default: si falta, la API NO arranca.
  JWT_SECRET: z.string().min(32, 'Al menos 32 caracteres'),
});

const resultado = envSchema.safeParse(process.env);

if (!resultado.success) {
  console.error('✖ Falta configuración o está mal');
  process.exit(1);
}

export const env = resultado.data;   // tipado: env.PORT es number

Es el mismo Zod de la unidad 7, usado para otra cosa. Y la idea de fondo es idéntica: la configuración también es una entrada que viene de afuera, así que también se valida en el borde.

Importante
Fallar ruidosamente y temprano. Una API que levanta con la configuración incompleta y explota en el primer login es mucho peor de depurar que una que directamente no levanta y dice qué falta. Probalo: borrá la línea del JWT_SECRET de tu .env, arrancá el 9.3 y mirá el mensaje.
Bloque 3

Contraseñas: qué se guarda en esa columna

Ahora sí, la primera pieza de autenticación. La pregunta es una sola y es concreta: ¿qué se guarda en la columna de la contraseña?

El ejemplo 9.1.1 recorre tres ideas malas antes de llegar a la buena. Conviene leerlas en ese orden: cada una falla por un motivo distinto y los tres motivos importan.

Idea 1 — guardarla tal cual

{ email: 'ana@dsw.com', password: 'messi10' }

Cualquiera que vea esa fila sabe la contraseña: el que administra la base, el que hace un backup, el que se filtra un dump. Y hay un daño que no es de tu sistema: la gente reusa contraseñas. Filtrar tu tabla le abre el mail a todos ellos.

Idea 2 — cifrarla

Suena mejor: el que mira la base ve un chorizo ilegible. Pero cifrar es una operación de ida y vuelta, y la clave para descifrar está en el mismo servidor que la base.

Importante
Para contraseñas no querés cifrado: querés algo que ni vos puedas deshacer. La prueba la tenés a la vista todos los días y nunca la miraste: los sistemas serios ofrecen "restablecer contraseña" y nunca "recordar mi contraseña". No la tienen. Si algún sitio te manda tu contraseña vieja por mail, la está guardando mal.

Idea 3 — hashear con un hash rápido

Un hash sí es de una sola dirección. Vamos bien. Pero SHA-256 tiene dos problemas:

sha256('messi10') // 87739c6d8a84a660f7d0f137dcd1ab00...
sha256('messi10') // 87739c6d8a84a660f7d0f137dcd1ab00...  ← idéntico

Es determinístico: dos usuarios con la misma contraseña tienen el mismo hash. Se puede mirar la tabla y deducir "estos catorce tienen todos la misma, debe ser 123456".

Y el grave: es rápido. Está diseñado para serlo. El ejemplo 9.1.1 termina rompiendo un hash por diccionario:

for (const candidato of diccionario) {
  if (sha256(candidato) === objetivo) { // ¡encontrada! }
}

// encontrada: "messi10" en 3 intentos
// tiempo: 0.154 ms
Cuidado
Acá el hash no se rompió. Nadie invirtió SHA-256 — eso sigue siendo imposible. Lo que se hizo fue probar candidatos, que es infinitamente más barato de lo que parece. Una placa de video común hace miles de millones de SHA-256 por segundo, y las listas de contraseñas filtradas tienen cientos de millones de entradas.

bcrypt: las dos cosas que faltaban

9.1.2 — el mismo password, dos hashes distintos
const hash1 = await bcrypt.hash('messi10', 10);
const hash2 = await bcrypt.hash('messi10', 10);

hash1 === hash2;  // false

Lo que cambió es que bcrypt genera un salt aleatorio por hash. Y la pregunta que aparece sola —"¿dónde guardo el salt?"— tiene una respuesta que sorprende: en ningún lado, viene adentro.

$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
 │  │  └─────── salt (22) ────────┘└──────── hash (31) ───────┘
 │  └─ cost factor: 10
 └──── versión del algoritmo: 2b

Sesenta caracteres, cuatro partes, una sola columna — un varchar(60). Y que el salt sea público no lo rompe: su trabajo es que dos usuarios con la misma contraseña no compartan hash, no ser secreto.

El cost factor

La segunda pieza: bcrypt es lento a propósito, y regulable. Cada +1 duplica el trabajo.

CostTiempo por hash
4~2 ms
8~21 ms
10~84 ms
12~346 ms
Idea central
"Lento" suena a error de diseño y es justo al revés. El costo lo pagás una vez por login, donde 100 ms no los nota nadie; el atacante lo paga en cada intento. Un diccionario de diez millones de entradas pasa de segundos a semanas. La asimetría es todo el truco.

Verificar

await bcrypt.compare('messi10', hashGuardado);  // true

compare() vuelve a hashear el candidato usando el salt que viene dentro del hash guardado y compara los resultados. Nunca desencripta nada. Y no hay atajo: comparar con === contra un hash nuevo siempre da false, porque el salt es otro.

Bloque 4

El login, y por qué no alcanza

Con hash y compare ya se puede escribir el login. Es corto:

9.3 — services/auth.service.ts, la idea
const usuario = await repo.findByEmail(datos.email);
const coincide = await bcrypt.compare(datos.password, usuario.passwordHash);

if (!usuario || !coincide) {
  throw new UnauthorizedError('Credenciales inválidas');
}

El mensaje de error

Ese if junta dos casos que la versión ingenua separa:

Ingenuo
if (!usuario)
  return 'No existe ese email';

if (!coincide)
  return 'Contraseña incorrecta';
Correcto
if (!usuario || !coincide)
  return 'Credenciales inválidas';

La diferencia entre los dos mensajes es información gratis: permite averiguar qué emails están registrados sin saber ninguna contraseña. Se llama enumeración de usuarios, y en un sitio donde estar registrado dice algo de vos, importa bastante.

Cuidado
Unificar el mensaje no alcanza: si el usuario no existe y devolvemos ya mismo, la respuesta llega mucho más rápido porque no corrió bcrypt. El tiempo filtra lo mismo que el mensaje. Por eso el ejemplo 9.1.3 compara igual, contra un hash descartable, para que las dos ramas tarden parecido. Es un detalle chiquito que muestra bien cómo se piensa en seguridad: no alcanza con tapar la puerta si la ventana dice lo mismo.

Y ahora el problema de verdad

El login anda. Verificamos la contraseña de Ana. Llega el request siguiente y…

Idea central
HTTP no tiene memoria. Cada request llega solo, sin ninguna relación con el anterior. El servidor autenticó a Ana hace dos segundos y en el request siguiente no tiene la menor idea de quién es. Eso no es una limitación que haya que arreglar: es el diseño de HTTP, y es lo que permite que una API escale a varias instancias.

Entonces, ¿cómo hace el servidor para acordarse? Hay dos familias de respuestas, y conviene nombrar las dos aunque usemos una:

Sesión en el servidorToken (JWT)
Quién guarda el estadoEl servidor, en memoria o en una tablaNadie: viaja en el token
Qué manda el clienteUn id de sesiónEl token entero
Cerrar sesiónBorrar una fila. InmediatoNo se puede: hay que esperar que venza
Varias instancias de la APIHay que compartir las sesionesSale gratis

Ninguna es "la correcta". Las sesiones son más simples de razonar y permiten un logout de verdad; los tokens escalan sin infraestructura extra y sirven igual para un front web, una app móvil y otra API. En la cátedra usamos JWT, que es lo que vas a encontrar en el 90% del material y lo que va a consumir el front de la materia.

Bloque 5

JWT: qué es, y sobre todo qué no es

Este es el bloque conceptual de la unidad. Todo lo demás es plomería; esto es el modelo mental.

9.2.1 — emitir un token
const token = jwt.sign(
  { sub: '1', email: 'ana@dsw.com', rol: 'usuario' },
  SECRET,
  { expiresIn: '1h' },
);

// eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxIiwiZW1haWwiOi...

Ese chorizo tiene tres partes separadas por punto. Y las dos primeras se abren con una línea:

const [header, payload, firma] = token.split('.');

JSON.parse(Buffer.from(payload, 'base64url').toString());
// { sub: '1', email: 'ana@dsw.com', rol: 'usuario', iat: ..., exp: ... }
Cuidado
Acabamos de leer el payload sin el secret. Base64 no es encriptación: es una forma de escribir bytes con caracteres seguros para una URL, y se deshace sin ninguna clave. Cualquiera con el token lo lee: el usuario, una extensión del navegador, cualquiera que abra jwt.io.
Idea central
Un JWT no es secreto. Es auténtico. Son dos propiedades distintas y confundirlas es el error más caro de la unidad. Se puede leer; no se puede falsificar. Consecuencia directa y no negociable: en el payload va el id del usuario y el rol —cosas que él ya sabe de sí mismo— y nunca la contraseña, su hash, el DNI ni nada privado.

Entonces me edito el payload y me pongo admin

Es la primera pregunta que aparece, y el ejemplo 9.2.2 lo intenta:

const payloadTrucho = { ...payloadOriginal, rol: 'admin' };
const tokenTrucho = `${header}.${nuevoPayload}.${firmaOriginal}`;

jwt.decode(tokenTrucho);   // { rol: 'admin' }  ← dice admin
jwt.verify(tokenTrucho, SECRET);
// JsonWebTokenError: invalid signature

La tercera parte es la firma, y no es JSON:

firma = HMAC-SHA256( header + '.' + payload, SECRET )

Un hash de las dos primeras partes, mezclado con el secret. Cambiar una letra del payload invalida la firma, y recalcularla requiere el secret. Editar el payload es trivial; hacer que la firma cierre, no.

El ejemplo prueba tres ataques y los tres fallan por el mismo motivo:

  1. Editar el payload y dejar la firma vieja → invalid signature.
  2. Firmar uno nuevo con un secret inventado → invalid signature.
  3. Poner alg: none en el header, para que no valide nada → jwt signature is required.
Importante
El tercero es un clásico histórico: en 2015 varias librerías lo aceptaban. La moraleja vale mucho más que el caso — nunca dejes que el dato que estás validando decida cómo se valida. Por eso en el código de la materia el verify lleva { algorithms: ['HS256'] }: el algoritmo lo fija el servidor, no el token.

decode nunca, verify siempre

Chequea la firmaChequea expNecesita el secret
jwt.decode()NoNoNo
jwt.verify()SíSíSí

En el servidor, cualquier decisión se toma con verify(). decode() sirve del lado del cliente, para mostrar el nombre del usuario en la barra sin volver a pedirlo — ahí no se está autorizando nada.

El secret

Todo el esquema se apoya en una sola pieza secreta. Cuatro reglas:

  • Largo y aleatorio, 32 bytes o más. Se genera con randomBytes(32).toString('hex'), no se inventa.
  • Fuera del código, en el .env del bloque 2. Ahora se ve para qué era.
  • Distinto en desarrollo y en producción.
  • Si se filtra, cualquiera emite tokens válidos para cualquier usuario. Cambiarlo invalida todos los tokens vigentes — que es justo lo que querés en ese caso.

Lo que la firma no resuelve

Un token copiado del navegador de otra persona funciona igual de bien: es válido, la firma cierra y no venció. La firma prueba que lo emitió el servidor, no que lo esté usando su dueño. De ahí las tres precauciones reales: HTTPS siempre, expiración corta y no dejarlo donde cualquier script de la página lo pueda leer.

Cuidado
La contra grande del enfoque: los JWT son autocontenidos. El servidor no guarda nada, así que no tiene dónde tachar un token. El "cerrar sesión" borra el token del cliente, pero una copia hecha antes sigue sirviendo hasta el exp. No es un bug de la implementación: es el precio de no tener estado.
Lo que sigue
Con esto ya tenemos las dos piezas: contraseñas guardadas bien y un token que el servidor puede verificar. Falta lo más fácil y lo que más se rompe en el TP: meterlas en la API sin dejar ninguna puerta abierta.
Bloque 6

El middleware de autenticación

Volvemos al proyecto de la unidad 8 y le agregamos la puerta. La estructura casi no se mueve:

src/
├─ config/       env.ts                  ← nuevo: el .env validado
├─ entities/     usuario.entity.ts       ← nuevo
│                producto.entity.ts      ← + creadoPor
├─ middlewares/  autenticar.ts           ← nuevo: ¿quién sos?
│                autorizar.ts            ← nuevo: ¿podés?
├─ services/     auth.service.ts         ← nuevo: registro y login
├─ shared/       jwt.ts                  ← nuevo: emitir y verificar
├─ types/        express.d.ts            ← nuevo: req.usuario
└─ app.ts                                ← + cors

La entidad nueva no tiene sorpresas, salvo una columna:

entities/usuario.entity.ts
@Property({ length: 60, hidden: true })
passwordHash!: string;
  • Se llama passwordHash y no password. El nombre es documentación: el que lea la entidad tiene que ver de una que ahí no hay una contraseña.
  • length: 60 porque eso mide un hash de bcrypt. Los sesenta caracteres del bloque 3.
  • hidden: true hace que MikroORM la saque al serializar a JSON. Sin eso, un res.json(usuario) manda el hash por la red.

El middleware, entero

middlewares/autenticar.ts
export function autenticar(req: Request, res: Response, next: NextFunction) {
  try {
    const header = req.headers.authorization;

    if (!header?.startsWith('Bearer ')) {
      throw new UnauthorizedError('Falta el token de autenticación');
    }

    req.usuario = verificarToken(header.slice('Bearer '.length));

    next();
  } catch {
    next(new UnauthorizedError('Token inválido o expirado'));
  }
}

Eso es todo. Es un middleware de Express común y silvestre —la mecánica ya la conocen del validar de la unidad 7 y del RequestContext de la 8— y hace tres cosas: saca el token del header, lo verifica, lo deja en req.usuario.

Bearer significa "portador": el token vale por tenerlo, como un boleto de colectivo. No importa quién lo presente — que es exactamente la contra del bloque anterior, dicha desde el estándar.

req.usuario sin any

Request es un tipo de Express y no tiene esa propiedad. La salida fácil es (req as any).usuario, y es una mentira que se paga después. La correcta es declaration merging:

types/express.d.ts
declare global {
  namespace Express {
    interface Request {
      usuario?: PayloadToken;
    }
  }
}

TypeScript permite reabrir una interface declarada en otro paquete y sumarle campos. Es una de las cosas más útiles del lenguaje y no la vimos en la unidad 7; este es el caso donde se necesita.

Importante
El ? no es un detalle de sintaxis. En una ruta pública el middleware no corrió y req.usuario es undefined. El tipo lo dice y el compilador obliga a contemplarlo en cada controller. Si lo declaráramos obligatorio, el tipo estaría mintiendo — que es justo lo que la unidad 7 pide no hacer.

Las rutas son el mapa de permisos

routes/productos.routes.ts
productosRouter.get('/', listar);                                // pública
productosRouter.post('/', autenticar, validar(schema), crear);   // autenticada
productosRouter.delete('/:id', autenticar, eliminar);           // + autorizada

Leyendo tres líneas se sabe quién puede hacer qué. Esa legibilidad es el argumento para poner la autenticación acá y no adentro de cada controller: un permiso olvidado se ve como una línea que falta.

Y el get público está a propósito: no todo tiene que estar protegido. El catálogo se ve sin cuenta, como en cualquier tienda.

Cuidado
El orden importa: autenticar va antes que validar. Si un anónimo manda un body inválido, la respuesta correcta es 401 y no 400 — no tiene por qué enterarse del formato de una ruta que no puede usar. Es el mismo criterio del mensaje unificado del login: no regalar información.
Bloque 7

Autorización: por rol y por dueño

Volvemos a la distinción del bloque 1, ahora con código. Autenticar es una pregunta; autorizar son muchas, una por cada regla del sistema. Por eso no hay un middleware de autorización: hay una fábrica que produce el que hace falta.

middlewares/autorizar.ts
export function requiereRol(...rolesPermitidos: Rol[]) {
  return (req: Request, res: Response, next: NextFunction) => {
    if (!rolesPermitidos.includes(req.usuario.rol)) {
      next(new ForbiddenError('No tenés permiso para esta operación'));
      return;
    }

    next();
  };
}

requiereRol('admin') no es el middleware: devuelve el middleware. Es una función de orden superior, el mismo patrón que validar(schema) de la unidad 7. Es la segunda vez que aparece, y con dos casos ya se ve el patrón: cuando un middleware necesita un parámetro, se envuelve en una función que lo devuelve.

authRouter.get('/usuarios', autenticar, requiereRol('admin'), listarUsuarios);

La regla que no entra en un middleware

Ahora la otra: "podés borrar este producto si lo creaste vos". Y acá aparece el punto conceptual del bloque, el que más se lleva puesto en el TP:

Depende solo del token
"Tenés que ser admin." Se contesta con lo que trae el request, sin tocar la base. → middleware
Depende del recurso
"Este producto es tuyo." No se puede contestar sin ir a buscarlo. → service

Si la segunda la pusiéramos en un middleware, ese middleware consultaría la base y el service la consultaría de nuevo: dos veces la misma query, y una regla de negocio escrita en la capa equivocada.

services/productos.service.ts
export async function eliminarProducto(id: number, quienPide: PayloadToken) {
  const producto = await repo.findByIdOrFail(id);        // 1. ¿existe? → 404

  const esAdmin = quienPide.rol === 'admin';
  const esDueno = producto.creadoPor.id === Number(quienPide.sub);

  if (!esAdmin && !esDueno) {                            // 2. ¿podés? → 403
    throw new ForbiddenError('Solo podés borrar los productos que creaste');
  }

  await repo.eliminar(producto);                        // 3. borrar
}
Idea central
La regla para decidir dónde va cada chequeo: si para contestar hay que ir a la base, es del service. Todo lo demás, middleware.

Lo que decide permisos no se le pregunta al cliente

Tres decisiones del código del 9.3 que son en realidad la misma decisión:

  1. El dueño del producto sale del sub del token, no del body. Si viniera del body, cualquiera crearía productos a nombre de otro.
  2. El rol no se acepta en el registro: todo registro público crea un usuario común. Si se aceptara, cualquiera se registraría como admin.
  3. El algoritmo de verificación no se lee del header del token: lo fija el servidor con { algorithms: ['HS256'] }.
Cuidado
Hay una fuga chiquita en el orden 404-después-403: pedir un producto inexistente da 404 y pedir uno ajeno da 403, así que cualquiera puede averiguar qué ids existen aunque no pueda tocarlos. Acá no importa (los productos se listan públicamente). Cuando importa —historias clínicas, facturas— la respuesta correcta es devolver 404 también en el caso del 403: "si no es tuyo, para vos no existe". La decisión es de producto; lo importante es tomarla a conciencia y no que salga sola del orden de los if.
Bloque 8

CORS: el error que va a aparecer en el front

Cierre de la unidad con el tema que no es de autenticación pero aparece siempre junto con ella: el momento en que el front intenta llamar a esta API y no puede.

Directo: este error lo vas a tener sí o sí, la semana que conectes el front con el back. La idea del bloque es que cuando pase sepas qué estás mirando.

Qué es

El navegador tiene una regla vieja llamada same-origin policy: el JavaScript de una página solo puede leer respuestas de su mismo origen. Un origen es la terna esquema + host + puerto, y los tres tienen que coincidir.

http://localhost:5173   ← el front
http://localhost:3000   ← la API
                  ↑
       distinto puerto = OTRO ORIGEN

CORS es el mecanismo por el cual el servidor levanta esa restricción para orígenes específicos, mandando unos headers en la respuesta.

El error, y lo que esconde

Access to fetch at 'http://localhost:3000/api/productos' from origin
'http://localhost:5173' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested resource.

Y ahora lo que hay que mostrar al lado, en el log de la API:

GET     /api/productos       origin: http://localhost:5173
Idea central
El request llegó. El servidor contestó 200. Lo que el navegador bloquea es que esa página lea la respuesta. De ahí dos cosas que desconciertan: un POST bloqueado por CORS igual puede haber creado el registro, y fetch rechaza con un TypeError: Failed to fetch sin ningún detalle — el motivo real solo está en la consola del navegador.

Dos consecuencias más, que ordenan todo lo demás:

  • La restricción la aplica el navegador, no el servidor. Por eso los .http, Postman y curl nunca dan error de CORS: no son navegadores y no tienen a quién proteger. Es exactamente la razón por la que este problema aparece recién cuando entra el front.
  • CORS no protege tu API. Protege al usuario de que una página cualquiera use su sesión sin que se entere. Cualquiera puede pegarle a tu API desde una terminal. La seguridad la dan la autenticación y la autorización — todo lo anterior.

El preflight

Cuando el request lleva el header Authorization, el navegador manda antes uno que nadie escribió:

OPTIONS /api/productos
Origin: http://localhost:5173
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type

Es el preflight: "¿me dejás mandar un POST con estos headers?". Si la respuesta no autoriza, el POST no se manda nunca — en el log de la API se ve el OPTIONS y no se ve el POST.

No todos los requests lo disparan; los simples (un GET, un POST de formulario) salen directo. Pero se vuelve no-simple en cuanto lleva Content-Type: application/json o un header propio como Authorization — es decir, casi cualquier request de una API REST con login.

La configuración

app.ts — y va PRIMERO, antes que las rutas
app.use(cors({
  origin: env.CORS_ORIGIN,
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
}));

Va primero porque, si un error se produce más abajo y la respuesta sale sin los headers de CORS, el front ve un error de CORS en vez del 500 real. Y el origen sale del .env porque cambia por ambiente — bloque 2, otra vez.

Cuidado
app.use(cors()) a secas es origin: '*': cualquier página del mundo puede llamar a la API desde el navegador de tu usuario. Es lo primero que aparece buscando el error y "arregla" el problema al instante. Para una API pública de solo lectura puede estar bien; para una con login, no. Además es incompatible con credentials: true: si el front manda cookies, hay que declarar el origen exacto igual.

El error específico de esta unidad

El más difícil de diagnosticar, porque parece que CORS ya está resuelto:

app.use(cors({ origin: 'http://localhost:5173', allowedHeaders: ['Content-Type'] }));

El origen está bien. El GET público anda perfecto. Y el POST con token falla. Falta Authorization en la lista: el preflight contesta que solo autoriza Content-Type y el navegador corta.

Dato
Detalle que sorprende: si no se pasa allowedHeaders, el paquete cors copia en la respuesta los headers que el preflight pidió, y Authorization pasa sin problema. O sea que declarar la lista a medias es peor que no declararla. Por eso este error aparece justo cuando alguien "se puso a configurar CORS bien".

Checklist para cuando falle

  1. ¿El middleware de CORS está antes que las rutas?
  2. ¿El origin es exactamente el del front? Con el puerto y sin barra final.
  3. Si declaraste allowedHeaders, ¿está Authorization?
  4. Si declaraste methods, ¿está el que usás? El DELETE se olvida seguido.
  5. ¿Estás leyendo el error en la consola del navegador? El de fetch no dice nada.
Autoevaluación

Ponete a prueba

Respondé cada pregunta mentalmente y después tocá para revelar la respuesta y verificar.

1. Un usuario logueado intenta borrar un producto de otro. ¿La API responde 401 o 403, y por qué?
403. El 401 es no sé quién sos: falta el token, venció o la firma no cierra, y se arregla yendo a loguearse. Acá el token es válido y la API sabe perfectamente quién sos — lo que falta es el permiso. Volver a loguearte no cambiaría nada, y esa es justo la prueba de que el código correcto es 403.
2. ¿Por qué no alcanza con cifrar la contraseña antes de guardarla?
Porque cifrar es una operación de ida y vuelta: si el sistema puede descifrar, la clave para hacerlo está en el mismo servidor que la base, y quien se lleva una se lleva la otra. Lo que hace falta es un hash, que no se puede deshacer ni siquiera desde adentro. La prueba está a la vista en cualquier sitio serio: te ofrecen restablecer la contraseña y nunca recordarla, porque no la tienen.
3. Si el salt de bcrypt es aleatorio y distinto en cada hash, ¿dónde se guarda para poder verificar después?
En ningún lado: viene adentro del hash. El string de 60 caracteres tiene cuatro partes — $2b$10$<salt de 22><hash de 31>: versión, cost factor, salt y hash. Por eso la columna de la base es una sola (varchar(60)) y por eso compare() puede rehashear el candidato con el salt correcto. Que el salt sea público no rompe nada: su trabajo es que dos usuarios con la misma contraseña no compartan hash, no ser secreto.
4. ¿Por qué está bien que bcrypt sea lento, si eso normalmente es un defecto?
Porque el costo es asimétrico: vos lo pagás una vez por login, donde 100 ms no los nota nadie; el que intenta adivinar contraseñas lo paga en cada intento. Con SHA-256 se prueba un diccionario entero en segundos; con bcrypt en cost 10, el mismo diccionario tarda semanas. El cost factor es exponencial —cada +1 duplica el trabajo— y se sube con los años, sin invalidar los hashes viejos porque cada uno lleva su cost adentro.
5. ¿Podés guardar el DNI del usuario en el payload del JWT para no consultarlo después?
No. El payload es JSON en base64url, y base64 no es encriptación: se lee con una línea de código, sin el secret. Cualquiera con el token lo ve — el usuario, una extensión del navegador, jwt.io. Un JWT no es secreto, es auténtico: no se puede falsificar sin el secret, que es otra cosa. En el payload va el id, el rol y la expiración: cosas que el propio usuario ya sabe de sí mismo.
6. Editás el payload de tu token para que diga rol: "admin". ¿Qué pasa cuando lo mandás?
La API responde 401 con invalid signature. La tercera parte del token es la firma: HMAC-SHA256(header + '.' + payload, SECRET). Al cambiar una letra del payload, la firma que corresponde es otra, y calcularla requiere el secret del servidor. Editar el payload es trivial; hacer que la firma cierre, no. Lo mismo pasa si firmás un token nuevo con un secret inventado.
7. ¿Por qué el login contesta lo mismo cuando el email no existe que cuando la contraseña está mal?
Para no revelar qué emails están registrados. Dos mensajes distintos permiten averiguarlo probando de a uno, sin saber ninguna contraseña (se llama enumeración de usuarios). Y unificar el mensaje no alcanza: si cuando el usuario no existe cortás antes de correr bcrypt, la respuesta llega mucho más rápido y el tiempo filtra lo mismo que el mensaje. Por eso se compara igual, contra un hash descartable.
8. "Solo el que creó el producto puede borrarlo". ¿Va en un middleware o en el service?
En el service. Es la regla que separa las dos clases de autorización: la que depende solo del token ("tenés que ser admin") se resuelve sin tocar la base y es un middleware; la que depende del recurso necesita ir a buscar el producto para ver de quién es. Si la pusieras en un middleware, ese middleware consultaría la base y el service la consultaría otra vez. Si para contestar hay que ir a la base, es del service.
9. El front tira un error de CORS al llamar a la API. ¿El request llegó al servidor?
Sí, casi siempre llegó, y el servidor contestó. Lo que el navegador bloquea es que esa página lea la respuesta. De ahí dos cosas raras: un POST bloqueado por CORS igual puede haber creado el registro, y fetch rechaza con un TypeError: Failed to fetch sin ningún detalle — el motivo real solo está en la consola del navegador. La excepción es cuando hay preflight y se rechaza: ahí el request de verdad nunca sale.
10. Si CORS no protege tu API, ¿de qué protege?
Protege al usuario, no al servidor. Sin la same-origin policy, cualquier página que abrieras podría hacerle requests a tu banco con tu sesión y leer las respuestas. La restricción la aplica el navegador, así que a tu API le puede pegar cualquiera desde una terminal — por eso los archivos .http, Postman y curl nunca dan error de CORS. La seguridad de la API la dan la autenticación y la autorización.
11. ¿Por qué el .env no se sube al repositorio, pero el .env.example sí?
El .env tiene los valores reales —tu contraseña de MySQL, el secret del JWT— y publicarlos es publicar la llave de tu casa; peor todavía, borrarlos en el commit siguiente no alcanza, porque quedan en el historial de git. El .env.example tiene solo los nombres de las variables y valores de ejemplo: es lo que le dice al que clona el repo qué necesita configurar. Sin él, el proyecto no arranca en otra máquina y nadie sabe por qué.
Cierre

Resumen

  • Autenticación es "¿quién sos?" y falla con 401. Autorización es "¿podés hacer esto?" y falla con 403. Volver a loguearse arregla el primero y no cambia nada en el segundo.
  • Los secretos salen del código y van a un .env que no se versiona, con un .env.example que sí. La configuración se valida al arrancar: fallar temprano y ruidosamente.
  • La contraseña no se guarda. Se guarda un hash de bcrypt de 60 caracteres, con la versión, el cost y el salt adentro. Cifrar no sirve: es reversible.
  • El salt hace que el mismo password dé hashes distintos. El cost factor hace que calcularlo sea lento a propósito: se paga una vez por login y millones de veces por ataque.
  • Un login que falla contesta siempre lo mismo, y tarda lo mismo en las dos ramas.
  • HTTP no tiene memoria. El token es la prueba que el cliente vuelve a presentar en cada request.
  • Un JWT no es secreto, es auténtico: el payload se lee sin el secret y no se puede falsificar con él. Por eso ahí va el id y el rol, nunca nada privado.
  • En el servidor, verify() siempre; decode() nunca. Y el algoritmo lo fija el servidor, no el header del token.
  • Un JWT es una foto del momento en que se emitió. No hay logout real: el servidor no guardó nada que pueda tachar.
  • La autorización que depende solo del token es un middleware; la que depende del recurso va en el service. Si hay que ir a la base para contestar, es del service.
  • Lo que decide permisos no se le pregunta al cliente: ni el dueño, ni el rol, ni el algoritmo.
  • CORS no protege la API, protege al usuario. Lo aplica el navegador, y por eso los .http nunca lo muestran.
