Introducción

Contenidos de la guía

Última unidad de la materia, y la que cobra todo lo anterior de golpe. Hasta hoy cada unidad dejó una promesa: el .env de la 9 existe porque en producción la configuración no puede estar en el código; las migraciones de la 8.4 existen porque contra una base con datos no se puede sincronizar el esquema a lo bruto; los tests de la 10 existen, entre otras cosas, para que un servidor pueda negarse a publicar una versión rota. Creá las cuentas antes de necesitarlas. La base de Aiven tarda varios minutos en pasar de Rebuilding a Running, y el primer build de Render otros tantos. Si dejás los dos registros para el día de la entrega, esos minutos aparecen justo cuando no los tenés. Ninguna de las dos pide tarjeta.

Bloque 1

"Anda en mi máquina"

Levantá el 9.3 como venías haciendo: npm run dev, el productos.http, login, crear, borrar. Todo funciona. Y ahí llega la pregunta:

Mandame el link.

No hay link. Hay http://localhost:3000, que en la computadora de cualquier otro apunta a su propia máquina, donde no hay nada. Después de tres meses de trabajo, la API la puede usar exactamente una persona.

Importante
localhost no es una dirección de internet: es "esta computadora". Suena obvio dicho así y no lo es — mucha gente pasa un cuatrimestre entero sin haberlo pensado.

Las tres piezas

Deployar es resolver tres cosas, y conviene tenerlas claras antes de tocar nada:

Dónde corre el proceso
Una máquina prendida siempre, con Node, que ejecuta tu código y escucha requests. Es lo que hace Render.
Dónde viven los datos
Un MySQL que no es el tuyo, también prendido siempre, al que se llega por internet. Es lo que hace Aiven.
De dónde sale la configuración
Las credenciales de esa base y el secret del JWT, que no pueden estar en el repositorio. Ya lo resolvimos en la unidad 9.
Y una cuarta, gratis
Un dominio y un certificado HTTPS, que las plataformas dan hechos. Hace diez años era medio día de trabajo.

La tercera ya está resuelta desde la unidad 9, y vale decirlo en voz alta: el .env no era una prolijidad, era esto.

Dato
Las palabras que van a leer en todos lados: hosting es alquilar la máquina, deploy es el acto de poner tu versión ahí, PaaS (Render, Railway, Fly) es que la plataforma se ocupe del sistema operativo por vos, y IaaS (una máquina virtual pelada) es que te lo ocupes vos. Nosotros usamos PaaS, que es a un servidor de verdad lo que un ORM es a escribir SQL a mano: te ahorra el 90% y te oculta cosas que en algún momento vas a querer saber.
Bloque 2

El build: de tsx a dist/

La primera pregunta que le hace cualquier plataforma a cualquier aplicación es "¿con qué comando te ejecuto?". Y ahí aparece un problema que veníamos esquivando desde la unidad 7.

En el servidor no hay tsx. Hay node, y node no entiende TypeScript.

package.json
"dev": "tsx watch src/server.ts",     // tu máquina
"build": "tsc",                       // src/ -> dist/
"start": "node dist/server.js"       // el servidor

Es la primera vez en toda la materia que npm run build deja de ser decorativo. Corrélo y abrí dist/: JavaScript plano, sin un solo tipo, ejecutable por cualquier Node.

Importante
La fila que sorprende de esa tabla es una sola: tsx no chequea tipos. Los borra y ejecuta. Por eso un proyecto puede venir andando perfecto con npm run dev durante tres semanas y romperse en el primer npm run build — que va a ser el día del deploy, con el TP para entregar. Ese es el motivo del npm run check que arrastramos desde la unidad 7, y el motivo por el que hay que correrlo antes de subir nada.

Qué se sube al servidor

Otra sorpresa: no se sube dist/. Se sube el repositorio, y el servidor compila.

npm ci && npm run build     // build command
npm start                    // start command

dist/ está en el .gitignore y ahí se queda. Un dist/ commiteado es la forma más rápida de que lo que corre en producción no sea lo que dice el repositorio: alguien toca el .ts, se olvida de recompilar, y el servidor sigue con el .js viejo.

ComandoQué haceDónde
npm installinstala y puede modificar el package-lock.jsontu máquina
npm ciinstala exactamente lo del lock, y falla si no coincideel servidor, siempre
--omit=devsaltea las devDependenciesdespués de compilar

Que npm ci falle cuando el package.json y el lock no coinciden es una virtud, no una molestia: en el servidor querés que el deploy se niegue antes que instalar una versión distinta de la que probaste.

Cuidado
El error de razonamiento que hace todo el mundo la primera vez: "en producción no necesito las devDependencies, entonces npm ci --omit=dev". Y el build muere con Cannot find module 'typescript', porque TypeScript es una devDependency y el build lo necesita. Primero se instala todo y se compila; recién después, si querés adelgazar, npm prune --omit=dev. En el 11.1 la diferencia es medible: 49 MB contra 3,5 MB.

La trampa de nuestro stack

Esta no está en ningún tutorial de deploy, porque es consecuencia de una decisión de la unidad 8. Usamos TsMorphMetadataProvider: para saber que precio: number es un decimal y nombre: string un varchar, MikroORM lee los tipos de los archivos TypeScript al arrancar.

En el servidor corre node dist/server.js, y en dist/ hay JavaScript. La aplicación muere al arrancar:

MetadataError: Source file './dist/entities/usuario.entity.ts' not found.
Check your 'entitiesTs' option and verify you have 'compilerOptions.declaration'
enabled in your 'tsconfig.json'.

La solución está adentro del error, que es una rareza. Una línea en el tsconfig.json:

tsconfig.json
{
  "compilerOptions": {
    "declaration": true     // emite los .d.ts al lado de cada .js
  }
}

Los .d.ts son archivos de solo tipos, sin código. Ahí está lo que el ORM necesita.

Bloque 3

El arranque, y el healthcheck

Tres líneas que en tu máquina no cambian absolutamente nada, y sin las cuales el deploy no termina. Es lo que las hace difíciles: no hay forma de darse cuenta de que faltan hasta que fallan.

1. El puerto no lo elegís vos

// Lo que veníamos haciendo
app.listen(3000);

// Lo que hay que hacer
const PORT = Number(process.env.PORT) || 3000;

La plataforma corre muchas aplicaciones en la misma máquina y le asigna a cada una su puerto por variable de entorno. Si te aferrás al 3000, escuchás en un puerto al que nadie te va a hablar. La plataforma espera respuesta, no la recibe, y el deploy se queda colgado hasta que muere con "no open ports detected".

2. La interfaz tampoco

app.listen(PORT, '0.0.0.0');

0.0.0.0 significa "aceptá conexiones por cualquier interfaz de red". localhost significa "solo desde esta máquina" — y adentro de un contenedor eso quiere decir solo desde adentro del contenedor, con el proxy de la plataforma del lado de afuera.

3. Apagarse bien

process.on('SIGTERM', () => {
  server.close(async () => {
    await orm.close();
    process.exit(0);
  });
});

Para publicar una versión nueva, la plataforma no mata el proceso viejo: le manda SIGTERM y espera unos segundos. Si lo ignorás, llega SIGKILL, que no se puede ignorar, y los requests que estaban a mitad de camino se cortan.

El orden importa: primero server.close(), que deja de aceptar requests nuevos y termina los que están en curso; después la base. Al revés, los requests a mitad de camino se encuentran con la conexión cerrada y contestan 500 justo durante el deploy.

Dato
Este bloque es el event loop de la unidad 3 apareciendo por última vez. Un proceso Node vive mientras tenga algo pendiente: el servidor escuchando es un handle abierto, y por eso npm run dev no termina nunca. Cerrarlo es lo que deja que el proceso muera solo. El setTimeout(...).unref() del 11.2 es la contracara exacta: un timer que no cuenta para mantener vivo el proceso.

El healthcheck

app.get('/health', (req, res) => {
  res.json({ estado: 'ok' });
});

Una ruta que no hace nada. Es cómo la plataforma se entera de si la aplicación está viva: le pega cada pocos segundos y, si deja de contestar, reinicia la instancia. Sin healthcheck, lo único que la plataforma sabe es que el proceso no se cayó, que no es lo mismo que que la API esté respondiendo.

ReglaPor qué
Que sea barataSi consulta la base, un pico de carga la hace tardar, la plataforma te da por muerto y te reinicia justo cuando más tráfico tenías
Que no pida tokenEl que pregunta es un robot sin credenciales
Que no cuente nadaEs una URL pública: ni versiones de librerías ni estado interno
Importante
La primera regla es más contraintuitiva de lo que parece, y en internet hay discusión: "si la base está caída, la API no sirve, ¿no tendría que dar rojo?". El problema es la consecuencia: dar rojo hace que te reinicien, y reiniciar no arregla una base caída — solo agrega downtime a un problema que ya tenías. El healthcheck contesta "¿este proceso está vivo?", no "¿todo el sistema funciona?".
Bloque 4

La base deja de ser tuya

Hasta hoy MySQL estuvo en localhost:3306, con usuario root y contraseña root, en la misma máquina que la API. Tres cosas que dejan de ser ciertas todas juntas.

Por qué la base va afuera

La pregunta llega sola: ¿por qué no instalamos MySQL en el mismo servidor? Y la respuesta es la más importante del bloque:

Idea central
El disco del contenedor donde corre tu aplicación es efímero: se borra entero en cada deploy. Todo lo que escribas ahí —archivos subidos, logs, una base de datos— desaparece la próxima vez que hagas git push. Por eso la base vive afuera, en un servicio que sí tiene disco persistente. Es la misma razón por la que un archivo que sube un usuario no se guarda en uploads/ sino en un servicio aparte.

TLS, y el atajo que anula el punto

Una base gestionada rechaza las conexiones sin cifrar. Tiene sentido: en localhost el tráfico no sale de tu máquina, pero ahora las contraseñas y los datos de tus usuarios cruzan la red de terceros.

src/mikro-orm.config.ts
driverOptions: {
  connection: {
    ssl: { ca: env.DB_SSL_CA, rejectUnauthorized: true }
  }
}

El ca es el certificado de la autoridad que firmó el del servidor: sirve para verificar que del otro lado está tu base y no alguien haciéndose pasar por ella. Se descarga del panel del proveedor y va como variable de entorno, porque el repositorio no tiene por qué llevar certificados.

Cuidado
Lo que aparece en la mitad de los tutoriales y en la primera respuesta de Stack Overflow: 
ssl: { rejectUnauthorized: false }
Arregla el error en un segundo y desactiva justo la parte que importa. Sigue cifrando, pero deja de verificar con quién está hablando: es TLS sin la garantía de TLS. Lo vas a encontrar igual, así que mejor que sea acá primero y con el motivo — es la diferencia entre pegarlo sin pensar y saber qué estás desactivando.

Y schema.update() se termina

Este es el cambio de fondo. En las unidades 8 y 9, el db.ts decía:

await orm.schema.update();   // comodísimo, y solo mientras la base sea tuya

schema.update() compara tus entidades con la base y genera el SQL para que se parezcan. Cuando la diferencia es "sobra una columna", el SQL que genera es un DROP COLUMN. No pregunta, no avisa y no hay Ctrl+Z.

Renombrar un campo en una entidad —dos segundos de trabajo— borra la columna vieja con todo lo que tenía adentro.

// Antes
@Property()
nombre!: string;

// Después: para el ORM, "falta 'titulo' y sobra 'nombre'"
@Property()
titulo!: string;

La versión que sirve es la de la unidad 8.4: cada cambio de esquema es un archivo de migración versionado, revisable en un pull request, y la tabla mikro_orm_migrations lleva la cuenta de cuáles se aplicaron en cada base.

Dato
En el 11.2 las migraciones corren al arrancar la aplicación (ver db.ts). Lo prolijo es que sean un paso aparte —un pre-deploy command— para que una migración fallida no deje la aplicación en un bucle de reinicios. Los planes gratuitos no tienen ese paso, y hacerlo al arrancar es la opción razonable. Tenelo como lo que es —un atajo—, porque en el trabajo vas a ver las dos formas.
Importante
Abrí el 9.3 y el 11.2 lado a lado, en services/, controllers/, entities/ y schemas/: idénticos. Todo lo que cambió está en config/, db.ts, server.ts y el tsconfig. Eso no es casualidad ni suerte: es la arquitectura de la unidad 6 haciendo su trabajo por cuarta vez.
Bloque 5

Subirla

Esta parte se aprende haciéndola. Dos servicios y un orden que importa: la base primero, porque la API no arranca sin ella.

Paso 1 — la base (Aiven)

  1. Crear el servicio Aiven for MySQL, plan Free: 1 CPU, 1 GB de RAM, 1 GB de disco, sin tarjeta y sin vencimiento.
  2. Elegir región cerca de donde va a estar la API. Cada consulta cruza esa distancia; base en Europa y API en Oregon son cien milisegundos por query.
  3. Esperar a que pase de Rebuilding a Running.
  4. De Connection information salen los cinco valores del .env y el ca.pem.

Y antes de tocar Render, el paso que ahorra media hora de adivinanza: apuntar el .env local a la base de la nube y correr npm run dev. Si arranca y aplica las migraciones, la base está bien y todo lo que falle después es del hosting. Dos problemas separados se resuelven en la mitad de tiempo que dos problemas juntos.

Dato
Render también ofrece bases de datos, y las gratuitas se borran a los 30 días. Para algo que tiene que llegar vivo a la defensa del TP, la base va afuera. Si el proyecto usa PostgreSQL, Neon es el equivalente de Aiven; para MikroORM el cambio es chico —otro paquete de driver— pero hay que regenerar las migraciones, porque el SQL no es el mismo.

Después, las variables de entorno en el panel: las mismas del .env.example menos PORT, que la pone Render. Y ahí conviene detenerse un segundo, porque es la unidad 9 cerrando el círculo: este panel es el .env de producción. Mismo concepto, otro lugar, y por eso el código no necesita un solo if.

Importante
El JWT_SECRET de producción tiene que ser otro, distinto al del .env de desarrollo. Si son el mismo, cualquiera que vea el repositorio del TP puede firmar tokens que el servidor de verdad acepta — y en un repositorio de facultad, "cualquiera" incluye a todo el curso. Render lo puede generar solo (generateValue: true en el render.yaml), que es mejor que cualquier cosa que escribamos nosotros.

Y el archivo que evita todos esos clics

Todo lo anterior, escrito:

render.yaml
services:
  - type: web
    name: dsw-api
    runtime: node
    plan: free
    buildCommand: npm ci && npm run build
    startCommand: npm start
    healthCheckPath: /health
    envVars:
      - key: NODE_ENV
        value: production
      - key: DB_PASSWORD
        sync: false       # existe, pero el valor se carga a mano
      - key: JWT_SECRET
        generateValue: true  # que lo invente Render

sync: false es la forma de declarar un secreto: queda documentado que la variable hace falta, sin que el valor toque el repositorio.

Cuidado
Antes del git push, verificá que el .env no esté en el repositorio: git status, y que no lo nombre. Hacelo aunque parezca innecesario. Es el error más caro de toda la materia y no se arregla borrando el archivo después: queda en el historial de git para siempre, y lo único que sirve es rotar todos los secretos que se filtraron.
Bloque 6

Cuando falla: leer el log

Va a fallar. No es una posibilidad, es el trámite: la primera vez le falla a todo el mundo. Y la habilidad que hay que llevarse de esta unidad no es acertar de una — es saber qué mirar.

Importante
Que quede dicho antes de que pase, y en serio: el primer deploy siempre falla. No es que lo hiciste mal. Lo que separa a alguien que resuelve esto en diez minutos de alguien que pierde la tarde no es la experiencia con Render — es abrir el log y leerlo, en vez de volver a apretar "Deploy" a ver si esta vez sale.
Lo que dice el logQué es

✖ Falta configuración: JWT_SECRETFalta una variable en el panel

El segundo merece un párrafo aparte, porque es el único que no es un error de la plataforma sino un mensaje nuestro. Ese ✖ Falta configuración lo escribimos en el env.ts de la unidad 9, y aparece porque validamos la configuración al arrancar en vez de dejar que explote en el primer login.

Idea central
Fallá al arrancar y en voz alta. En producción esto vale el doble que en tu máquina: el log del deploy dice exactamente qué falta, en el primer segundo, en vez de dejarte una API que levanta contenta y se rompe cuando el primer usuario intenta loguearse. Una aplicación que no arranca es un problema de dos minutos; una que arranca mal es un problema de dos horas.

El que más cuesta es el que no aparece

El deploy dice Live, la URL contesta, el .http anda perfecto — y el front sigue viendo un error de CORS.

No hay nada roto. Falta el dominio del front en CORS_ORIGIN, con https:// y sin barra final. Es la unidad 9 otra vez, y ahora con dominios de verdad en vez de localhost:5173.

Bloque 7

Que no se suba nada roto

Render conectado a GitHub deploya solo en cada push a main. Es cómodo, y esa comodidad tiene un agujero que se ve enseguida:

Deploya aunque los tests estén rojos.

Acá termina de pagarse la unidad 10. Una suite que corre en tu máquina cuando te acordás sirve bastante; una que corre sola y frena el deploy sirve mucho más.

Qué es GitHub Actions, en un minuto

Un servidor que GitHub te presta. Ante un evento que elegís —un push, un pull request— levanta una máquina virtual vacía, corre los pasos que le pediste, y la tira.

Importante
Que la máquina empiece vacía es la mitad del valor: es "anda en mi máquina" verificado por alguien que no es tu máquina. No tiene tu node_modules, ni tu .env, ni esa librería que instalaste global hace tres meses y te olvidaste. Si el proyecto anda ahí, anda en cualquier lado.
.github/workflows/ci.yml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
      - run: npm ci
      - run: npm run check     # tsx no chequea tipos: este es el único lugar
      - run: npm test
      - run: npm run build     # que pasen los tests no garantiza que compile

El resultado queda pegado al commit: el tilde verde o la cruz roja que aparece en la lista de commits y arriba de cada pull request. En un TP de equipo, el de los pull requests es el que más rinde: la rama se testea antes de mezclarse, sin que nadie tenga que acordarse de correr nada.

Y el portero

Para que el deploy dependa de los tests hay que sacarle el volante a Render (Auto-Deploy: OFF) y dispararlo desde el workflow. Todo el archivo existe por una línea:

publicar:
  needs: verificar

needs significa "no arranques hasta que verificar haya terminado bien". Sin esa línea, los dos trabajos corren en paralelo: el pipeline mira los tests fallar y publica igual.

Dato
Los nombres: CI (integración continua) es que cada cambio se verifique automáticamente; CD (entrega continua) es que además se publique solo. Suenan a metodología de libro y son literalmente estos dos archivos. Vale desmitificarlo: no es una arquitectura, son treinta líneas de YAML.
Bloque 8

Lo que cambia cuando está en internet

Está publicada. Cuatro cosas que ahora son distintas, y la última es la que más sorprende.

Se duerme

El plan gratuito de Render apaga el servicio a los 15 minutos sin tráfico. El primer request lo despierta: entre 30 y 60 segundos, con la base reconectando encima. No es un bug, es el trato — la máquina se la prestan a otro mientras no la usás.

Cuidado
Esto tiene una consecuencia muy concreta: el día de la defensa del TP, entrá a la URL diez minutos antes. Si el tribunal es el primero en pegarle en horas, la primera pantalla que vean va a ser un minuto de carga. Es el detalle más práctico de toda esta guía.

No hay consola

El console.log sigue existiendo, pero sale en el panel de la plataforma, mezclado con todo y con un límite de retención. Por eso el errorHandler del 11.2 le pone un identificador a cada 500:

{ "error": "Error interno del servidor", "id": "3f9a2b1c" }

El usuario dice "me tiró error 3f9a2b1c" y eso se busca en el log. Encontrarlo pasa de adivinanza a búsqueda.

Cualquiera le pega

A las pocas horas de estar publicada, el log va a tener requests a /wp-login.php, /.env y /admin. Son robots que barren internet buscando servidores mal configurados, y no tienen nada personal contra el TP.

Importante
Cuando tu servicio lleve un rato arriba, abrí el log y buscá esos requests. Es el mejor argumento de toda la materia para la unidad 9 y no necesita ninguna explicación: alguien, ahora mismo, está probando si tenés el .env expuesto. Todo lo que se dijo sobre secretos, hashes y no contar de más en el 500 deja de ser teoría en ese momento.

Y cambiar algo cuesta

Se acabó el npm run dev que recarga al guardar. Cada cambio es commit, push, build y arranque: dos o tres minutos, en los que la versión vieja sigue andando hasta que la nueva pasa el healthcheck.

Autoevaluación

Ponete a prueba

Respondé cada pregunta mentalmente y después tocá para revelar la respuesta y verificar.

1. En tu máquina la API arranca con npm run dev. ¿Por qué en el servidor no alcanza con eso?
Porque npm run dev usa tsx, que transpila TypeScript en memoria y lo ejecuta. En el servidor no hay tsx: hay node, y node no entiende TypeScript. Por eso el proyecto necesita npm run build (tsc compila src/ a dist/) y npm start (node dist/server.js). Hay un efecto secundario que conviene tener presente: tsx no chequea tipos, así que un proyecto puede venir andando semanas con npm run dev y romperse en el primer build.
2. ¿Por qué dist/ no se versiona en git?
Porque es una salida generada, no código fuente. Lo que se versiona es src/, y el build es un paso reproducible que el servidor vuelve a correr en cada deploy. Si commiteás dist/, tarde o temprano alguien toca un .ts, se olvida de recompilar, y lo que corre en producción deja de ser lo que dice el repositorio — con la particularidad de que nada lo avisa. Es la misma idea que las migraciones: se versiona el cambio, no el estado resultante.
3. Ponés npm ci --omit=dev && npm run build como comando de build y falla con Cannot find module 'typescript'. ¿Qué pasó?
Que TypeScript es una devDependency y --omit=dev justamente la saltea. El razonamiento de fondo ("en producción no necesito las herramientas de desarrollo") es correcto, pero el orden está al revés: el build es parte del desarrollo, no de la ejecución. Lo que corresponde es npm ci && npm run build, y recién después, si querés adelgazar, npm prune --omit=dev.
4. El deploy queda colgado y termina con No open ports detected, pero en tu máquina la API arranca perfecto. ¿Cuáles son las dos causas posibles?
Las dos tienen que ver con dónde estás escuchando, y las dos funcionan igual en tu máquina, que es lo que las hace difíciles de encontrar:
  • El puerto está fijo (app.listen(3000)). La plataforma te asigna un puerto por variable de entorno y hay que usar ese: Number(process.env.PORT) || 3000.
  • Estás escuchando en localhost en vez de 0.0.0.0. Adentro de un contenedor, localhost significa "solo desde adentro del contenedor", y el proxy de la plataforma queda del lado de afuera.
5. ¿Por qué el healthcheck no debería consultar la base de datos?
Porque el healthcheck responde "¿este proceso está vivo?", no "¿todo el sistema funciona?". Si consulta la base, un pico de carga hace que tarde, la plataforma te da por muerto y te reinicia justo cuando más tráfico tenías. Y si la base está caída de verdad, reiniciar la API no la arregla: solo agrega downtime a un problema que ya tenías. Las otras dos reglas: que no pida token (el que pregunta es un robot sin credenciales) y que no cuente nada (es una URL pública).
6. Venías usando orm.schema.update() al arrancar y funcionaba perfecto. ¿Qué tiene de peligroso contra la base de producción?
Que compara tus entidades con la base y genera el SQL para que se parezcan — sin preguntar. Cuando la diferencia es "sobra una columna", el SQL que genera es un DROP COLUMN. Renombrar un campo en una entidad (dos segundos de trabajo) borra la columna vieja con todos los datos que tenía adentro, y no hay Ctrl+Z. Mientras la base es tuya y está vacía no pasa nada; con datos de usuarios reales, no. La alternativa son las migraciones: cada cambio de esquema es un archivo versionado, revisable, y la tabla mikro_orm_migrations lleva la cuenta de cuáles se aplicaron en cada base.
7. El deploy dice Live, la URL contesta y el .http anda perfecto — pero el front sigue viendo un error de CORS. ¿Dónde está el problema?
En ningún lado: no hay nada roto. Falta el dominio del front en la variable CORS_ORIGIN, con https:// y sin barra final. Y el .http nunca lo iba a detectar, porque CORS no existe fuera del navegador: es una restricción que aplica el navegador, no el servidor. Es el error más frustrante del primer deploy justamente porque todas las señales dicen que está bien.
8. Al conectar con la base gestionada te tira un error de TLS, y la primera respuesta que encontrás es ssl: { rejectUnauthorized: false }. Hace desaparecer el error. ¿Por qué no conviene?
Porque desactiva justo la parte que importa. Con esa opción la conexión sigue cifrada, pero deja de verificar con quién está hablando: es TLS sin la garantía de TLS. Cualquiera que se meta en el medio puede presentarse como tu base y recibir las credenciales y los datos. Lo correcto es pasarle el certificado de la autoridad certificante que publica el proveedor: ssl: { ca: env.DB_SSL_CA, rejectUnauthorized: true }, con el certificado como variable de entorno para que no viaje en el repositorio.
Cierre

Resumen

  • Deployar no es reescribir la aplicación: es terminar de resolver lo que la aplicación daba por sentado. Entre el 9.3 y el 11.2, el código de negocio no cambia ni una línea.
  • Tres piezas: dónde corre el proceso, dónde viven los datos, de dónde sale la configuración. La tercera estaba resuelta desde la unidad 9.
  • En el servidor no hay tsx: hay node. npm run build compila src/ a dist/, y dist/ no se versiona — se genera en el servidor en cada deploy.
  • tsx no chequea tipos. Un proyecto puede andar tres semanas con npm run dev y romperse en el primer build. Por eso existe npm run check.
  • npm ci en el servidor, no npm install: instalación exacta desde el lock, y falla si no coincide. Y sin --omit=dev, porque el build necesita TypeScript.
  • Con TsMorphMetadataProvider hace falta "declaration": true: el ORM lee los tipos para armar el esquema, y en dist/ hay JavaScript.
  • El puerto sale de process.env.PORT y se escucha en 0.0.0.0. Las dos cosas funcionan igual en tu máquina y las dos rompen el deploy.
  • SIGTERM primero cierra el servidor, después la base. Al revés, los requests en curso contestan 500 durante el deploy.
  • El healthcheck responde por el proceso, no por sus dependencias: barato, sin token y sin contar nada.
  • El disco del contenedor es efímero: se borra en cada deploy. Por eso la base va afuera, y los archivos que suben los usuarios también.
  • Contra una base gestionada, TLS es obligatorio. rejectUnauthorized: false "arregla" el error y desactiva justo la garantía que da TLS.
  • schema.update() contra una base con datos genera DROP COLUMN sin preguntar. De acá en adelante, migraciones.
  • Fallá al arrancar y en voz alta. Una aplicación que no arranca es un problema de dos minutos; una que arranca mal, de dos horas.
  • El primer deploy siempre falla. La habilidad es leer el log, no acertar de una.
  • El auto-deploy publica aunque los tests estén rojos. needs en el workflow es lo que lo cierra.
  • El plan gratuito duerme el servicio a los 15 minutos. Entrar a la URL antes de la defensa.

El checklist de entrega

  1. La URL de la API contesta, y el .http del TP anda contra ella.
  2. El .env no está en el repositorio; el .env.example sí.
  3. El JWT_SECRET de producción es distinto al de desarrollo.
  4. Las migraciones están aplicadas en la base de la nube.
  5. CORS_ORIGIN tiene el dominio del front, con https:// y sin barra final.
  6. Hay un usuario admin, creado a mano en la base.
  7. Entrar a la URL diez minutos antes de mostrarla.

Lo que sigue

Se terminan las unidades. Lo que queda afuera, en orden de qué conviene aprender primero:

  • Docker. Es lo que hace que "anda en mi máquina" deje de ser un problema del todo: la aplicación viaja con su sistema operativo adentro. La cátedra tiene material y es el paso natural después de hoy.
  • Deployar el front. Otra cosa: archivos estáticos, sin proceso Node corriendo. Vercel, Netlify o Cloudflare Pages, en dos clics.
  • Observabilidad. Logs estructurados, métricas y alertas. Cuando el sistema tiene usuarios de verdad, enterarse de que algo se rompió por un mail y no por un mensaje de un usuario es la diferencia.
  • Ambientes. Una copia de producción donde probar antes. Es lo primero que se agrega en cualquier equipo.
  • Escalar. Varias instancias, balanceo, caché. No hace falta hasta que hace falta, y hace falta mucho más tarde de lo que uno cree.

Para profundizar

  • The Twelve-Factor App (12factor.net). Doce reglas para aplicaciones que se deployan, escritas en 2011 y todavía vigentes. Las de configuración, procesos y disposability son literalmente los bloques 3 y 4 de esta guía, mejor explicadas.
  • La documentación de Render, en particular las páginas de Environment Variables y Blueprints. Es corta y está bien escrita.
  • La página de deployment de MikroORM, para la alternativa del caché generado que evita necesitar ts-morph en producción.
  • Docker, cuando quieran que el deploy deje de depender de que la plataforma adivine cómo construir el proyecto.
  • Si alguien pregunta por AWS, Azure o GCP: son lo mismo con muchas más piezas y una factura. Lo que aprendieron hoy —puerto, configuración, healthcheck, migraciones— es exactamente lo que se necesita ahí también, con otros nombres.
