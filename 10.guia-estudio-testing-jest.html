Testing con Jest

Cómo saber que la API anda sin abrir el .http — Material de estudio

Prerequisito: la arquitectura en capas (unidad 6), TypeScript (unidad 7) y la API con autenticación (unidad 9)
Introducción

Contenidos de la guía

Esta es la unidad donde la arquitectura de la unidad 6 cobra por tercera vez. Separamos en capas para poder cambiar de base de datos (unidad 8) y para meter autenticación sin tocar el service (unidad 9). Acá se ve la razón por la que se separa en capas en primer lugar: un service que no sabe de dónde salen los datos se puede probar sin datos.

Una advertencia antes de empezar: el testing es fácil de convertir en ceremonia —escribir tests porque hay que escribirlos, y terminar con doscientos que no dicen nada—. Nada de lo que sigue tiene sentido como obligación moral. Tiene sentido por una razón concreta y egoísta: son lo que te deja tocar tu código sin miedo.

Bloque 1

¿Cómo sabemos que esto anda?

Abrí el productos.http del 9.3 y corrélo entero: listar, crear sin token, loguearte, crear con token, borrar el propio, borrar el ajeno, borrar uno que no existe. Siete requests, uno por uno, mirando cada respuesta.

Y después la pregunta: ¿cuánto tardaste? Dos, tres minutos. Segunda pregunta, la que importa: mañana tocás el service, ¿los corrés todos de nuevo?

Nadie los corre todos de nuevo. Corrés el que estabas tocando, y los otros seis quedan a la suerte.

Importante
Conviene decirlo explícito: ya venías testeando. Todo el cuatrimestre estuviste testeando. Lo que pasa es que lo hacías a mano, no queda registro, y depende de que alguien se acuerde. Acá no empezás a testear: empezás a automatizar lo que ya hacías.

Un test automatizado es solamente esto: código que ejecuta tu código y afirma qué tendría que haber pasado. Nada más. Si la afirmación se cumple, pasa; si no, falla y dice dónde.

Los tres niveles

Unitario
Una pieza sola, con todo lo demás de mentira. Milisegundos. Es el 90% de lo que vas a escribir y el foco de esta guía.
Integración
Varias piezas juntas: la ruta, el middleware, el controller y el errorHandler. Segundos. Es el ejemplo 10.4.
End-to-end
El sistema completo, con navegador y base de verdad. Minutos, y se rompen solos. Pocos y solo para los caminos críticos.
La regla práctica
Muchos abajo, pocos arriba. No porque los de arriba sean malos: porque cuestan caro de escribir y más caro de mantener.
Cuidado
Dónde termina "unitario" y empieza "integración" es una discusión de internet que no tiene respuesta y no vale tu tiempo. Si te preguntás si el 10.4 es unitario o de integración: no importa. Lo que importa es cuánto tarda y qué te dice cuando se pone rojo.
Bloque 2

El primer test: anatomía y matchers

Empecemos por lo más fácil que hay: una función que no depende de nada. Le entra un número, sale un número.

src/precios.ts
export function aplicarDescuento(precio: number, porcentaje: number): number {
  if (porcentaje < 0 || porcentaje > 100) {
    throw new RangeError('El descuento va de 0 a 100');
  }

  return precio - (precio * porcentaje) / 100;
}

Y su test:

src/precios.test.ts
import { describe, it, expect } from '@jest/globals';
import { aplicarDescuento } from './precios.js';

describe('aplicarDescuento', () => {
  it('descuenta el porcentaje indicado', () => {
    // ARRANGE — preparar
    const precio = 1000;
    const porcentaje = 20;

    // ACT — ejecutar UNA sola cosa
    const resultado = aplicarDescuento(precio, porcentaje);

    // ASSERT — afirmar
    expect(resultado).toBe(800);
  });
});

Tres piezas y ninguna más: describe agrupa, it es un test, expect es la afirmación. Y las tres partes de adentro son el patrón AAA (Arrange-Act-Assert), que no hace falta comentar porque se nota en la forma.

Importante
El nombre del test se lee en voz alta pegado al describe: "aplicarDescuento descuenta el porcentaje indicado". Si eso no suena a español, el test está mal nombrado; y si para que suene bien hace falta un "y" en el medio, el test está probando dos cosas y hay que partirlo. Es un truco tonto que ordena la mitad de los problemas de una suite.

El matcher del primer día

Este error lo vas a cometer, así que mejor provocarlo a propósito una vez y reconocerlo:

expect({ nombre: 'Mate', precio: 5000 }).toBe({ nombre: 'Mate', precio: 5000 });

Falla. Y el mensaje es memorable:

Expected: {"nombre": "Mate", "precio": 5000}
Received: serializes to the same string

"Se serializa igual" es Jest diciendo: el contenido es idéntico, pero me pediste identidad. toBe compara con Object.is, o sea que para objetos pregunta si son el mismo objeto en memoria. Es el paso por compartición de la unidad 4 volviendo a aparecer.

MatcherPara quéOjo con
toBenúmeros, strings, booleanosobjetos y arrays: casi nunca es lo que querés
toEqualobjetos y arrays, por contenidoignora las claves con undefined
toThrowque algo explotese le pasa una función, no el resultado
toHaveLengthlargo de un arraymejor mensaje que .length + toBe

El de toThrow merece atención aparte porque la forma es contraintuitiva:

// MAL: el error explota antes de que expect llegue a existir
expect(aplicarDescuento(1000, -5)).toThrow();

// BIEN: se le pasa la función SIN ejecutar, para que la ejecute Jest
expect(() => aplicarDescuento(1000, -5)).toThrow(RangeError);
Dato
Esa función que se pasa sin ejecutar es una función de orden superior de la unidad 2, exactamente igual que el callback de forEach. Es el mismo mecanismo —"te paso la función para que la llames vos"— y acá sirve para que quien la llame pueda envolverla en un try.

Muchos datos, un solo test

it.each([
  [1000, 1210],
  [100, 121],
  [0, 0],
  [1999.99, 2419.99],   // el redondeo: sin él daría 2419.9879
])('a $%s le suma IVA y da $%s', (precio, esperado) => {
  expect(precioConIva(precio)).toBe(esperado);
});

Cuando cambian los datos y no la lógica del test, repetir el it es ruido. Y si falla la tercera fila, Jest dice cuál falló.

Bloque 3

El peaje: Jest con ESM y TypeScript

Jest nació en el mundo de require y nosotros venimos escribiendo ESM + TypeScript desde la unidad 7. Eso cuesta cuatro líneas de configuración, y las cuatro tienen motivo.

jest.config.js
export default {
  // Jest no entiende TypeScript: ts-jest transforma los .ts antes de
  // ejecutarlos. La variante "-esm" respeta "type": "module".
  preset: 'ts-jest/presets/default-esm',

  testEnvironment: 'node',

  // Nuestros imports dicen './precios.js' y el archivo es .ts. Jest lee sin
  // compilar y busca un .js que todavía no existe.
  moduleNameMapper: {
    '^(\\.{1,2}/.*)\\.js$': '$1',
  },
};

Más una en tsconfig.json ("isolatedModules": true, porque ts-jest transpila archivo por archivo) y una en el script de npm:

package.json
"test": "node --experimental-vm-modules node_modules/jest/bin/jest.js"
Cuidado
La documentación de Jest dice NODE_OPTIONS=--experimental-vm-modules jest. Esa forma es sintaxis de shell de Unix y falla en la terminal de Windows: es literalmente la razón por la que a la mitad del curso no le arranca. La versión de arriba hace lo mismo y funciona en los tres sistemas: copiá esa.

Los cuatro errores del primer día

El mensajeQué falta
Cannot find module './precios.js'el moduleNameMapper, o le falta una barra invertida
Cannot use import statement outside a moduleel preset ESM, el "type": "module" o la bandera de Node
describe is not definedel import de @jest/globals
el test pasa y no deberíaun async sin await

El último es el peligroso, porque no se ve. Un test que devuelve una promesa que nadie espera termina antes que la afirmación, y Jest lo da por bueno.

Dato
Usamos import { describe, it, expect } from '@jest/globals' y no las variables globales que Jest inyecta. En JavaScript las globales funcionan igual; en TypeScript, sin ese import haría falta @types/jest para que el compilador sepa qué es describe. Un import explícito es una dependencia menos. Si copiás de un tutorial y no aparece el import, es por eso.
Bloque 4

El problema: el service agarra su repository

Lo anterior era fácil porque aplicarDescuento no depende de nada. Ahora abrí el service de productos del 9.3, que es lo que de verdad querés testear:

9.3-api-auth/src/services/productos.service.ts
import * as repo from '../repositories/productos.repository.js';

export async function crearProducto(datos, autor) {
  const existente = await repo.findByNombre(datos.nombre);

  if (existente) {
    throw new ValidationError(`Ya existe un producto llamado "${datos.nombre}"`);
  }

  return repo.guardar(datos, Number(autor.sub));
}

Y ahí está el problema, en la primera línea. Ese repo va a MySQL. Para testear crearProducto tal como está haría falta:

  1. Un MySQL andando. En tu máquina, en la de cada compañero, y en el servidor donde corran los tests.
  2. Datos conocidos adentro, porque el test necesita saber qué hay antes de empezar.
  3. Limpiar la base entre test y test, o el segundo test ve lo que dejó el primero.
  4. Que nadie más esté usando esa base al mismo tiempo.

Un test así es lento (segundos en vez de milisegundos), frágil (falla porque el MySQL no arrancó, no porque el código esté mal) y no determinista (pasa o no según lo que haya quedado de la corrida anterior).

Importante
Un test que falla por motivos que no son el código es peor que no tener test. Enseña a ignorar el rojo. Después de la tercera vez que la suite falla por la base, la gente corre los tests y sigue de largo sin mirar — y ahí el test ya no sirve para nada, pero da la sensación de que el proyecto está cubierto.

Lo que queremos

El service no necesita MySQL: necesita que alguien le conteste cuando pregunta si existe un producto con ese nombre. Si en vez de la base le contesta un objeto que dice "no, no hay ninguno", el service no puede notar la diferencia.

Eso es un doble de prueba: algo que ocupa el lugar de una dependencia real durante el test. Como el doble de riesgo en una película — se viste igual, hace la escena, y no es el actor.

NombreQué hace
StubContesta lo que le dijiste que conteste. Nada más.
SpyAdemás anota cómo lo llamaron, para poder revisarlo después.
FakeTiene una implementación de verdad, pero simplificada (un array en vez de MySQL).
MockEn la literatura, uno con expectativas adentro. En la práctica, todo el mundo le dice "mock" a cualquiera de los anteriores.
Cuidado
No te pelees con la taxonomía. Los cuatro nombres tienen definiciones precisas que nadie respeta, y discutirlas gasta tiempo sin agregar nada. Lo que sí importa distinguir son los dos usos: preparar la respuesta (para poner al service en la situación que querés probar) y verificar la llamada (porque hablar con el repository también es parte de lo que el service tiene que hacer). Eso sí cambia cómo se escribe el test.
Bloque 5

Inyectar la dependencia

La respuesta es más simple de lo que parece: que el service no elija. Que reciba el repository desde afuera.

Antes (9.3)
import * as repo from '../repositories/productos.repository.js';

export async function crearProducto(datos, autor) {
  const existente = await repo.findByNombre(...);
  // ...
}
Después (10.2)
export function crearProductosService(repo: ProductosRepository) {
  return {
    async crear(datos, autor) {
      const existente = await repo.findByNombre(...);
      // ...
    },
  };
}

El cuerpo de la función es idéntico. Lo único que cambió es de dónde sale repo: antes lo agarraba solo, ahora se lo dan.

Y el contrato es un tipo, no una clase ni nada ceremonioso:

export type ProductosRepository = {
  findAll(): Promise<Producto[]>;
  findByNombre(nombre: string): Promise<Producto | null>;
  findById(id: number): Promise<Producto | null>;
  guardar(datos: ProductoNuevo, creadoPorId: number): Promise<Producto>;
  eliminar(producto: Producto): Promise<void>;
};

Cinco firmas. No dice MySQL, no dice MikroORM, no dice nada de cómo se guardan las cosas. Y un tipo así lo puede cumplir un objeto de mentira escrito en tres líneas.

El repository falso

const repo = {
  findAll: jest.fn<ProductosRepository['findAll']>(),
  findByNombre: jest.fn<ProductosRepository['findByNombre']>(),
  findById: jest.fn<ProductosRepository['findById']>(),
  guardar: jest.fn<ProductosRepository['guardar']>(),
  eliminar: jest.fn<ProductosRepository['eliminar']>(),
};

const service = crearProductosService(repo);

jest.fn() devuelve una función que no hace nada pero que anota: con qué argumentos la llamaron, cuántas veces, qué devolvió. Y se le puede decir qué contestar.

Con eso, el test entero:

it('guarda el producto cuando el nombre está libre', async () => {
  repo.findByNombre.mockResolvedValue(null);
  repo.guardar.mockResolvedValue(mate);

  const creado = await service.crear({ nombre: 'Mate', precio: 5000 }, juan);

  expect(creado).toEqual(mate);
});

Sin MySQL, sin servidor, sin token de verdad. Milisegundos.

Importante
El parámetro de tipo del jest.fn<...>() no es adorno: hace que TypeScript verifique que lo que le mandás contestar tenga la forma correcta. Si mañana el repository cambia su firma, el archivo de tests deja de compilar y te enterás antes de correr nada. Es la unidad 7 trabajando para la 10, y es la ventaja grande de este camino sobre el del bloque 6.

Dónde se juntan las piezas

En producción alguien tiene que pasarle el repository de verdad. Ese lugar es uno solo y se llama composition root:

src/main.ts
const service = crearProductosService(productosRepository);

Una línea. Es el único archivo de la aplicación que sabe cuál es el repository "de verdad".

Importante
Esto es lo que quiere decir "lo difícil de testear no es el test, es el código". No inventamos una técnica de testing: desacoplamos el código, y el test salió gratis. El test es el segundo cliente que tiene tu service, y un segundo cliente siempre encuentra las suposiciones que el primero dejaba pasar.
Cuidado
No es gratis, y conviene saberlo para no volverse fanático: inyectar todo lleva a fábricas de fábricas y a un composition root ilegible. La regla razonable es inyectar lo que cruza el borde de tu aplicación —base de datos, red, reloj, sistema de archivos— y nada más. Una función de utilidad que suma precios se importa y listo.
Bloque 6

El otro camino: mockear el módulo

Lo anterior pide tocar el código de producción. Con el TP ya escrito, la pregunta llega sola: ¿y si no puedo?

Se puede igual. En vez de cambiar el service para que reciba otro repository, se le cambia el repository por debajo: cuando pida ese módulo, Jest le entrega otro.

// 1. El módulo falso: las mismas claves que exporta el original.
const repo = {
  findById: jest.fn<typeof RepoModule.findById>(),
  // ...
};

// 2. Registrarlo.
jest.unstable_mockModule('../repositories/productos.repository.js', () => repo);

// 3. RECIÉN AHORA importar el service. Dinámico, nunca arriba del archivo.
const { crearProducto } = await import('./productos.service.js');

El paso 3 es el que sorprende, y la explicación vale porque es la misma razón por la que ESM se comporta distinto en todo lo demás.

En CommonJS, jest.mock() se hoistea: Jest reescribe el archivo al compilarlo y sube esa llamada arriba de todos los require. Por eso en los tutoriales aparece en el medio del archivo y anda igual.

En ESM eso es imposible. Los import se resuelven antes de que corra la primera línea del archivo — es parte de la definición del formato. Si el service estuviera importado arriba con un import normal, ya se habría cargado con el repository de verdad y el mock llegaría tarde.

Cuidado
Si copiás jest.mock() de un tutorial, en un proyecto ESM no intercepta nada y no avisa: sin error, sin warning. El test corre contra el repository de verdad, que en el 9.3 significa contra MySQL. El síntoma es un connect ECONNREFUSED 127.0.0.1:3306 en un test que "estaba mockeado". Cuando veas eso, el problema no es la base: es que el mock nunca se aplicó.

Los dos caminos, comparados

Inyección (10.2)Mock de módulo (10.3)
Código de producciónhay que cambiarloqueda igual
El testse lee solotres pasos, y el orden importa
Si cambia la firma del repono compila: te enteráscompila, y el mock queda mintiendo

Importante
La fila que más duele en la práctica es la tercera. Un mock de módulo puede quedar desactualizado en silencio: si el repository real pasa a devolver otra cosa, el falso sigue devolviendo lo de antes, los tests siguen verdes y la aplicación está rota. Es la peor combinación posible — el test no solo no encuentra el bug, sino que da confianza de que no lo hay.
Dato
El prefijo unstable_ es del propio Jest y significa que la API puede cambiar. Está así desde 2021 y es la forma oficial de mockear módulos ESM. Que el nombre incomode viene bien: el 10.2 es el camino recomendado y este es la salida de emergencia.
Bloque 7

Los tests como documentación de las reglas

Hasta acá los tests fueron una red de seguridad. Falta la otra mitad, que es la que convence a los escépticos. Volvamos a la regla de autorización de la unidad 9:

"Solo el que lo creó, o un admin, puede borrar un producto."

Eso hoy vive en un comentario y en la cabeza de quien lo escribió. Como tests, vive así:

describe('eliminar', () => {
  it('deja borrar al dueño', async () => { /* ... */ });
  it('deja borrar a un admin aunque no sea el dueño', async () => { /* ... */ });
  it('no deja borrar el producto de otro', async () => { /* ... */ });
  it('avisa que no existe', async () => { /* ... */ });
  it('contesta 404 y no 403 cuando el producto no existe', async () => { /* ... */ });
});
Idea central
Leídos de corrido, esos cinco nombres son la especificación de la regla. Y es la única forma de documentación que no puede quedar desactualizada: si algún día miente, se pone roja. Un comentario que miente se queda ahí durante años.

Los errores esperados

it('no deja borrar el producto de otro', async () => {
  repo.findById.mockResolvedValue(mate);   // mate es de juan (7)

  await expect(service.eliminar(1, ana)).rejects.toThrow(ForbiddenError);
  expect(repo.eliminar).not.toHaveBeenCalled();
});

Dos cosas nuevas y las dos importan:

rejects es para promesas que tienen que fallar. Y el await de adelante no es opcional: sin él el test pasa siempre, porque termina antes de que la promesa se resuelva. Es el error más silencioso de toda la unidad.

El segundo expect es el que suele faltar. Un error tirado a tiempo también significa no hacer lo que seguía. Verificar que el borrado no ocurrió es la mitad importante de la regla.

El test que vale doble

it('usa como dueño el id del token, no lo que venga en los datos', async () => {
  repo.findByNombre.mockResolvedValue(null);
  repo.guardar.mockResolvedValue(mate);

  await service.crear({ nombre: 'Mate', precio: 5000 }, juan);

  expect(repo.guardar).toHaveBeenCalledWith({ nombre: 'Mate', precio: 5000 }, 7);
});

Este test es la regla de seguridad de la unidad 9 —lo que decide permisos no se le pregunta al cliente— convertida en código ejecutable. Si alguien "arregla" el service para tomar el dueño del body, el test del camino feliz sigue verde y este se pone rojo.

El detalle que arruina suites enteras

beforeEach(() => {
  jest.clearAllMocks();
});

Sin eso, un test ve las llamadas del anterior y toHaveBeenCalledTimes empieza a contar de más. Produce el bug más desconcertante que hay: la suite entera pasa, pero un test solo falla. O al revés, que es peor.

Cuidado
La regla general es que ningún test puede depender de otro, ni del orden en que corren. Jest de hecho corre los archivos en paralelo y en orden variable, así que un test que dependa del anterior va a fallar en la máquina de otro y no en la tuya. Si dos tests necesitan compartir preparación, va en beforeEach, nunca en el cuerpo del primero.
Bloque 8

Cobertura, y qué NO testear

Jest mide qué líneas de tu código se ejecutaron durante los tests. Sobre los once tests de integración del 10.4:

File                      | % Stmts | % Branch | % Funcs | % Lines | Uncovered
--------------------------|---------|----------|---------|---------|----------
All files                 |   94.23 |    91.66 |     100 |   94.23 |
  app.ts                  |     100 |      100 |     100 |     100 |
  productos.controller.ts |   93.33 |      100 |     100 |   93.33 | 12
  autenticar.ts           |     100 |      100 |     100 |     100 |
  productos.routes.ts     |     100 |      100 |     100 |     100 |
  errorHandler.ts         |   86.66 |     87.5 |     100 |   86.66 | 44-45

94% suena a mucho. Hay dos lecturas y la segunda es la que importa.

Las líneas que faltan son las correctas. La 44-45 del errorHandler es la rama del 500, el error que no reconocemos. Provocarla adrede pide fabricar un fallo inesperado y como test aporta poco. Saber cuál es el 6% que falta vale mucho más que el 94.

Y faltan archivos enteros. No están productos.service.ts, ni productos.repository.ts, ni server.ts: Jest solo mide los archivos que los tests importaron. Un archivo sin un solo test no baja el porcentaje — directamente no aparece.

Idea central
La cobertura mide qué código se ejecutó, no qué código se verificó. Este test da 100% de cobertura de una ruta y no comprueba absolutamente nada: 
it('anda', async () => {
  await request(app).get('/api/productos');
});
Sirve para encontrar lo que no probaste, leyendo la columna de líneas descubiertas. Como nota, se manipula sin esfuerzo.

Qué no testear

NoPor qué
Getters y setters trivialesSi se rompen, se rompe todo lo demás y ya te enteraste.
Librerías de tercerosQue Express rutee bien no es tu problema. Ya tiene sus tests.
La configuraciónQue el .env se lea se ve al arrancar la aplicación.
Los detalles internosUn test atado a cómo está hecho algo se rompe con cada refactor sin que nada esté mal.

Qué sí

  1. Las reglas de negocio. Todo lo que tenga un "solo si", un "salvo que" o un "no puede".
  2. Los casos borde. El vacío, el cero, el límite, el negativo, el que no existe.
  3. Los bugs que ya encontraste. Primero el test que lo reproduce, después el arreglo. Así ese bug no vuelve nunca: se llama test de regresión y es el que más rinde de todos.
  4. Lo que te da miedo tocar. Literalmente. El miedo es una medida bastante buena de dónde hacen falta.
Importante
El .http no se tira. Sigue siendo la mejor herramienta para explorar mientras escribís código nuevo. Lo que cambia después de hoy es que deja de ser la única prueba de que la API anda.
Lo que sigue
La última unidad es deploy: poner la API en internet. Y ahí los tests cobran una vez más — el lugar donde de verdad se paga tener una suite es en el servidor que, antes de publicar una versión nueva, corre npm test y se niega a subirla si algo está en rojo.
Autoevaluación

Ponete a prueba

Respondé cada pregunta mentalmente y después tocá para revelar la respuesta y verificar.

1. ¿Por qué es un problema que un test necesite MySQL andando, si al final prueba lo mismo?
Porque es lento (segundos en vez de milisegundos), frágil (falla porque la base no arrancó, no porque tu código esté mal) y no determinista (pasa o no según lo que haya quedado de la corrida anterior). Y hay una consecuencia peor: un test que falla por motivos que no son el código te enseña a ignorar el rojo. Después de la tercera vez, corrés la suite y seguís de largo sin mirar.
2. Comparás el producto que devolvió el service con { id: 1, nombre: 'Mate' } y el test falla diciendo "serializes to the same string". ¿Qué pasó?
Usaste toBe con un objeto. toBe compara con Object.is: para objetos pregunta si son el mismo objeto en memoria, y dos objetos idénticos escritos en dos lugares distintos no lo son (es el paso por compartición de la unidad 4). El mensaje es Jest diciéndote "el contenido es idéntico, pero me pediste identidad". Querías toEqual.
3. ¿Qué hay que cambiarle al service del 9.3 para poder testearlo sin base de datos?
Que reciba el repository por parámetro en vez de importarlo. El cuerpo de las funciones no cambia en nada: lo único distinto es de dónde sale repo. Con eso, en producción se le pasa el repository de MySQL y en el test un objeto de mentira, y el service no puede notar la diferencia porque nunca eligió.
4. Copiaste jest.mock() de un tutorial y el test falla con connect ECONNREFUSED 127.0.0.1:3306. ¿Cuál es el problema?
Que el mock nunca se aplicó: en un proyecto ESM, jest.mock() no intercepta nada — y no avisa, no tira error ni warning. Tu test está corriendo contra el repository de verdad. En ESM los import se resuelven antes de que corra la primera línea, así que no existe el hoisting de CommonJS: va jest.unstable_mockModule() y después await import() del service, en ese orden.
5. ¿Por qué await expect(service.eliminar(1, ana)).rejects.toThrow() necesita el await de adelante?
Porque sin él el test pasa siempre. La afirmación devuelve una promesa; si nadie la espera, el test termina antes de que se resuelva y Jest lo da por bueno. Es el error más silencioso de la unidad: no te da un test roto, te da un test que miente. La misma regla aplica a cualquier it asincrónico.
6. Tu test verifica que crear devuelve el producto esperado. ¿Qué bug de la unidad 9 no atrapa, y cómo se atrapa?
No atrapa que el dueño salga del body en vez del token. Si alguien cambia el service para tomar el creadoPorId de lo que manda el cliente, crear sigue devolviendo un producto y tu test sigue verde — con un agujero de seguridad adentro. Se atrapa verificando la llamada y no solo el resultado: expect(repo.guardar).toHaveBeenCalledWith(datos, 7).
7. Tenés 100% de cobertura. ¿Qué significa exactamente, y qué no?
Significa que todas las líneas se ejecutaron durante los tests. No significa que se hayan verificado: un it que llama a la función y no tiene ni un expect suma cobertura igual. Además Jest solo mide los archivos que los tests importaron, así que un archivo sin ningún test no baja el porcentaje — directamente no aparece en la tabla. Sirve para encontrar lo que no probaste, leyendo qué líneas quedaron afuera; como nota se manipula sin esfuerzo.
8. ¿Para qué está el jest.clearAllMocks() en el beforeEach?
Para que cada test arranque de cero. Los jest.fn() acumulan las llamadas que recibieron, así que sin eso un test ve las del anterior y toHaveBeenCalledTimes empieza a contar de más. Produce el bug más desconcertante que hay: la suite entera pasa pero un test solo falla, o al revés. La regla general es que ningún test puede depender de otro ni del orden en que corren.
Cierre

Resumen

  • Un test automatizado es código que ejecuta tu código y afirma qué tenía que pasar. Ya testeábamos a mano con el .http; hoy lo automatizamos.
  • El argumento no es moral: los tests son lo que te deja cambiar el código sin miedo.
  • describe agrupa, it es un test, expect afirma. Adentro, AAA: preparar, ejecutar una sola cosa, afirmar.
  • toBe para números y strings; toEqual para objetos y arrays. "Serializes to the same string" es Jest diciendo que querías toEqual.
  • Los casos borde son los que encuentran bugs: el vacío, el cero, el límite, el que no existe.
  • Jest con ESM y TypeScript pide cuatro líneas de configuración. Es andamiaje: se copia del 10.1 y se sigue.
  • Un test que necesita MySQL es lento, frágil y no determinista. Y un test que falla por motivos que no son el código enseña a ignorar el rojo.
  • Inyectar la dependencia —que el service reciba el repository en vez de importarlo— es todo el truco. El cuerpo del service no cambia.
  • El contrato es un tipo con cinco firmas, y un objeto de mentira lo cumple en tres líneas. Los tipos de la unidad 7 avisan si el falso se desactualiza.
  • En ESM, jest.mock() no funciona y no avisa. La forma es unstable_mockModule + await import(), en ese orden, porque el hoisting de CommonJS no existe acá.
  • Los tests son la documentación de las reglas de negocio que no puede mentir: si miente, se pone roja.
  • Verificar la llamada (toHaveBeenCalledWith) atrapa cosas que verificar el resultado no ve — como que el dueño salga del token y no del body.
  • Para promesas que fallan: await expect(...).rejects.toThrow(). Sin el await, el test pasa siempre.
  • jest.clearAllMocks() en un beforeEach. Ningún test puede depender de otro ni del orden.
  • La cobertura mide qué se ejecutó, no qué se verificó. Sirve para encontrar lo que falta, no como nota.
  • Lo que más rinde: reglas de negocio, casos borde, los bugs que ya aparecieron, y lo que te da miedo tocar.

Lo que sigue

Queda una sola unidad: deploy. La API tiene capas, tipos, base de datos, usuarios y ahora tests — le falta estar en internet. Y ahí los tests aparecen por última vez, en el lugar donde de verdad se pagan solos: el servidor que corre npm test antes de publicar y se niega a subir una versión rota.

Para profundizar

  • La documentación de Jest, en particular la lista de matchers y la página de ECMAScript Modules. Es buena y corta.
  • Working Effectively with Legacy Code, de Michael Feathers, para el capítulo sobre "costuras" (seams): es la idea del bloque 5 explicada quince años antes de que existiera Jest.
  • El artículo Mocks Aren't Stubs, de Martin Fowler, si alguien quiere la taxonomía completa de dobles de prueba.
  • Vitest: la alternativa moderna a Jest. API casi idéntica y soporte de ESM y TypeScript sin nada de la configuración del bloque 3. Vale tenerla en el radar: si arrancás un proyecto nuevo el año que viene, es probable que uses esa.
  • Sobre TDD (escribir el test antes que el código): es una disciplina que se aprende mejor una vez que testear ya no cuesta. El orden de esta materia es a propósito.
