Bloque 1

El bug que JavaScript no ve

Arrancamos por donde duele. Este es el service de productos de la clase de arquitecturas, tal cual quedó, en JavaScript:

productos.service.js — la versión que ya tenés
export async function crearProducto(datos) {
  if (!datos.nombre || datos.precio <= 0) {
    throw new ValidationError('Datos inválidos');
  }
  return repo.guardar(datos);
}

Funciona. Ahora, tres cosas que pueden pasar un martes cualquiera:

  1. Alguien escribe datos.precioo por error de tipeo. En JavaScript eso vale undefined, undefined <= 0 es false, la validación pasa y el producto se guarda sin precio.
  2. Llega un body con { "precio": "15000" } — el precio como string. "15000" <= 0 también es false: pasa. Tres pantallas después, precio + envio devuelve "1500010".
  3. El repository cambia de guardar(datos) a guardar(datos, usuario). Hay ocho lugares que lo llaman; se actualizan siete. El octavo se descubre en producción.

Los tres son el mismo problema con distinta ropa: en JavaScript el error existe desde que se escribe, pero recién se manifiesta cuando el código corre — y solo si esa línea llega a ejecutarse con esos datos. Escribamos ese mismo service en TypeScript:

productos.service.ts
export interface ProductoNuevo {
  nombre: string;
  precio: number;
}

export async function crearProducto(datos: ProductoNuevo): Promise<Producto> {
  if (!datos.nombre || datos.precioo <= 0) {
    //                     ^^^^^^^^
    // Error: Property 'precioo' does not exist on type 'ProductoNuevo'.
    //        Did you mean 'precio'?
    throw new ValidationError('Datos inválidos');
  }
  return repo.guardar(datos);
}

El caso 1 y el caso 3 dejan de ser bugs de producción y pasan a ser subrayados rojos en el editor, antes de guardar el archivo. Ese es todo el negocio de TypeScript: correr el error para adelante en el tiempo.

Cuidado
El caso 2 —el precio que llega como string desde el body— TypeScript no lo detecta. Y no es un defecto: los tipos son una promesa sobre el código que vos escribís, y el body lo escribe el que consume tu API. Ese hueco es real y lo tapa el bloque 7, con Zod. Tenerlo presente desde ahora evita la ilusión de que "con TypeScript ya está validado".
Importante
TypeScript no cambia lo que corre: lo que corre sigue siendo JavaScript. Lo que cambia es cuándo te enterás del error — al escribir en vez de al ejecutar. Es la misma idea que las capas de la clase anterior: no agrega poder, agrega orden y garantías.
Bloque 2

TypeScript no se ejecuta: se compila

Antes de escribir un tipo, hay que entender el flujo, porque es la fuente número uno de confusión del primer día: Node no sabe qué es un archivo .ts. TypeScript es un compilador que toma .ts y produce .js; lo que Node ejecuta es siempre ese .js.

  1. Escribís src/app.ts con tipos.
  2. tsc chequea los tipos. Si hay errores, avisa.
  3. tsc borra los tipos y emite dist/app.js — JavaScript común y corriente.
  4. node dist/app.js corre. En tiempo de ejecución, de TypeScript no queda nada.

Borrado de tipos, en concreto

src/precio.ts (lo que escribís)
export function conIva(precio: number): number {
  return precio * 1.21;
}
dist/precio.js (lo que corre)
export function conIva(precio) {
  return precio * 1.21;
}

Idéntico, menos los tipos. Esto se llama type erasure (borrado de tipos) y explica de una vez tres cosas: por qué TypeScript no hace más lento el programa, por qué no puede validar lo que llega de afuera en tiempo de ejecución, y por qué cualquier archivo .js que ya funciona es también un archivo TypeScript válido.

Armar el proyecto desde cero

terminal
# el compilador y los tipos de Node, siempre como dependencias de desarrollo
npm install --save-dev typescript @types/node

# genera el tsconfig.json con comentarios
npx tsc --init

# ejecuta .ts directo en desarrollo, sin compilar a mano
npm install --save-dev tsx

typescript va en devDependencies porque en producción no se compila: se ejecuta el dist/ ya compilado. @types/node es lo que le enseña a TypeScript qué son process, console o el módulo fs — el propio Node no viene tipado.

tsconfig.json — lo mínimo que hay que entender
{
  "compilerOptions": {
    "target": "ES2022",        // a qué versión de JS compila
    "module": "NodeNext",     // sistema de módulos (ESM de Node)
    "moduleResolution": "NodeNext",
    "rootDir": "./src",       // dónde está el código fuente .ts
    "outDir": "./dist",       // dónde deja el .js compilado
    "strict": true,           // TODAS las verificaciones estrictas
    "esModuleInterop": true,  // import express from 'express' funciona
    "skipLibCheck": true      // no chequea adentro de node_modules
  },
  "include": ["src/**/*"]
}

De todas, la que importa es "strict": true. Sin ella, TypeScript acepta variables sin tipo y no controla null/undefined: queda un JavaScript con adornos. Proyecto nuevo, siempre en strict.

package.json (fragmento)
{
  "type": "module",
  "scripts": {
    "dev": "tsx watch src/app.ts",   // desarrollo: ejecuta .ts y recarga
    "build": "tsc",                  // compila src/ -> dist/
    "start": "node dist/app.js",    // producción: corre lo compilado
    "check": "tsc --noEmit"         // solo chequea tipos, no emite nada
  }
}

Es el mismo package.json de la unidad de Express con dos cambios: nodemon lo reemplaza tsx watch (que además compila en memoria), y aparece un paso de build que antes no existía.

Cuidado
Con "module": "NodeNext", los imports relativos llevan la extensión .js aunque el archivo que estás importando sea .ts: import { productosRouter } from './routes/productos.routes.js'. No es un error ni un typo. El import lo resuelve Node en tiempo de ejecución, cuando ese archivo ya se compiló a .js; TypeScript nunca reescribe la ruta. Es lo que más desconcierta el primer día.
Dato
tsc --noEmit chequea tipos sin generar archivos. Es el comando que corre un pipeline de integración continua, y el que conviene tener a mano cuando el editor marca todo en verde pero algo no cierra.
Bloque 3

Tipos, inferencia y strict

La sintaxis es una sola cosa: dos puntos y el tipo, después del nombre.

7.1.1-tiposBasicos.ts
let nombre: string = 'Teclado';
let precio: number = 25000;
let disponible: boolean = true;

precio = 'muy caro';
// Error: Type 'string' is not assignable to type 'number'.

Inferencia: no anotes lo que TypeScript ya sabe

Este es el primer reflejo a corregir. TypeScript deduce el tipo del valor inicial, así que anotar de más es ruido:

Ruidoso
const nombre: string = 'Teclado';
const precios: number[] = [100, 200];
Idiomático
const nombre = 'Teclado';   // string
const precios = [100, 200]; // number[]

La regla práctica: anotá en los bordes —parámetros de funciones, valores de retorno, datos que entran al sistema— y dejá que la inferencia se ocupe de las variables locales. En un editor, pasar el mouse por encima de una variable muestra el tipo inferido; ese es el modo de verificar sin anotar.

Arrays y objetos

const nombres: string[] = ['Teclado', 'Mouse'];
const matriz: number[][] = [[1, 2], [3, 4]];

// el tipo de un objeto es su forma
const producto: { nombre: string; precio: number } = {
  nombre: 'Teclado',
  precio: 25000,
};

Uniones y tipos literales

Acá TypeScript empieza a hacer cosas que otros lenguajes no: un valor puede ser uno de varios tipos, y hasta uno de varios valores concretos.

let id: number | string;        // unión de tipos
id = 1;        // ok
id = 'abc';    // ok

type Estado = 'activo' | 'pausado' | 'borrado';  // unión de literales

let estado: Estado = 'activo';
estado = 'Activo';
// Error: Type '"Activo"' is not assignable to type 'Estado'.

Las uniones de literales reemplazan a los strings mágicos desperdigados por el código: el editor autocompleta los tres valores posibles y cualquier otro es error de compilación. Es de las cosas que más rápido se extrañan al volver a JavaScript.

Estrechar el tipo: typeof vuelve a aparecer

Si un valor puede ser de dos tipos, TypeScript solo deja hacer lo que sirva para ambos. Para usar lo específico de uno, hay que estrecharlo (narrowing) — y se hace con el mismo typeof de la unidad de sintaxis básica:

function formatearId(id: number | string): string {
  if (typeof id === 'string') {
    return id.toUpperCase();  // acá TS sabe que es string
  }
  return `#` + id.toFixed(0);   // y acá, que es number
}
Importante
El if (typeof …) no es solo una guarda en ejecución: el compilador lo lee y ajusta el tipo adentro de cada rama. Es el mismo código defensivo que ya escribías en JavaScript, pero ahora el editor lo entiende y te autocompleta los métodos correctos en cada bloque.

any y unknown: la puerta de atrás y la puerta con llave

let a: any = JSON.parse(texto);
a.loQueSea().tampocoImporta;   // compila. Y explota en ejecución.

let u: unknown = JSON.parse(texto);
u.loQueSea();
// Error: 'u' is of type 'unknown'.

if (typeof u === 'object' && u !== null && 'nombre' in u) {
  // recién acá TS deja tocarlo
}

any apaga TypeScript para ese valor: todo compila y no queda ninguna garantía. unknown dice lo mismo —"no sé qué es"— pero obliga a chequear antes de usar. Cuando de verdad no se sabe el tipo (un JSON.parse, un body, una respuesta de fetch), unknown es la opción correcta.

Cuidado
any es contagioso: todo lo que sale de un any también es any. Un any puesto para "salir del paso" en el repository puede dejar sin chequear media aplicación, y encima en silencio. Está bien usarlo como deuda temporal durante una migración; no está bien que sea la solución por defecto cuando el compilador molesta.

Qué prende strict, en la práctica

// sin strict: 'nombre' es any implícito, nadie avisa nada
function saludar(nombre) { return 'Hola ' + nombre; }
// con strict → Error: Parameter 'nombre' implicitly has an 'any' type.

const encontrado = productos.find((p) => p.id === 1);
console.log(encontrado.nombre);
// con strict → Error: 'encontrado' is possibly 'undefined'.

Ese segundo error es el que más bronca da al principio y el que más bugs evita: find puede no encontrar nada, y en JavaScript eso es un TypeError en producción. La solución no es apagar strict, es contemplar el caso:

if (!encontrado) {
  throw new NotFoundError('Producto no encontrado');
}
console.log(encontrado.nombre);  // ahora TS sabe que existe
Bloque 4

Funciones tipadas

En una función se tipan dos cosas: los parámetros y lo que devuelve.

7.1.2-funciones.ts
function conIva(precio: number): number {
  return precio * 1.21;
}

// parámetro opcional (?) y valor por defecto
function formatearPrecio(precio: number, moneda: string = '$'): string {
  return `${moneda}${precio.toFixed(2)}`;
}

// no devuelve nada: void
function logProducto(nombre: string): void {
  console.log('[producto] ' + nombre);
}

// arrow: misma idea
const duplicar = (n: number): number => n * 2;

El tipo de retorno se puede omitir (TypeScript lo infiere), pero en las funciones exportadas conviene escribirlo: es documentación, y si un día el cuerpo devuelve otra cosa por accidente, el error aparece en la función y no tres archivos más allá.

Tipar una función que recibe otra función

Acá vuelve, tipado, el ejemplo de funciones de orden superior de la unidad de funciones. El tipo de una función se escribe con la misma flecha que la arrow function: (n: number) => number se lee "recibe un number y devuelve un number".

// 2.7 de la unidad de funciones, ahora tipado
function procesarArreglo(
  arreglo: number[],
  operacion: (n: number) => number
): number[] {
  return arreglo.map(operacion);
}

procesarArreglo([1, 2, 3], duplicar);           // [2, 4, 6]
procesarArreglo([1, 2, 3], (n) => n * n);      // [1, 4, 9]

procesarArreglo([1, 2], (n) => 'valor: ' + n);
// Error: Type 'string' is not assignable to type 'number'.

Y la que devuelve una función —el closure del ejemplo 2.8— se tipa igual, poniendo la flecha en el retorno:

function crearMultiplicador(factor: number): (n: number) => number {
  return (numero) => numero * factor;   // no hace falta anotar 'numero'
}

const por5 = crearMultiplicador(5);
por5(7);   // 35

Fijarse en el detalle del callback: (numero) no lleva anotación y aun así está tipado. TypeScript sabe qué firma tiene que cumplir esa función porque ya la declaró el retorno — se llama inferencia contextual, y es la razón por la que en la práctica se escriben muchos menos tipos de los que imaginás.

async siempre devuelve Promise<T>

Conexión directa con la unidad de asincronía: una función async nunca devuelve el valor, devuelve una promesa de ese valor. El tipo lo dice explícitamente:

async function listarProductos(): Promise<Producto[]> {
  return repo.findAll();
}

const productos = listarProductos();
productos.map(...);
// Error: Property 'map' does not exist on type 'Promise<Producto[]>'.

const productos2 = await listarProductos();  // Producto[] ✔
Importante
El await olvidado es el bug clásico de la unidad de asincronía, y en JavaScript se manifiesta como un undefined raro dos funciones más adelante. En TypeScript es un error de compilación con nombre y apellido: "no existe map en Promise". Solo por esto ya paga la migración de una API con async/await.
Bloque 5

Objetos, interfaces y clases

Repetir { nombre: string; precio: number } en cada firma no escala. Para eso están las dos formas de ponerle nombre a una forma de objeto:

interface
interface Producto {
  id: number;
  nombre: string;
  precio: number;
}
type
type Producto = {
  id: number;
  nombre: string;
  precio: number;
};

Para describir objetos hacen prácticamente lo mismo. La recomendación para la materia, para no perder tiempo en el debate: interface para entidades y formas de objetos (un Producto, un Usuario), type para todo lo demás — uniones, alias, tipos derivados. Lo importante no es cuál elegís: es ser consistente en todo el proyecto.

Opcionales, readonly y tipos derivados

interface Producto {
  readonly id: number;   // no se puede reasignar después de creado
  nombre: string;
  precio: number;
  descripcion?: string;  // opcional: string | undefined
}

// El producto que llega en el POST es un Producto SIN id (lo pone el repo).
// En vez de duplicar la interface, se deriva:
type ProductoNuevo = Omit<Producto, 'id'>;

const nuevo: ProductoNuevo = { nombre: 'Mouse', precio: 15000 };  // ✔

Omit, Pick y Partial son utility types: tipos que se construyen a partir de otros. Con estos tres alcanza para el 90% de los casos de una API — Omit para el alta, Partial para el update parcial, Pick para lo que se devuelve. La ventaja de derivar en vez de duplicar: si mañana Producto suma un campo, ProductoNuevo se actualiza solo.

Clases en TypeScript

Las clases de la unidad correspondiente siguen siendo las mismas, con dos agregados: modificadores de acceso y la posibilidad de declarar que una clase cumple una interface.

7.1.4-clases.ts
class Producto {
  private descuento = 0;

  // "parameter properties": declara y asigna las propiedades de una vez
  constructor(
    public readonly id: number,
    public nombre: string,
    public precio: number
  ) {}

  precioFinal(): number {
    return this.precio * (1 - this.descuento);
  }
}

const p = new Producto(1, 'Teclado', 25000);
p.descuento = 0.5;
// Error: Property 'descuento' is private and only accessible within class 'Producto'.
p.id = 99;
// Error: Cannot assign to 'id' because it is a read-only property.
Cuidado
private de TypeScript existe solo en tiempo de compilación: se borra al compilar y en el .js resultante la propiedad es accesible como cualquier otra. El #privado de JavaScript, en cambio, es privado de verdad en ejecución. private protege del error propio; # protege el dato. Los dos son válidos — pero saber la diferencia evita una sorpresa fea.

Y el uso que más va a aparecer de acá en adelante: una interface como contrato, y una clase que se compromete a cumplirlo.

interface RepositorioProductos {
  findAll(): Promise<Producto[]>;
  guardar(datos: ProductoNuevo): Promise<Producto>;
}

class ProductosEnMemoria implements RepositorioProductos {
  private productos: Producto[] = [];

  async findAll(): Promise<Producto[]> {
    return this.productos;
  }

  async guardar(datos: ProductoNuevo): Promise<Producto> {
    const nuevo = { id: this.productos.length + 1, ...datos };
    this.productos.push(nuevo);
    return nuevo;
  }
}

Esto es, con sintaxis, el puerto de la arquitectura hexagonal de la clase anterior: la interface es el puerto —"necesito algo que guarde productos"— y la clase, el adaptador. En JavaScript ese contrato existía únicamente en la cabeza del equipo; acá el compilador lo verifica, y el día que el repository pase a MikroORM, la nueva clase tiene que cumplir la misma interface o no compila.

Lo que sigue
Las entidades de MikroORM —la próxima unidad— son exactamente esto: clases TypeScript con propiedades tipadas, más unos decoradores (@Entity(), @Property()) que le cuentan al ORM cómo mapear cada propiedad a una columna. Todo lo de este bloque es la base directa de esa clase; por eso TypeScript va antes que persistencia.
Bloque 6

La API en capas, ahora en TypeScript

Segunda parte, y todo lo anterior aplicado de una sola vez: la API de productos de la unidad de arquitecturas —routes, controllers, services, repositories— migrada a TypeScript. La estructura de carpetas no cambia; aparece dist/ (generada, va al .gitignore) y un lugar donde viven los tipos del dominio.

src/
├─ types/
│  └─ producto.ts          ← Producto, ProductoNuevo
├─ routes/       productos.routes.ts
├─ controllers/  productos.controller.ts
├─ services/     productos.service.ts
├─ repositories/ productos.repository.ts
├─ shared/       errors.ts, errorHandler.ts
└─ app.ts
dist/                    ← lo compilado (no se versiona)
tsconfig.json

Qué tipa cada capa:

Routes
Casi no cambian. Solo el import lleva .js y el Router ya viene tipado por @types/express.
Controllers
Tipan el trío de Express: Request, Response, NextFunction. Es donde se ve que req.body no está tipado.
Services
Reciben ProductoNuevo y devuelven Promise<Producto>. El contrato del negocio, explícito.
Repositories
Es el dueño del tipo Producto: el array pasa a ser Producto[] y las firmas devuelven promesas tipadas.
+ Middleware
El errorHandler se tipa con ErrorRequestHandler, que ya obliga a los cuatro parámetros en el orden correcto — el detalle que en JavaScript se equivocaba en silencio.
src/types/producto.ts
export interface Producto {
  id: number;
  nombre: string;
  precio: number;
}

// el alta llega sin id: lo asigna el repository
export type ProductoNuevo = Omit<Producto, 'id'>;
src/repositories/productos.repository.ts
import type { Producto, ProductoNuevo } from '../types/producto.js';

const productos: Producto[] = [{ id: 1, nombre: 'Teclado', precio: 25000 }];

export async function findAll(): Promise<Producto[]> {
  return productos;
}

export async function guardar(datos: ProductoNuevo): Promise<Producto> {
  const nuevo: Producto = { id: productos.length + 1, ...datos };
  productos.push(nuevo);
  return nuevo;
}

El import type es una forma de importar que dice "esto es solo un tipo": desaparece por completo al compilar y nunca genera un import en el .js. Con Producto, que no existe en tiempo de ejecución, es lo correcto.

src/services/productos.service.ts
import * as repo from '../repositories/productos.repository.js';
import { ValidationError } from '../shared/errors.js';
import type { Producto, ProductoNuevo } from '../types/producto.js';

export async function listarProductos(): Promise<Producto[]> {
  return repo.findAll();
}

export async function crearProducto(datos: ProductoNuevo): Promise<Producto> {
  if (!datos.nombre || datos.precio <= 0) {
    throw new ValidationError('Datos inválidos');
  }
  return repo.guardar(datos);
}
src/controllers/productos.controller.ts
import type { Request, Response, NextFunction } from 'express';
import * as service from '../services/productos.service.js';

export async function listar(req: Request, res: Response, next: NextFunction) {
  try {
    res.json(await service.listarProductos());
  } catch (err) {
    next(err);
  }
}

export async function crear(req: Request, res: Response, next: NextFunction) {
  try {
    const producto = await service.crearProducto(req.body);
    //                                          ^^^^^^^^ esto es 'any'
    res.status(201).json(producto);
  } catch (err) {
    next(err);
  }
}

Ese comentario es el punto más importante del bloque, y hay que detenerse ahí: req.body es any. Express no puede saber qué te van a mandar, así que TypeScript acepta pasárselo a crearProducto() sin chequear absolutamente nada. Toda la cadena está tipada y aun así el agujero del bloque 1 sigue abierto.

Instalar los tipos de Express

terminal
npm install express
npm install --save-dev @types/express

Express está escrito en JavaScript, así que sus tipos vienen aparte, en un paquete @types/* mantenido por la comunidad (el proyecto DefinitelyTyped). Regla general: si al importar una librería el editor dice "Could not find a declaration file for module …", la respuesta casi siempre es npm i -D @types/esa-librería.

Lo que se gana, en concreto

  • Agregar stock: number a Producto hace que el compilador marque uno por uno los lugares que quedaron incompletos —acá, el array del repository— y no compile hasta que estén todos. La refactorización deja de ser una búsqueda de texto con la esperanza de no haberse olvidado ninguno.
  • El editor autocompleta res.status(…).json(…) y las propiedades del producto: menos idas y vueltas a la documentación.
  • El contrato entre capas es verificable: si el service devuelve otra cosa, el controller no compila.
  • Cuando en la próxima unidad el repository pase a MikroORM, la firma Promise<Producto> ya está: el service no se toca.
Bloque 7

Zod: el tipo que sí existe en runtime

Recapitulemos el problema con precisión, porque es una distinción que se usa todos los días y casi nunca se explica:

TypeScriptZod
Cuándo actúaAl compilarAl ejecutar
Qué controlaEl código que vos escribísLos datos que te mandan
Después de compilarDesapareceSigue ahí: es código JavaScript
Sirve paraQue las capas encajen entre síBodies, params, variables de entorno, respuestas de otras APIs

Zod es una librería de validación de esquemas. Se escribe un esquema —una descripción de la forma esperada— y Zod chequea los datos en tiempo de ejecución. Hasta ahí es lo que hacía el if a mano de la clase de arquitecturas. Lo que lo vuelve interesante en TypeScript es lo que viene después.

terminal
npm install zod

Ojo: zod va en dependencies, no en devDependencies. Es la diferencia entre una herramienta de desarrollo y una que corre en producción.

src/schemas/producto.schema.ts
import { z } from 'zod';

export const productoNuevoSchema = z.object({
  nombre: z.string().min(1, 'El nombre es obligatorio'),
  precio: z.number().positive('El precio debe ser mayor a 0'),
});

// ── la línea que justifica toda la clase ──
export type ProductoNuevo = z.infer<typeof productoNuevoSchema>;
// ProductoNuevo === { nombre: string; precio: number }

Leamos z.infer despacio, porque es la idea central del bloque: el esquema es un valor de JavaScript (existe en ejecución, valida datos reales) y z.infer extrae de ese valor el tipo de TypeScript. No hay que escribir la interface por un lado y la validación por el otro: se escribe una sola vez, y el tipo se deriva.

Sin Zod: dos verdades
// tipos.ts
interface ProductoNuevo {
  nombre: string;
  precio: number;
}

// service.ts — validación aparte
if (!datos.nombre || datos.precio <= 0) {
  throw new ValidationError(...);
}
// ¿te acordás de tocar las dos
// cuando cambie el modelo?
Con Zod: una sola
// producto.schema.ts
export const productoNuevoSchema =
  z.object({
    nombre: z.string().min(1),
    precio: z.number().positive(),
  });

export type ProductoNuevo =
  z.infer<typeof productoNuevoSchema>;
// el tipo no puede desincronizarse

Validar el body: safeParse

const resultado = productoNuevoSchema.safeParse(req.body);

if (!resultado.success) {
  // resultado.error tiene el detalle campo por campo
  return res.status(400).json({ errores: resultado.error.issues });
}

// dentro de este bloque, resultado.data es ProductoNuevo — tipado y validado
const producto = await service.crearProducto(resultado.data);

Dos formas de usarlo: parse() lanza una excepción si falla (cómoda si ya hay un errorHandler centralizado que la traduzca) y safeParse() devuelve un objeto con success. Fijarse en el detalle: adentro del if (!resultado.success) TypeScript sabe que hay un error, y afuera sabe que hay un data tipado. Es una unión discriminada, el mismo narrowing del bloque 3 en un caso real.

Y ahora, como middleware

Validar dentro de cada controller repite código en cada endpoint. La clase de arquitecturas ya dio la respuesta para lo que se repite: middleware.

src/shared/validar.ts
import type { Request, Response, NextFunction } from 'express';
import type { ZodTypeAny } from 'zod';

// Recibe un esquema y devuelve un middleware: una función de orden superior,
// como las de la unidad de funciones — pero tipada.
export function validar(schema: ZodTypeAny) {
  return (req: Request, res: Response, next: NextFunction) => {
    const resultado = schema.safeParse(req.body);

    if (!resultado.success) {
      return res.status(400).json({
        error: 'Datos inválidos',
        detalle: resultado.error.issues.map((i) => ({
          campo: i.path.join('.'),
          mensaje: i.message,
        })),
      });
    }

    req.body = resultado.data;  // body limpio y validado para el controller
    next();
  };
}
src/routes/productos.routes.ts
import { Router } from 'express';
import { listar, crear } from '../controllers/productos.controller.js';
import { validar } from '../shared/validar.js';
import { productoNuevoSchema } from '../schemas/producto.schema.js';

export const productosRouter = Router();

productosRouter.get('/', listar);
productosRouter.post('/', validar(productoNuevoSchema), crear);
//                        ^^^^^^^ se valida antes de llegar al controller

Con eso, el request con "precio": "15000" —el del bloque 1— muere en el middleware con un 400 y un mensaje que dice exactamente qué campo está mal. El controller solo recibe bodies que ya cumplen el esquema, y el service vuelve a ocuparse únicamente de reglas de negocio (que el nombre no esté repetido, que el descuento no supere el máximo), no de formato.

Importante
La división de trabajo, en una línea: TypeScript chequea lo que vos escribís; Zod chequea lo que te mandan. Los dos hacen falta y ninguno reemplaza al otro. Y con z.infer, el esquema de validación y el tipo son la misma fuente de verdad — no dos declaraciones que hay que acordarse de mantener sincronizadas.
Dato
El mismo esquema sirve para todo lo que entra desde afuera: los params y el query de una ruta, las variables de entorno al arrancar la app (que llegan siempre como string), y las respuestas de APIs de terceros. Validar el process.env con Zod al inicio es una práctica muy común, y evita el clásico "andaba en mi máquina" por una variable que en el servidor no estaba.
Bloque 8

Migrar un proyecto JS que ya existe

Lo más probable es que no arranques de cero: el TP ya está escrito en JavaScript. La buena noticia es que la migración es gradual — no hace falta parar todo y convertir el proyecto entero.

  1. Instalar TypeScript y crear el tsconfig.json con "allowJs": true: .js y .ts conviven en el mismo proyecto.
  2. Renombrar de a un archivo .js → .ts, empezando por las hojas del árbol (el repository, los helpers) y subiendo hacia el controller.
  3. Arreglar los errores de ese archivo. Si alguno es muy trabado, any temporal y un // TODO: es deuda, pero acotada y visible.
  4. Cuando ya casi todo es .ts, prender "strict": true y hacer la última pasada.
  5. Sacar allowJs y borrar los any que quedaron.
tsconfig.json durante la migración
{
  "compilerOptions": {
    "allowJs": true,     // deja compilar los .js que todavía no migraste
    "checkJs": false,    // ...sin exigirles tipos (todavía)
    "strict": false      // se prende al final, no al principio
  }
}

Un atajo útil antes de renombrar nada: poner "checkJs": true y agregar comentarios JSDoc a los archivos .js. TypeScript los lee y chequea el archivo sin cambiarle la extensión — sirve para ver cuánto rompería la migración antes de encararla.

/** @param {number} precio */
export function conIva(precio) {
  return precio * 1.21;
}

conIva('25000');
// con checkJs → Error: Argument of type 'string' is not assignable to
//               parameter of type 'number'. (en un archivo .js)

Los cuatro errores del primer día

MensajeQué pasaQué hacer
Parameter implicitly has an 'any' type Un parámetro sin anotar, con strict prendido. Anotarlo. Es el error más frecuente al migrar y también el más fácil.
Object is possibly 'undefined' Un find, un [0] o un campo opcional que puede no venir. Contemplar el caso con un if. No apagar strictNullChecks.
Could not find a declaration file for module 'x' La librería está en JavaScript y no trae tipos. npm i -D @types/x. Si no existe, declarar el módulo o usar any.
Relative import paths need explicit file extensions Falta el .js en un import relativo, con NodeNext. Agregarlo: './productos.service.js', aunque el archivo sea .ts.
Cuidado
La tentación del primer día es resolver todo con any o con as (aserciones de tipo). Ambos le dicen al compilador "confiá en mí", y si uno se equivoca, el error vuelve a runtime — que es exactamente de lo que se estaba escapando. Usalos cuando de verdad sepas algo que el compilador no puede saber, no para que el rojo desaparezca.

Ponete a prueba

Respondé cada pregunta mentalmente y después tocá para revelar la respuesta y verificar.

1. ¿Por qué Node no puede ejecutar directamente un archivo .ts?
Porque TypeScript no es un lenguaje que Node entienda: es un compilador. tsc chequea los tipos, los borra y emite JavaScript común en dist/; eso es lo que corre con node dist/app.js. En desarrollo tsx hace ese paso en memoria y da la ilusión de que ejecuta el .ts, pero por debajo lo compila igual.
2. ¿Qué significa que los tipos se borran al compilar, y qué consecuencia práctica tiene?
Que en el .js generado no queda ni una anotación: es el mismo código sin los tipos (type erasure). Consecuencias: TypeScript no hace más lento el programa, cualquier .js que funciona es TypeScript válido, y —la importante— no puede validar en ejecución lo que llega de afuera. Por eso hace falta Zod.
3. ¿Cuál es la diferencia entre any y unknown?
Los dos dicen "no sé qué tipo es", pero any apaga el chequeo (podés hacer cualquier cosa con ese valor y compila igual, incluso si explota en ejecución) y además se contagia a todo lo que sale de ahí. unknown obliga a verificar antes de usar el valor, normalmente con typeof. Para datos que vienen de afuera (JSON.parse, fetch), la opción correcta es unknown.
4. Si el archivo se llama productos.service.ts, ¿por qué se importa como './productos.service.js'?
Porque con "module": "NodeNext" el import lo resuelve Node en tiempo de ejecución, cuando ese archivo ya se compiló a .js. TypeScript nunca reescribe la ruta del import. No es un error ni un typo: es la extensión del archivo que va a existir cuando el código corra.
5. La API quedó tipada de punta a punta. ¿Por qué un POST con { "precio": "15000" } puede pasar igual, y qué lo evita?
Porque req.body es any: Express no puede saber qué te van a mandar, así que TypeScript acepta pasárselo al service sin chequear nada. Los tipos son una promesa sobre el código que escribís vos, no sobre los datos que te mandan. Lo que lo evita es validar en ejecución con Zod, idealmente como middleware antes del controller.
6. ¿Qué hace z.infer y qué problema resuelve?
Extrae el tipo de TypeScript a partir del esquema de Zod: type ProductoNuevo = z.infer<typeof productoNuevoSchema>. Resuelve el problema de tener dos verdades —la interface por un lado y la validación por otro— que hay que acordarse de mantener sincronizadas. Con z.infer escribís el esquema una sola vez y el tipo se deriva solo.
7. ¿Qué error te da TypeScript si te olvidás un await, y por qué?
Algo como "Property 'map' does not exist on type 'Promise<Producto[]>'". Una función async no devuelve el valor sino una promesa de ese valor, y eso queda escrito en su tipo de retorno. En JavaScript el await olvidado se manifiesta como un undefined raro dos funciones más adelante; en TypeScript es un error de compilación en la línea exacta.
8. ¿Cómo migrarías a TypeScript un proyecto JavaScript que ya está en marcha?
Gradualmente: allowJs: true para que .js y .ts convivan, renombrar de a un archivo empezando por las hojas (el repository, los helpers) y subiendo hacia el controller, any temporal con un // TODO donde algo se trabe, y recién al final prender "strict": true y sacar allowJs. No hace falta frenar el desarrollo para convertir todo de una.
Cierre

Resumen

  • TypeScript es JavaScript más un sistema de tipos que se chequea al compilar y se borra al emitir: lo que corre es siempre JavaScript.
  • El flujo es .ts → tsc → dist/*.js → node. En desarrollo, tsx ejecuta el .ts directo; en producción se corre lo compilado.
  • "strict": true desde el primer día: sin él, TypeScript no controla ni los any implícitos ni null/undefined.
  • Anotar en los bordes —parámetros, retornos, datos que entran— y dejar que la inferencia haga el resto.
  • any apaga el chequeo y se contagia; unknown obliga a verificar antes de usar. Para lo que viene de afuera, unknown.
  • Las funciones se tipan por firma, incluidos los callbacks ((n: number) => number); async siempre devuelve Promise<T>, y el await olvidado pasa a ser error de compilación.
  • interface para entidades, type para uniones y derivados. Omit, Pick y Partial evitan duplicar formas de objetos.
  • En la API, el tipo del dominio viaja por las capas: en cualquier refactorización el compilador marca qué quedó incompleto y no compila hasta que esté resuelto.
  • req.body es any: TypeScript no valida lo que entra. Zod valida en ejecución y, con z.infer, el esquema y el tipo son la misma fuente de verdad.
  • Migrar es gradual: allowJs, un archivo por vez desde las hojas hacia arriba, y strict al final.
