Bloque 1

De la constructor function a class

Repasemos lo último de la guía anterior. Estas dos formas de definir Producto hacen exactamente lo mismo:

Constructor function (pre-ES6)

function Producto(nombre, precio) {
  this.nombre = nombre;
  this.precio = precio;
}

Producto.prototype.describir =
  function() {
    return `${this.nombre}: $${this.precio}`;
  };

Class (ES6, recomendada)

class Producto {
  constructor(nombre, precio) {
    this.nombre = nombre;
    this.precio = precio;
  }

  describir() {
    return `${this.nombre}: $${this.precio}`;
  }
}

Y no es una metáfora: se puede verificar que por debajo hay lo mismo de siempre.

const teclado = new Producto('Teclado', 25000);

console.log(typeof Producto);                              // 'function' (!)
console.log(Object.getPrototypeOf(teclado) === Producto.prototype); // true
console.log(teclado.describir === Producto.prototype.describir);   // true

Una clase es una función, y los métodos viven en Producto.prototype, igual que cuando los poníamos a mano. La cadena de prototipos es idéntica a la que viste en la guía anterior:

teclado
su prototipo→
Producto.prototype
su prototipo→
Object.prototype
su prototipo→
null

La clase no cambió el modelo de objetos de JS: solo cambió cómo se escribe.

Cuatro cosas que class sí cambia

Decir «es solo azúcar» es una simplificación útil, pero incompleta. La sintaxis de clase agrega cuatro reglas que la constructor function no tenía:

ReglaQué pasa si no se cumple
new es obligatorioProducto('Teclado', 100) tira TypeError. Con constructor function, la llamada sin new «funcionaba» y ensuciaba variables globales.
No hay hoisting utilizableUsar la clase antes de su declaración tira ReferenceError. Las funciones sí se podían usar antes (guía de funciones); las clases están en la temporal dead zone, como let y const.
Siempre en modo estrictoEl cuerpo de una clase corre en strict mode aunque el archivo no lo declare. Esto es la causa del bug del bloque 6.
Los métodos no son enumerablesNo aparecen en Object.keys() ni en for...in. Es lo que uno quiere: al recorrer un producto salen sus datos, no su comportamiento.
Conecta con la clase de asincronía
Es el mismo patrón que ya vieron: async/await es azúcar sobre promesas, y class es azúcar sobre prototipos. En los dos casos, el mecanismo de abajo sigue estando y aparece cuando algo falla. Por eso no alcanza con la sintaxis nueva: hay que saber qué hay debajo.
Bloque 2

Anatomía de una clase

Una clase tiene tres tipos de miembro que conviene nombrar bien, porque después aparecen en cualquier documentación:

class Producto {
  // 1. CAMPOS DE INSTANCIA (instance fields): datos, con valor por defecto
  stock = 0;
  activo = true;

  // 2. CONSTRUCTOR: se ejecuta una vez, al hacer new
  constructor(nombre, precio) {
    this.nombre = nombre;
    this.precio = precio;
  }

  // 3. MÉTODOS DE INSTANCIA: comportamiento
  describir() {
    return `${this.nombre}: $${this.precio} (stock: ${this.stock})`;
  }

  precioFinal() {
    return this.precio * 1.21; // IVA
  }
}

const teclado = new Producto('Teclado', 25000);
teclado.stock = 12;

console.log(teclado.describir());   // Teclado: $25000 (stock: 12)
console.log(teclado.precioFinal()); // 30250

Notar que los campos con valor por defecto (stock = 0) se escriben sin let ni const, y sin coma al final. Es un error de sintaxis frecuente en la primera clase que escribís.

Dónde vive cada cosa

Esta es la parte que hay que entender de verdad, porque explica todo lo demás: los datos van a la instancia, los métodos van al prototipo.

console.log(Object.keys(teclado));
// ['stock', 'activo', 'nombre', 'precio']  → solo datos

console.log(teclado.hasOwnProperty('precio'));    // true  → es suyo
console.log(teclado.hasOwnProperty('describir')); // false → lo hereda

La consecuencia es de eficiencia y es la razón de ser del prototipo: si creo mil productos, hay mil copias de nombre y precio, pero una sola copia de describir, compartida por todos.

Ojo con el atajo de la arrow function
Se puede definir un método como campo con arrow function (describir = () => {...}) y a veces conviene —lo vas a ver en el bloque 6—, pero tiene un costo: deja de ser un método del prototipo y pasa a ser una copia por instancia. Por defecto, método normal; la arrow es una excepción con motivo.

Métodos async en una clase

Un método puede ser async como cualquier función. No hay sintaxis nueva, y esto es lo que vas a ver en todos los services y repositories de la unidad de APIs:

class ProductoService {
  async buscarPorId(id) {
    const respuesta = await fetch(`https://api.ejemplo.com/productos/${id}`);
    return await respuesta.json();
  }
}

const service = new ProductoService();
const producto = await service.buscarPorId(1); // devuelve una promesa
Bloque 3

Getters, setters y validación

Un getter es un método que se usa como si fuera una propiedad: se declara con get y se lee sin paréntesis. Sirve para valores derivados, que no se guardan pero se calculan a partir de lo que sí está guardado.

class Producto {
  constructor(nombre, precio) {
    this.nombre = nombre;
    this.precio = precio;
  }

  get precioConIva() {
    return this.precio * 1.21;
  }
}

const teclado = new Producto('Teclado', 25000);

console.log(teclado.precioConIva);   // 30250 — SIN paréntesis
console.log(teclado.precioConIva()); // TypeError: teclado.precioConIva is not a function

Un setter es el par: se ejecuta cuando alguien asigna a esa propiedad. Su utilidad real es una sola —validar antes de guardar— y esa es la razón por la que existe la encapsulación.

El problema que resuelve

Sin setter, cualquiera puede dejar el objeto en un estado inválido, y el error va a aparecer mucho después, en otro archivo:

teclado.precio = -5000;      // nadie protesta
teclado.precio = 'muy caro';  // tampoco

console.log(teclado.precioConIva); // NaN, tres archivos más adelante

Con setter, el objeto se defiende solo y el error salta en el momento y el lugar en que se produce:

class Producto {
  #precio; // el dato real, privado (lo vemos en detalle en el bloque 4)

  constructor(nombre, precio) {
    this.nombre = nombre;
    this.precio = precio; // pasa por el setter, así que también valida acá
  }

  get precio() {
    return this.#precio;
  }

  set precio(valor) {
    if (typeof valor !== 'number' || valor <= 0) {
      throw new Error('El precio tiene que ser un número positivo');
    }
    this.#precio = valor;
  }
}

const teclado = new Producto('Teclado', 25000);
teclado.precio = -5000; // Error: El precio tiene que ser un número positivo

El detalle importante: como el constructor asigna con this.precio = precio, la validación corre también al crear el objeto. No hay forma de fabricar un producto con precio negativo.

⚠ El error clásico: el setter que se llama a sí mismo
Si el campo se llama igual que el setter, la asignación de adentro vuelve a disparar el setter, infinitamente: 
set precio(valor) {
  this.precio = valor; // ❌ se llama a sí mismo
}
// RangeError: Maximum call stack size exceeded
La solución es que el dato viva en otro nombre: #precio (privado, recomendado) o _precio (convención vieja). Es exactamente el mismo tipo de error que la recursión sin caso base de la guía de funciones.

¿Getter o método?

Usá un getterUsá un método
El valor es un dato derivado barato de calcular (precioConIva, nombreCompleto).La operación hace algo: modifica el objeto, guarda, imprime, pide datos.
Leerlo no tiene efectos secundarios ni sorpresas.Necesita parámetros (un getter no puede recibir ninguno).
Se lee como una propiedad y esa lectura es honesta.Es lento o asincrónico: que lleve () avisa que ahí pasa algo.
Bloque 4

Encapsulamiento: campos privados y miembros estáticos

Privado de verdad: el prefijo #

Durante veinte años, «privado» en JS fue una convención: se ponía un guion bajo adelante (_stock) y se confiaba en que nadie lo tocara. No impedía nada. Desde ES2022 hay campos realmente privados: los que empiezan con #.

class Producto {
  #stock; // privado: hay que declararlo arriba, antes del constructor

  constructor(nombre, precio, stock = 0) {
    this.nombre = nombre;
    this.precio = precio;
    this.#stock = stock;
  }

  get stock() {
    return this.#stock; // se puede leer, no escribir desde afuera
  }

  vender(cantidad) {
    this.#validarCantidad(cantidad); // método privado
    if (cantidad > this.#stock) {
      throw new Error(`Stock insuficiente: hay ${this.#stock}`);
    }
    this.#stock -= cantidad;
    return this.#stock;
  }

  // los métodos también pueden ser privados
  #validarCantidad(cantidad) {
    if (!Number.isInteger(cantidad) || cantidad <= 0) {
      throw new Error('La cantidad tiene que ser un entero positivo');
    }
  }
}

Desde afuera, #stock no existe. Y no es un error en tiempo de ejecución que se pueda atrapar: es un error de sintaxis, el archivo no arranca.

const teclado = new Producto('Teclado', 25000, 10);

console.log(teclado.stock);  // 10 — el getter, sí
teclado.vender(3);            // 7  — la puerta que la clase abrió

// console.log(teclado.#stock);
// SyntaxError: Private field '#stock' must be declared in an enclosing class

teclado.stock = 9999;         // hay getter y no hay setter:
// TypeError: Cannot set property stock of #<Producto> which has only a getter
// (en modo estricto avisa; sin 'use strict' falla en silencio)

La idea de fondo no es «esconder por esconder»: es que toda modificación del stock pase por vender(), que es donde vive la regla de negocio. Un dato público es un dato que cualquiera puede dejar inconsistente.

Miembros estáticos: lo que es de la clase, no del objeto

Un miembro static pertenece a la clase y no a cada instancia. Se usa cuando la operación no necesita un producto concreto: contadores, constantes y fábricas.

class Producto {
  static #creados = 0;        // campo estático privado
  static IVA = 0.21;            // constante de la clase

  constructor(nombre, precio) {
    this.nombre = nombre;
    this.precio = precio;
    Producto.#creados++;       // ojo: Producto, no this
  }

  static get creados() {
    return Producto.#creados;
  }

  // método fábrica: construye una instancia desde otra representación
  static desdeJSON(texto) {
    const datos = JSON.parse(texto);
    return new Producto(datos.nombre, datos.precio);
  }
}

new Producto('Teclado', 25000);
new Producto('Mouse', 12000);

console.log(Producto.creados); // 2  — se pide a la CLASE
console.log(Producto.IVA);     // 0.21

Un método estático no ve this como instancia, porque no hay instancia: si adentro de desdeJSON se escribe this.nombre, no hay nada ahí. Se llama sobre la clase (Producto.desdeJSON(...)), nunca sobre un objeto.

Clases y JSON: por qué hace falta la fábrica

Acá se junta con la guía anterior, y es un punto que sorprende:

const teclado = new Producto('Teclado', 25000, 10);

const texto = JSON.stringify(teclado);
console.log(texto); // {"nombre":"Teclado","precio":25000}
// ¡se perdieron los métodos Y el campo privado #stock!

const recuperado = JSON.parse(texto);
console.log(recuperado instanceof Producto); // false — es un objeto plano
// recuperado.vender(1); → TypeError: recuperado.vender is not a function

JSON.parse siempre devuelve objetos planos: tienen los datos pero no el comportamiento. Por eso existe Producto.desdeJSON(texto) — es la forma de volver a tener una instancia de verdad. Y si querés controlar qué se serializa (por ejemplo, incluir el #stock), la clase puede definir toJSON():

  toJSON() {
    return { nombre: this.nombre, precio: this.precio, stock: this.#stock };
  }
// JSON.stringify lo llama solo: {"nombre":"Teclado","precio":25000,"stock":10}
Conecta con lo que viene
Este ida y vuelta es literalmente el trabajo de una API: llega un POST con un JSON, hay que convertirlo en un objeto del dominio, validarlo y guardarlo; y a la salida, convertir el objeto en JSON. En la unidad de APIs ese pasaje va a tener nombre y lugar propio en la arquitectura.
Bloque 5

Herencia y polimorfismo

Un producto físico y uno digital comparten casi todo —nombre, precio, stock— pero se diferencian en algo: el físico se envía y el digital se descarga. Duplicar la clase entera para cambiar un método sería absurdo. Para eso está extends.

class ProductoFisico extends Producto {
  constructor(nombre, precio, pesoKg) {
    super(nombre, precio); // ejecuta el constructor de Producto
    this.pesoKg = pesoKg;   // lo propio va después
  }

  costoEnvio() {
    return this.pesoKg * 800;
  }

  // sobrescribe el método del padre y lo reutiliza con super.
  precioFinal() {
    return super.precioFinal() + this.costoEnvio();
  }
}

class ProductoDigital extends Producto {
  constructor(nombre, precio, tamanioMb) {
    super(nombre, precio);
    this.tamanioMb = tamanioMb;
  }

  // no sobrescribe precioFinal: hereda el de Producto, sin envío
}

super hace dos trabajos distintos según dónde aparezca:

  • super(...) en el constructor: llama al constructor de la clase padre.
  • super.metodo() en un método: llama a la versión del padre del método que estoy sobrescribiendo.
⚠ super() va primero, siempre
Tocar this antes de llamar a super() en el constructor de una subclase tira ReferenceError: Must call super constructor ... before accessing 'this'. Es literal: hasta que no corre el constructor del padre, el objeto todavía no existe. Y si la subclase no define constructor, JS le pone uno que llama a super(...) con todos los argumentos — por eso a veces «funciona sin escribirlo».

Polimorfismo: el mismo mensaje, distinta respuesta

Acá está el pago de todo el bloque. Una vez que las dos subclases responden a precioFinal(), el código que las usa deja de preguntar de qué tipo son:

const carrito = [
  new ProductoFisico('Teclado', 25000, 0.9),
  new ProductoDigital('Curso de Node', 30000, 1200),
  new ProductoFisico('Monitor', 180000, 4.2),
];

const total = carrito.reduce((acum, p) => acum + p.precioFinal(), 0);
console.log(total); // cada uno calcula lo suyo, el reduce no se entera

Lo que no hay que escribir es esto, que es la alternativa sin polimorfismo:

// ❌ el if que hay que ir a tocar cada vez que aparece un tipo nuevo
if (p.tipo === 'fisico') {
  total += p.precio * 1.21 + p.pesoKg * 800;
} else if (p.tipo === 'digital') {
  total += p.precio * 1.21;
}
Conecta con la clase de funciones
El reduce de arriba es una función de orden superior: recibe una función y la aplica a cada elemento. Polimorfismo y funciones de orden superior tiran para el mismo lado — que el código genérico no necesite saber los detalles de cada caso particular.

La cadena, otra vez

extends no inventó nada: solo enganchó un eslabón más en la cadena de prototipos.

teclado
prototipo→
ProductoFisico.prototype
prototipo→
Producto.prototype
prototipo→
Object.prototype
prototipo→
null

Al pedir teclado.describir(), JS sube hasta encontrarlo en Producto.prototype. Al pedir precioFinal(), lo encuentra antes, en ProductoFisico.prototype: por eso gana el de la subclase.

const teclado = new ProductoFisico('Teclado', 25000, 0.9);

console.log(teclado instanceof ProductoFisico); // true
console.log(teclado instanceof Producto);       // true — también es un Producto
console.log(teclado instanceof Object);         // true

instanceof devuelve true si la clase aparece en algún lugar de esa cadena. Y sí: los métodos estáticos también se heredan (ProductoFisico.desdeJSON existe), aunque devuelvan instancias del padre si están escritos con el nombre de la clase fijo.

Bloque 6

El this que se pierde

Este es el bloque que más vale de la guía, porque describe un bug que vas a tener sí o sí en el trabajo práctico y que, si es la primera vez que lo ves, es muy difícil de diagnosticar.

La regla de la guía anterior sigue valiendo: this apunta al objeto sobre el que se invocó el método. La trampa está en la palabra invocó: no depende de dónde se escribió el método, sino de cómo se lo llama.

const teclado = new Producto('Teclado', 25000);

teclado.describir();  // ✅ 'Teclado: $25000' — se invocó SOBRE teclado

const describir = teclado.describir; // guardo la función, sin llamarla
describir();
// ❌ TypeError: Cannot read properties of undefined (reading 'nombre')

Es la misma función. Lo que cambió es que en la segunda llamada no hay ningún objeto a la izquierda del punto, así que this queda en undefined — acordate de que el cuerpo de una clase corre siempre en modo estricto (bloque 1), y en modo estricto this no cae al objeto global: queda undefined.

Dónde aparece de verdad

Nadie escribe const describir = teclado.describir a propósito. El problema real es que pasar un método como callback hace exactamente eso:

const carrito = new Carrito();

// las tres formas rompen igual: se pasa la función suelta
['Teclado', 'Mouse'].forEach(carrito.agregar);   // ❌
setTimeout(carrito.vaciar, 1000);                     // ❌
router.get('/api/productos', controller.getAll);      // ❌ (Express)
⚠ Este es el bug del TP
La última línea es la que te vas a encontrar en la unidad de APIs: un controller escrito como clase, pasado a la ruta de Express, que explota con Cannot read properties of undefined apenas se hace el primer GET. El código «se ve bien» y por eso puede costarte una tarde. Haberlo visto acá, con un ejemplo de diez líneas, es la diferencia.

Las tres soluciones

// 1. bind — devuelve una función nueva con el this fijado
['Teclado', 'Mouse'].forEach(carrito.agregar.bind(carrito));  // ✅

// 2. envolver en una arrow function — la invocación conserva el punto
['Teclado', 'Mouse'].forEach((n) => carrito.agregar(n));      // ✅

// 3. definir el método como campo con arrow function, en la clase
class Carrito {
  items = [];

  agregar = (nombre) => {   // this queda atado a la instancia, siempre
    this.items.push(nombre);
  };
}

La tercera funciona porque, como viste en la guía de funciones, una arrow function no tiene this propio: lo toma del lugar donde fue creada, que acá es la instancia. Y ese es el motivo por el que la arrow no sirve como método de un objeto literal, pero sí sirve como campo de una clase — vale la pena detenerse en esa aparente contradicción, porque es la misma regla aplicada dos veces.

SoluciónCuándo conviene
bindPuntual, cuando se pasa el método una sola vez. Explícito y estándar.
Arrow que envuelveLo más legible y lo más común hoy. Además deja controlar qué argumentos se pasan.
Campo con arrowCuando el método siempre se va a usar como callback. Costo: una copia por instancia, no se hereda ni se sobrescribe bien.

Composición: cuándo no heredar

Una pregunta que parece inocente: ¿conviene escribir ProductoEnOferta extends Producto? El problema es que la clase de un objeto no se puede cambiar: si la oferta termina, no hay forma de que el objeto deje de ser un ProductoEnOferta. Y si además el producto es digital, harían falta ProductoDigitalEnOferta y ProductoFisicoEnOferta: la jerarquía se multiplica.

La oferta no es una especie de producto: es algo que el producto tiene. Eso se modela con composición — un objeto que contiene a otro:

Herencia (rígido)

class ProductoEnOferta
  extends Producto { /* ... */ }

// ¿y ProductoDigitalEnOferta?
// ¿y cuando la oferta termina?

Composición (flexible)

class Producto {
  descuento = null;

  precioFinal() {
    const base = this.precio * 1.21;
    return this.descuento
      ? this.descuento.aplicar(base)
      : base;
  }
}

La regla práctica, y sirve como criterio de diseño para el TP: heredá cuando la subclase es un tipo distinto y permanente; componé cuando es algo que el objeto tiene y puede cambiar. En la práctica, jerarquías de más de dos niveles casi siempre son un error de modelado.

Autoevaluación

Ponete a prueba

Respondé cada pregunta mentalmente y después tocá para revelar la respuesta y verificar.

1. Si class es azúcar sintáctico sobre prototipos, ¿qué agrega que la función constructora no tenía?
Cuatro reglas: new es obligatorio (llamarla sin new tira TypeError), no hay hoisting utilizable (está en la temporal dead zone, como let), el cuerpo corre siempre en modo estricto, y los métodos no son enumerables (no salen en Object.keys()).
2. ¿Dónde vive un campo de instancia y dónde vive un método? ¿Por qué importa?
El campo vive en cada instancia; el método, en Clase.prototype. Por eso con mil objetos hay mil copias de los datos y una sola del método. Se comprueba con obj.hasOwnProperty('describir'), que da false: el método se hereda por la cadena de prototipos.
3. ¿Para qué sirve un setter, y por qué el dato que guarda tiene que llamarse distinto?
Sirve para validar antes de guardar, así el objeto nunca queda en un estado inválido. Si el campo se llama igual que el setter (set precio guardando en this.precio), la asignación de adentro vuelve a disparar el setter y se cae con RangeError: Maximum call stack size exceeded. Por eso el dato va en #precio.
4. ¿Qué diferencia hay entre _stock y #stock?
_stock es una convención: avisa «no lo toques», pero no impide nada. #stock es privado de verdad — acceder desde afuera de la clase es un error de sintaxis, así que el archivo ni siquiera arranca. Sirve para que toda modificación pase por el método que tiene la regla de negocio.
5. ¿Cuándo conviene un miembro static?
Cuando la operación no necesita una instancia concreta: constantes de la clase, contadores y métodos fábrica como Producto.desdeJSON(texto). Se llaman sobre la clase, no sobre un objeto — igual que Math.random() o Number.isInteger(), que ya venís usando.
6. ¿Por qué super() tiene que ir antes de tocar this en el constructor de una subclase?
Porque hasta que no corre el constructor del padre, el objeto todavía no existe. Si lo hacés al revés, JS tira ReferenceError: Must call super constructor … before accessing 'this'. Si la subclase no define constructor, JS le pone uno que llama a super(...) con todos los argumentos.
7. Tenés un array con productos físicos y digitales y querés el total. ¿Qué te evita el polimorfismo?
El if por tipo. Si cada subclase implementa precioFinal() a su manera, el reduce que suma no necesita saber qué tipo es cada uno — y agregar una clase nueva no obliga a tocar ese código.
8. ¿Por qué ['a','b'].forEach(carrito.agregar) falla, y cómo se arregla?
Porque this depende de cómo se invoca el método, no de dónde se escribió: al pasarlo suelto no hay objeto a la izquierda del punto, y como el cuerpo de una clase corre en modo estricto, this queda undefined. Se arregla con carrito.agregar.bind(carrito), envolviéndolo en una arrow ((x) => carrito.agregar(x)) o definiendo el método como campo con arrow function.
9. ¿Cuándo heredar y cuándo componer?
Heredá cuando la subclase es un tipo distinto y permanente; componé cuando es algo que el objeto tiene y puede cambiar. Un producto en oferta no es una especie de producto: la oferta empieza y termina, y la clase de un objeto no se puede cambiar. En la práctica, jerarquías de más de dos niveles casi siempre son un error de modelado.
10. Serializás una instancia con JSON.stringify y la volvés a leer con JSON.parse. ¿Qué te queda?
Un objeto plano: tiene los datos públicos, pero perdió los métodos y los campos privados (#stock no se serializa). plano instanceof Producto da false y llamar a plano.vender(1) tira TypeError. Para recuperar una instancia de verdad hace falta un método fábrica; para controlar qué sale, toJSON().

Resumen de la clase

Puntos clave para recordar

  • class es azúcar sintáctico sobre prototipos: los métodos siguen viviendo en Clase.prototype. Pero suma reglas propias: new obligatorio, sin hoisting, modo estricto siempre y métodos no enumerables.
  • Los datos van a la instancia y los métodos al prototipo: mil objetos, mil copias de los datos y una sola del método.
  • Un getter se lee sin paréntesis y sirve para valores derivados; un setter existe para validar antes de guardar. Si el campo se llama igual que el setter, hay recursión infinita: el dato va en #campo.
  • El prefijo # hace un campo o método privado de verdad (acceder desde afuera es error de sintaxis). El objetivo es que las reglas de negocio no se puedan esquivar.
  • static es de la clase, no de la instancia: contadores, constantes y métodos fábrica como Producto.desdeJSON().
  • JSON.parse devuelve objetos planos, no instancias: se pierden los métodos y los campos privados. Para volver a una instancia hace falta una fábrica; para controlar la salida, toJSON().
  • extends + super() agrega un eslabón a la cadena de prototipos. super() va antes de tocar this.
  • Polimorfismo: si cada subclase implementa el mismo método a su manera, el código que las usa deja de necesitar if por tipo.
  • this depende de cómo se invoca, no de dónde se escribió. Pasar un método como callback lo pierde: se arregla con bind, con una arrow que envuelve, o con un campo de clase arrow.
  • Heredá cuando es; componé cuando tiene.

Lo que viene
Con esto se cierra la unidad de JavaScript. La próxima es Express y arquitecturas de API, y las clases de esta guía reaparecen enseguida: los services y repositories se escriben así, y el bug del this perdido aparece la primera vez que se pasa un método de un controller a una ruta. Más adelante, en TypeScript, esta misma sintaxis suma private, readonly y tipos; y en la unidad de persistencia, la clase Producto de acá se convierte —casi sin tocarla— en la entidad que se guarda en la base de datos.
