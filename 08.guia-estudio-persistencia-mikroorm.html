Persistencia: MikroORM y MySQL

Del array en memoria a una base de datos real — Material de estudio

Prerequisito: la API en capas con validación (unidad 6) y TypeScript, en especial clases e interfaces (unidad 7)
Introducción

Contenidos de la guía

Esta guía cierra un arco que empezó dos unidades atrás. En arquitecturas separamos la API en capas con el argumento de que "si algún día cambia la persistencia, se toca un solo archivo". En TypeScript escribimos esa promesa como tipos que el compilador verifica. Hoy se cobra: el repository pasa de un array a MySQL y el service no se toca.

El objetivo no es aprender la API de una librería, sino entender el modelo mental de un ORM: qué hace por vos, qué sigue siendo tu responsabilidad, y qué costos esconde la comodidad.

Bloque 1

El array que se borra al reiniciar

Arrancamos con el repository que venís usando desde la unidad de arquitecturas, tal cual quedó después de TypeScript y Zod:

7.3 — productos.repository.ts
const productos: Producto[] = [{ id: 1, nombre: 'Teclado', precio: 25000 }];

export async function guardar(datos: ProductoNuevo): Promise<Producto> {
  const nuevo: Producto = { id: productos.length + 1, ...datos };
  productos.push(nuevo);
  return nuevo;
}

Funciona, está tipado, valida lo que entra. Y tiene un problema que no se arregla con más TypeScript: ese array vive en la memoria del proceso de Node. Se termina el proceso, se termina el array.

La prueba dura treinta segundos: creá tres productos con el .http, pará el servidor con Ctrl+C, levantalo de nuevo y hacé el GET. Vuelve el teclado solo. Eso es todo lo que significa que los datos no persistan.

Y no es solo el reinicio. El mismo array explica tres problemas más, que en un TP no se ven y en producción sí:

  1. No se puede escalar. Dos instancias de la API para aguantar más tráfico son dos arrays distintos: lo que se crea en una no existe en la otra.
  2. No se puede consultar de verdad. "Los productos de más de $20.000 ordenados por precio, de a 20 por página" es un filter().sort().slice() sobre toda la colección en memoria. Con 500.000 productos, no entra.
  3. No hay integridad. Nada impide dos productos con el mismo nombre, o un producto apuntando a una categoría que no existe.

La respuesta a los cuatro problemas es la misma y tiene cincuenta años: una base de datos. Lo que falta decidir es cómo hablarle desde Node.

Importante
El array nunca estuvo mal: fue la decisión correcta para aprender las capas sin mezclar temas. Lo que cambia hoy es un solo archivo —el repository— y esa es justamente la tesis de la unidad de arquitecturas puesta a prueba. Vale decirlo así de explícito: hoy se cobra la deuda de esa clase.
Bloque 2

Qué hace un ORM y qué no

Hay dos formas de hablarle a MySQL desde Node. La primera es el driver pelado (mysql2): mandar strings de SQL y recibir filas.

con el driver, a mano
const [filas] = await conexion.query(
  'SELECT id, nombre, precio FROM producto WHERE precio > ?',
  [20000],
);

// filas es un array de objetos planos, sin tipo:
// [ { id: 1, nombre: 'Teclado', precio: 25000 } ]

// y para guardar, el mapeo al revés, campo por campo:
await conexion.query(
  'INSERT INTO producto (nombre, precio) VALUES (?, ?)',
  [producto.nombre, producto.precio],
);

Funciona perfecto y es lo que usa el ORM abajo. Pero deja tres trabajos repetitivos en manos de quien escribe: armar el SQL, convertir filas en objetos y objetos en filas, y acordarse de que el SELECT devuelve any.

La segunda forma es un ORM (Object-Relational Mapper): una capa que traduce entre el mundo de objetos de TypeScript y el mundo de tablas de SQL.

con el ORM
const caros = await em.find(Producto, { precio: { $gt: 20000 } });
// caros es Producto[] — instancias de la clase, tipadas

Las dos familias de ORM

Conviene nombrarlas porque el vocabulario aparece en cualquier documentación:

Active RecordData Mapper
Quién guardaLa entidad: producto.save()Un objeto aparte: el EntityManager
La entidad sabe……de la base de datos…solo de su dominio
EjemplosSequelize, Eloquent (PHP)MikroORM, TypeORM (modo DM), Doctrine

MikroORM es Data Mapper, y esa es la razón por la que la entidad va a ser una clase común que no hereda de nada. Es también el motivo de que no exista producto.save() — lo que sorprende a todo el mundo el primer día y se explica en el bloque 5.

Qué NO hace un ORM

Esta parte importa tanto como la anterior, y es la que suele faltar:

  • No te exime de saber SQL. Cuando una consulta tarde, la vas a leer en SQL. El ORM genera consultas; entender lo que generó es tu trabajo.
  • No diseña el modelo por vos. Qué tablas, qué claves, qué índices: eso sigue siendo diseño de base de datos, y el ORM ejecuta lo que le pidas aunque esté mal.
  • No hace la aplicación más rápida. Suele hacerla más lenta que el SQL escrito a mano. Lo que gana es tiempo de desarrollo y consistencia.
  • No valida lo que entra por HTTP. Eso sigue siendo Zod, en el borde.
Cuidado
La comodidad de un ORM es real y su costo también: es una capa de abstracción más, y las abstracciones filtran. Cuando algo anda raro —una consulta lenta, un dato que no se guardó, una relación vacía— hay que poder bajar un nivel y mirar el SQL. Por eso todos los ejemplos de la unidad corren con debug: true.

El detalle que hace perder la primera media hora

El ORM necesita saber que nombre es string y precio es number. Pero los tipos de TypeScript se borran al compilar — eso lo vimos en la unidad anterior. Entonces, ¿de dónde los saca?

  1. Con emitDecoratorMetadata, una opción de TypeScript que deja los tipos como metadata en el JavaScript emitido. Pero eso lo emite tsc, y nosotros en desarrollo corremos con tsx, que compila con esbuild y no lo soporta.
  2. Con TsMorphMetadataProvider, que lee los archivos .ts y saca los tipos de ahí. Funciona con tsx y permite escribir @Property() sin repetir el tipo.

Usamos la segunda. Si te salteás ese metadataProvider, el error es este:

Error: Please provide either 'type' or 'entity' attribute in Producto.id.
If you are using decorators, ensure you have 'emitDecoratorMetadata'
enabled in your tsconfig.json.

El mensaje sugiere prender emitDecoratorMetadata, y con tsx eso no alcanza: es un caso donde el error te manda para el lado equivocado. La otra salida, si no se quiere el paquete extra, es declarar el tipo en cada decorador: @Property({ type: 'string' }).

Cuidado
TsMorphMetadataProvider lee los .ts, así que en producción —donde corre el dist/ compilado y los .ts no están— hay que generar la caché de metadata durante el build (mikro-orm cache:generate --combined) o usar tipos explícitos. En desarrollo no se nota, y por eso agarra desprevenido justo el día del deploy. Vuelve en la unidad 11.
Bloque 4

Entidades: de la clase a la tabla

Acá se cobra lo que quedó plantado en la unidad de TypeScript. Una entidad es la clase del ejemplo 7.1.4 con anotaciones:

src/entities/producto.entity.ts
import { Entity, PrimaryKey, Property } from '@mikro-orm/decorators/es';
import type { Opt } from '@mikro-orm/core';

@Entity()
export class Producto {
  @PrimaryKey()
  id!: number;

  @Property({ length: 100 })
  nombre!: string;

  @Property()
  precio!: number;

  @Property({ nullable: true })
  descripcion?: string;

  @Property()
  creadoEn: Opt<Date> = new Date();
}

Cuatro cosas para mirar, en este orden:

  • La clase no hereda de nada. Es una clase de TypeScript común. Eso es Data Mapper: la entidad no sabe guardarse a sí misma.
  • El ! es de TypeScript, no del ORM. Significa "confiá en mí, esto se va a inicializar aunque no lo asigne en el constructor". Quien lo asigna es el ORM al traer la fila de la base.
  • nullable: true y el ? tienen que decir lo mismo. Si la columna admite NULL pero el tipo dice que siempre hay un string, el modelo miente y el compilador te va a dejar hacerlo.
  • Opt marca una propiedad que no hay que pasar al crear porque ya tiene valor. Sin eso, em.create() exige creadoEn.

En qué se convierte

La pregunta que ordena todo esto es "¿y esto qué tabla genera?". Se responde sin ejecutar nada, con getCreateSchemaSQL():

create table `producto` (
  `id` int unsigned not null auto_increment primary key,
  `nombre` varchar(100) not null,
  `precio` int not null,
  `descripcion` varchar(255) null,
  `creado_en` datetime not null
) default character set utf8mb4 engine = InnoDB;

Tres detalles para no pasar por alto:

  1. creadoEn pasó a creado_en. El ORM traduce camelCase a snake_case por convención, y es configurable. Es un buen momento para decir que SQL y JavaScript tienen convenciones de nombres distintas y que el mapeo también es eso.
  2. nombre quedó varchar(100) porque se lo pedimos. Sin length, el default es 255.
  3. precio quedó int. Nadie lo decidió: es el default para number. Para plata es una mala idea —no hay centavos— y se arregla con @Property({ columnType: 'decimal(10,2)' }).
Importante
El punto 3 es la moraleja de todo el bloque: el ORM elige por vos cuando vos no elegís. Y elige razonablemente, no siempre bien. Que un precio se guarde como entero es exactamente el tipo de bug que aparece seis meses después, cuando alguien carga $1.999,50 y se guarda 1999.

Del modelo a la base, en desarrollo

Con las entidades escritas, hay tres formas de crear las tablas. Conviene nombrarlas juntas para que quede claro cuál es cuál:

MétodoQué haceCuándo
schema.create()Crea las tablas de cero.Base vacía.
schema.update()Compara el modelo con la base y aplica las diferencias.Desarrollo, mientras el modelo cambia todos los días.
schema.refresh()Drop y create: deja la base igual al modelo, borrando todo.Ejemplos y pruebas. Nunca con datos que importen.

Las tres son de desarrollo. Para producción están las migraciones, en el bloque 8.

Bloque 5

El EntityManager: por qué no hay save()

Este es el bloque conceptual de la unidad. Todo lo demás es sintaxis; esto es el modelo mental.

La primera sorpresa aparece al querer guardar algo:

el update completo, en MikroORM
const producto = await em.findOneOrFail(Producto, 1);

producto.precio = 27000;   // ← esto es todo el "update"

await em.flush();          // ← acá recién viaja el SQL

No hay producto.save() ni em.update(producto). Se le asigna a la propiedad como a cualquier objeto de JavaScript, y en algún momento se hace flush(). Eso desconcierta el primer día y es la consecuencia directa de dos patrones.

Unit of Work: anotar todo y mandarlo junto

El EntityManager no ejecuta a medida que le hablás: anota. Recién en el flush() compara el estado actual de todo lo que tiene contra el estado en que lo leyó, calcula qué cambió y lo manda, en orden, dentro de una transacción.

productos[0].precio = 26000;                              // UPDATE
em.create(Producto, { nombre: 'Webcam', precio: 45000 }); // INSERT
em.remove(productos[2]);                                // DELETE

await em.flush();  // las tres cosas, una transacción, o todas o ninguna

Dos consecuencias que valen oro y que no son obvias:

  • El UPDATE que genera lleva solo los campos que cambiaron, porque el ORM sabe cómo estaba la fila cuando la leyó.
  • La atomicidad sale gratis: si el DELETE falla, el INSERT y el UPDATE tampoco se aplican. Con el driver a mano, esa transacción la abrís y la cerrás vos.

Identity Map: una fila, un objeto

const a = await em.findOne(Producto, 1);  // ← genera un SELECT
const b = await em.findOne(Producto, 1);  // ← NO genera nada

a === b;              // true — es el mismo objeto

a.precio = 99999;
b.precio;             // 99999

Dentro de un mismo EntityManager, la fila 1 es un objeto. No es solo ahorrarse una consulta: es una garantía de consistencia. Si dos partes del código piden el producto 1 y una lo modifica, la otra ve el cambio, porque son la misma instancia. Sin identity map serían dos copias que al guardarse se pisan.

Importante
Conectar con la unidad de objetos: esto es paso por compartición (el ejemplo 4.10) aplicado a escala de aplicación. Dos variables que apuntan al mismo objeto no son dos objetos. El identity map es esa misma idea, sostenida a propósito por el ORM para todo lo que se leyó de la base.

Y por eso, fork()

Si el identity map es tan útil, ¿por qué no tener uno solo para toda la aplicación? Porque un EntityManager que viva lo que vive el servidor se va llenando de entidades viejas: una fuga de memoria y, peor, datos desactualizados servidos como frescos.

Por eso cada unidad de trabajo usa su propio fork(), con su identity map vacío. En una API HTTP, una unidad de trabajo es un request — y de eso se ocupa el bloque siguiente.

OperaciónCuándo viaja el SQL
em.create()Marca para insertar. En el flush().
em.find() / findOne()Ya mismo. Es la única que consulta en el momento.
Asignar a una propiedadMarca para actualizar. En el flush().
em.remove()Marca para borrar. En el flush().
Lo que sigue
Con esto alcanza para el ORM solo. Lo que falta es meterlo en la API de la unidad 6 sin romper las capas — y ahí aparece el middleware que, si se olvida, hace que dos usuarios vean los datos del otro.
Bloque 6

La API en capas, ahora contra MySQL

Volvemos al proyecto de la unidad anterior —el 7.3, con Zod— y le cambiamos la persistencia. La estructura de carpetas casi no se mueve:

src/

├─ routes/       productos.routes.ts    ← sin cambios
├─ controllers/  productos.controller.ts ← sin cambios

Sin cambios. Ni se enteran de que hay una base.

El repository, en las dos versiones

7.3 — el array
const productos: Producto[] = [];

export async function

  return productos;
}

export async function
guardar(datos: ProductoNuevo) {
  const nuevo = {
    id: productos.length + 1,

8.2 — MySQL
import { orm } from '../db.js';

export async function
findAll(): Promise<Producto[]> {
  return orm.em.findAll(Producto);

  const producto =

Las firmas son iguales. Por eso el service no se toca:

productos.service.ts — idéntico al de 7.3
export async function crearProducto(datos: ProductoNuevo): Promise<Producto> {
  const existente = await repo.findByNombre(datos.nombre);

  if (existente) {
    throw new ValidationError(`Ya existe un producto llamado "${datos.nombre}"`);
  }

  return repo.guardar(datos);
}

El middleware que no se puede olvidar

src/app.ts
import { RequestContext } from '@mikro-orm/core';

app.use((req, res, next) => {
  RequestContext.create(orm.em, next);
});

Crea un fork del EntityManager para cada request. A partir de ahí, orm.em dentro del repository devuelve el fork de ese request: por eso el repository puede usarlo sin recibirlo por parámetro.

Es el em.fork() del bloque 5 llevado a HTTP. Qué pasa si falta —vale probarlo comentando esas líneas y mandando dos requests—:

  • Todos los requests comparten un identity map que nunca se vacía: fuga de memoria que crece con el uptime.
  • Entidades de un usuario visibles en el request de otro, y flushes que guardan cambios a medio hacer de otra parte.
  • Con requests concurrentes, MikroORM directamente corta: "Using global EntityManager instance methods for context specific actions is disallowed".

Si la entidad ya tipa, ¿para qué Zod?

La pregunta aparece sola. La respuesta es que cada control actúa en un momento distinto:

ControlDóndeQué garantiza
ZodMiddleware, antes del controllerEl formato de lo que entra
ServiceCapa de negocioReglas que dependen del estado (nombre repetido)
Entidad + MySQLLa baseQue lo guardado sea válido, pase lo que pase

Sin Zod, un {"precio": "60000"} llegaría hasta el driver y el error sería un 500 feo en vez de un 400 que dice qué campo está mal.

Dato
El unique de la columna atrapa un caso que el service no puede: dos requests simultáneos con el mismo nombre pasan los dos el SELECT de la validación —todavía no hay ninguno— y uno de los dos INSERT tiene que fallar. Por eso el errorHandler suma UniqueConstraintViolationException y responde 409. La validación en la aplicación da buenos mensajes; la restricción en la base es la que de verdad garantiza el dato.
Bloque 7

Relaciones, populate y el N+1

Un modelo con una sola entidad no muestra para qué sirve una base relacional. Agregamos categorías: un producto pertenece a una categoría, una categoría tiene muchos productos.

Lado dueño (muchos)
@Entity()
export class Producto {
  // ...

  @ManyToOne(() => Categoria)
  categoria!: Categoria;
}
Lado inverso (uno)
@Entity()
export class Categoria {
  // ...

  @OneToMany(() => Producto,
    (p) => p.categoria)
  productos =
    new Collection<Producto>(this);
}

La relación se declara dos veces, pero en la base existe una sola vez:

GeneraRegla
@ManyToOneLa columna categoria_id, su FK y su índiceLa clave foránea va siempre del lado muchos
@OneToManyNadaSolo necesita decir cuál propiedad del otro lado es la dueña

Y en el código se asignan objetos, no ids:

const perifericos = em.create(Categoria, { nombre: 'Periféricos' });
em.create(Producto, { nombre: 'Teclado', precio: 25000, categoria: perifericos });

await em.flush();
// el ORM ordena solo: primero la categoría, después el producto que la referencia

Las colecciones no vienen cargadas

Collection no es un array: es un array que sabe si está cargado. Por defecto no lo está, para que pedir una categoría no arrastre todos sus productos sin que nadie lo pida.

const categoria = await em.findOneOrFail(Categoria, 1);

categoria.productos.isInitialized();   // false
categoria.productos.getItems();        // vacío — ¡y no es que no haya!

await categoria.productos.init();      // ahora sí sale el SELECT
Cuidado
Recorrer una colección sin inicializar devuelve vacío sin avisar. Es el bug clásico de la unidad: la lista sale vacía en el JSON de la respuesta y los datos están en la base. Si un alumno dice "no me trae los productos", esto es lo primero para mirar.

El N+1

Es el error de performance más común con cualquier ORM, en cualquier lenguaje, y es invisible hasta que la tabla crece:

N+1 consultas
const cats = await em.findAll(Categoria);
// ↑ 1 consulta

for (const c of cats) {
  await c.productos.init();
  // ↑ +1 por cada categoría
  console.log(c.productos.length);
}
2 consultas, siempre
const cats = await em.findAll(
  Categoria,
  { populate: ['productos'] },
);

for (const c of cats) {
  console.log(c.productos.length);
}

Con 3 categorías son 4 consultas contra 2, y no se nota. Con 300 son 301 contra 2, y el endpoint tarda diez segundos. El resultado es idéntico; lo único que cambia es cuántas veces se fue hasta la base.

Importante
La regla práctica, corta: si el endpoint devuelve la relación, populate; si no, no la cargues. Y con debug: true prendido mientras se desarrolla, el N+1 se ve a simple vista — veinte consultas idénticas seguidas en la consola son inconfundibles.

Muchos a muchos, en dos minutos

Un producto puede tener varias etiquetas y una etiqueta está en varios productos. En SQL eso no entra en una columna: hace falta una tabla intermedia. Con @ManyToMany, el ORM la crea y la mantiene, y no hay ninguna clase que la represente.

@ManyToMany(() => Etiqueta, (e) => e.productos, { owner: true })
etiquetas = new Collection<Etiqueta>(this);

// producto_etiquetas(producto_id, etiqueta_id), con PK compuesta
teclado.etiquetas.add(oferta);
await em.flush();

Eso alcanza mientras la relación no tenga datos propios. Si hace falta guardar la cantidad de un producto en un pedido, o cuándo se asignó la etiqueta, la tabla intermedia deja de ser intermedia: pasa a ser una entidad más, con sus dos @ManyToOne.

Bloque 8

Migraciones

Hasta acá el esquema se sincronizaba con schema.update(). Es cómodo mientras se desarrolla y no sirve para producción. El caso que lo demuestra es concreto:

Se agrega stock: number a la entidad. La tabla producto ya existe con datos adentro. Un alter table producto add stock int not null a secas falla: MySQL no sabe qué stock ponerle a las filas que ya están. ¿Cero? ¿NULL? ¿El promedio? Es una decisión de negocio, y ninguna herramienta puede tomarla por vos.

Una migración es esa decisión, escrita como código y versionada en git:

src/migrations/Migration20260805093000.ts
export class Migration20260805093000 extends Migration {

  override up(): void | Promise<void> {
    this.addSql('alter table `producto` add `stock` int not null default 0;');
  }

  override down(): void | Promise<void> {
    this.addSql('alter table `producto` drop column `stock`;');
  }

}

Ese default 0 es la decisión: "los productos que ya existían arrancan sin stock".

El flujo

  1. Se cambia la entidad.
  2. npm run orm -- migration:create: la CLI compara el modelo contra la base y escribe el archivo.
  3. Se lee el archivo generado. No es opcional: la CLI acierta el 90% de las veces, y el 10% restante es justo el que borra datos.
  4. Se commitea junto con el cambio de la entidad, en el mismo commit.
  5. migration:up en cada ambiente: la máquina de cada uno, el servidor de pruebas, producción.

La tabla de control

La primera vez que se corre migration:up, el ORM crea mikro_orm_migrations: una fila por migración aplicada, con su fecha. Es el hasta acá llegué de esa base. Por eso una misma migración puede estar aplicada en tu máquina y pendiente en producción, y por eso migration:up se puede correr dos veces sin miedo: la segunda no hace nada.

schema.update()Migraciones
Registro de qué se aplicóNoSí, en una tabla

1. El TP funciona igual con un array en memoria. ¿Qué gana una base de datos, además de que los datos no se borren al reiniciar?
Tres cosas más. Escala: dos instancias de la API para aguantar más tráfico son dos arrays distintos, y lo que se crea en una no existe en la otra. Consulta: filtrar y ordenar sobre un array es recorrerlo entero en memoria, y con 500.000 productos no entra. Integridad: nada impide dos productos con el mismo nombre o uno apuntando a una categoría que no existe. La base resuelve las cuatro.
2. En MikroORM no existe producto.save(). ¿Cómo actualizás un producto, entonces?
Le asignás a la propiedad como a cualquier objeto y después hacés flush():
const producto = await em.findOneOrFail(Producto, 1);
producto.precio = 27000;
await em.flush();
El EntityManager no ejecuta a medida que le hablás: anota. En el flush() compara el estado actual contra el que leyó, calcula qué cambió y lo manda todo junto en una transacción. Como sabe cómo estaba la fila, el UPDATE lleva solo los campos que cambiaron. Eso es el patrón unit of work, y es la razón de que no haya save(): la entidad no sabe guardarse, de eso se ocupa el EntityManager.
3. ¿Qué garantiza el identity map, y por qué entonces hace falta un fork() por cada request?
Garantiza que, dentro de un mismo EntityManager, una fila sea un solo objeto: buscar dos veces el producto 1 devuelve la misma instancia y la segunda búsqueda no genera consulta. Es consistencia, no solo ahorro: si una parte del código lo modifica, la otra ve el cambio. Pero un EntityManager que viviera todo lo que vive el servidor se iría llenando de entidades viejas — fuga de memoria y datos desactualizados servidos como frescos. Por eso cada unidad de trabajo usa su propio fork, con el identity map vacío. En una API, una unidad de trabajo es un request.
4. ¿Qué pasa si te olvidás del middleware RequestContext?
Todos los requests comparten el mismo EntityManager, así que comparten un identity map que nunca se vacía: es una fuga de memoria que crece con el uptime del servidor. Peor todavía, podés ver entidades de otro usuario en tu request, y un flush() puede terminar guardando cambios a medio hacer de otra parte. Con requests concurrentes MikroORM directamente corta con «Using global EntityManager instance methods for context specific actions is disallowed». El middleware es una línea y es el em.fork() llevado a HTTP.
5. Si la entidad ya declara que precio es number, ¿para qué sigue haciendo falta Zod?
Porque controlan cosas distintas en momentos distintos. La entidad describe cómo se guarda el producto (columna, tipo SQL, largo, índices) y actúa cuando el dato ya entró al sistema. Zod describe qué se acepta en el body y actúa en el borde, antes de que entre. Sin Zod, un {"precio": "60000"} llegaría hasta el driver de MySQL y el error sería un 500 en vez de un 400 que dice qué campo está mal. Y encima queda un tercer control: el unique de la columna, que atrapa lo que el service no puede — dos requests simultáneos con el mismo nombre pasan los dos la validación, y uno de los dos INSERT tiene que fallar.
6. Tenés un endpoint que lista categorías con sus productos y en la consola aparecen 301 consultas. ¿Qué pasó?
Es el N+1: una consulta para traer las categorías y una más por cada categoría, porque estás navegando la relación adentro de un bucle (await c.productos.init()). Se arregla pidiendo de entrada lo que vas a usar:
await em.findAll(Categoria, { populate: ['productos'] });
Eso son 2 consultas fijas, haya 3 categorías o 300. La regla práctica: si el endpoint devuelve la relación, populate; si no, no la cargues. Con debug: true se ve a simple vista mientras desarrollás.
7. Pedís una categoría, recorrés categoria.productos y sale vacío, pero en la base los productos están. ¿Qué pasó?
La colección no estaba inicializada. Collection no es un array: es un array que sabe si está cargado, y por defecto no lo está, para que pedir una categoría no arrastre todos sus productos sin que nadie lo pida. Recorrerla sin cargar devuelve vacío sin avisar. Se resuelve con populate al buscar, o con await categoria.productos.init().
8. ¿Por qué schema.update() no va a producción, si deja la base igual al modelo?
Porque no sabe qué hacer con los datos que ya están. El caso típico: agregás stock: number y la tabla ya tiene filas; un add stock int not null a secas falla, porque MySQL no sabe qué stock ponerle a lo que ya existe. Poner default 0 es una decisión de negocio que ninguna herramienta puede tomar por vos. Además update() no deja registro de qué se aplicó, no se puede revisar en un pull request ni volver atrás. Las migraciones son ese cambio escrito como código y versionado: llegan en el git pull, se aplican en orden en cada ambiente y quedan anotadas en la tabla mikro_orm_migrations.
Cierre

Resumen

  • Un array en memoria se pierde al reiniciar, no escala a más de un proceso, no se consulta de verdad y no garantiza integridad. Las cuatro cosas las resuelve una base de datos.
  • Un ORM traduce entre objetos y tablas. No reemplaza saber SQL, no diseña el modelo y no valida lo que entra por HTTP.
  • MikroORM es Data Mapper: la entidad es una clase común que no sabe guardarse; de eso se ocupa el EntityManager.
  • La entidad es la clase de TypeScript con decoradores. Cuando no elegís el tipo de columna, el ORM elige por vos — y para plata, int no es lo que querés.
  • No hay save(): se modifica el objeto y se hace flush(). El unit of work junta todos los cambios y los manda en una transacción, con UPDATE de solo los campos que cambiaron.
  • El identity map garantiza que, dentro de un EntityManager, una fila sea un objeto. Por eso cada unidad de trabajo necesita su fork().
  • En una API, una unidad de trabajo es un request: eso es RequestContext, y olvidarlo mezcla datos entre usuarios.
  • Cambió un solo archivo, el repository. El service quedó idéntico: es la promesa de la unidad de arquitecturas, cumplida.
  • En las relaciones, la FK va del lado muchos y las colecciones no vienen cargadas. Navegar una relación dentro de un bucle es el N+1; la respuesta es populate.
  • En producción, el esquema se cambia con migraciones versionadas, no con schema.update(): dejan registro, se revisan, se vuelven atrás y deciden qué pasa con los datos que ya están.

Lo que sigue

Con una base de datos andando, aparece la entidad que faltaba: usuarios. La próxima unidad es autenticación y autorización — hashear contraseñas con bcrypt, emitir un JWT al hacer login y un middleware que proteja las rutas. Y ahí también se muda por fin lo que hoy quedó feo a propósito: las credenciales de la base salen del código y se van a un .env, junto con el secret del JWT.
